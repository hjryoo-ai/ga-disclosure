단서: 받은 것은 11단계 진행 기록과 요약이고 `docs/phase-06B-보고서.md`(`b28ed35`) 본문은 보지 못했다. 병합을 막지는 않는다 — 단계마다 중간 회신·질문·별도 승인(§9)으로 심사가 이미 진행됐고, CI 두 run·모듈별 수 일치·`TZ=UTC` 전체 check·주입 151건·데모(seed 2회, HTTP 2회)가 확인됐다. **Phase 7 계획 맨 앞에 6B 보고서의 D 표 전체와 "첫 시도에 놓친 것"(T4·P4) 표**를 붙이고, 넓히는 항목이 있으면 표시한다.

## 1. 인정하는 것

- **HTTP 데모의 첫 실패를 결함이 아니라 탐지의 정상 동작으로 읽은 것.** HTTP로 등록한 고객이 시드 고객과 기기 지문을 공유해 `SIGNATURE_DEVICE_REUSE`가 섰고, 관리자 확인이 그 플래그를 요구했다. 6A에서는 두 서명자가 같은 고객이라 한 번도 발화하지 않았던 경로다. 데모가 **6B에서 만든 관리자 플래그 경로를 실제로 쓰게** 고친 것이 맞고, 실패한 첫 시도가 남긴 상태(부분 서명·사용된 토큰)를 지우지 않고 보고서에 적은 것도 맞다.
- **CI 숫자를 처음 읽었을 때 "407건 중 398 실패"가 초록 빌드와 맞지 않는다고 멈춘 것.** `no-docker` 잡의 XML이었고, `build` 잡의 HTML 보고서에서 다시 셌다. 숫자가 맞지 않으면 어느 쪽이 틀렸는지 찾을 때까지 인용하지 않는다 — 그대로다.
- **R1을 앱 전체로 켰는데 기존 테스트 변경이 0건**이었던 것과, 그 사실을 "다른 라우트에도 적용된다"는 테스트로 따로 증명한 것. 계약(`additionalProperties: false`)과 구현이 이제 같다.
- **V20 인덱스를 "있다"가 아니라 "플래너가 쓴다"로 증명**한 것(5,000행).
- 재가져오기에서 `UNMATCHED` 행이 중복되지 않은 것을 따로 확인한 것 — 원장(결정 1)이 실제로 일한다는 증거다.
- 이번 Phase 전체로: 빈 보안 알림 둘을 직접 읽어 실제 결함 둘(계약 연결 영구 실패·폐기의 보류 미검사)을 찾았고, 자동 검토의 경로 우회 지적을 확인하다 6A부터 있던 같은 부류를 하나 더 찾았다. 알림을 신호로 쓰고 판단은 코드에서 했다.

## 2. 이번 Phase에서 내가 틀렸던 것 (기록)

- 조건 3(고객 등록)의 전제 — Phase 2가 이름·전화로 중복을 본다고 가정했다. 아니었고, 그 결과 "같은 422" 요구가 성립하지 않았다. Claude Code가 멈추고 물은 것이 맞았다.
- `42c2fef` 방향(무효·정정 보유 연결을 AMBIGUOUS로)은 Claude Code의 수정이었지만, 그 질문을 받고도 중간 회신에서 EXPIRED를 빼먹었다. 정의("유효한 보유자")에서 따라 나오는 것을 Claude Code가 채웠다.
