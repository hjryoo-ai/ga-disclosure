# Phase 7 수용 심사 결과 (2026-10-10)

## 판정: 수용. PR #12 병합 승인(merge commit), `phase-7` 태그 유지

단서: 요약만 받았고 `docs/phase-07-보고서.md`(`c1bed52`) 본문은 보지 못했다. 병합을 막지 않는다 — CI 세 run·모듈별 수 일치·주입 27건(첫 시도 누락 0)·E2E 12건의 네 가지 전수 검사(CSP·외부 출처·누출·접근성 0)·61건 재전송 후 37개 표 행 수 불변이 확인됐다. **Phase 8 계획 맨 앞에 Phase 7 보고서 §5 전체와 넓힘·계약 추가 표**를 붙인다.

## 1. 인정하는 것

- **"2회 실행 NOOP"를 화면에서 증명하는 방법.** 화면의 쓰기 61건을 같은 멱등 키로 재전송하고 37개 표의 행 수가 전부 같음을 본 것은, 서버 쪽 데모 NOOP보다 강한 증거다. 멱등 키를 본문에서 파생하지 않고 행위마다 난수로 둔 근거(두 번째 "비교"가 옛 답을 재생하는 문제, 고객 등록 본문 해시의 복원 위험 — 6B D-1과 같은 논리)도 맞다.
- **E2E가 강제한 화면 변경을 숨기지 않은 것.** 모바일 날짜 선택기가 타이핑을 무시해 **생년월일 없이 고객이 등록되던** 것은 E2E가 아니었으면 운영에서 발견됐을 결함이다. 서버가 생년월일을 선택 입력으로 받기 때문에 조용히 통과했다 — 이것이 "서버는 거부하지 않았다"가 "맞다"를 뜻하지 않는 사례다.
- **서명 버튼을 막지 않고 서버가 스크롤 완료를 판정**하게 둔 것. 화면에 업무 판단이 없다는 원칙을 가장 지키기 어려운 자리에서 지켰다.
- pdf.js 6.4.299에 `isEvalSupported`가 없고 eval도 없다는 것을 확인한 뒤, 계획의 주입 B1c를 **번들에 eval을 주입**하는 것으로 바꿔 CSP 검사가 잡는지 본 것. 주입의 목적(CSP가 eval을 막는가)을 지켰다.
- E2E 실패 스냅샷에 입력값이 남을 수 있다는 것을 스스로 찾아 CI 아티팩트에서 뺀 것, 그리고 `회수율`을 설계서 용어 `징구율`로 고친 것.

## 2. §5 판정

전부 수용. 넓힘 2건(Q1·Q3)은 계획 승인대로이고 서버 필터·업무 판단 0 조건이 지켜졌다(보고서에서 확인). 계약 추가 3건(`preview.watermark` 룰 키·데모 OIDC 계약·`preview.pdf`)은 추가형. 짚어 둘 것:

- **사유 코드를 자유 입력으로** 둔 것은 안전하다(서버가 닫힌 목록으로 거부한다)지만 사용성 결함이다. Phase 8에서 **룰 어휘 읽기 API**로 닫는다(아래 지시문).
- **로그인을 새 창으로** 열어 PKCE verifier를 메모리에 두는 것 — 저장소 사용 0 원칙에는 맞지만 팝업 차단 환경에서 실패한다. Phase 8 운영 문서에 전제 조건으로 적고, 대안(같은 창 리다이렉트 + verifier를 `sessionStorage`에 두는 것)은 **채택하지 않는다**는 결정과 이유(토큰 교환 전의 짧은 값이라도 저장소에 두지 않는다)를 설계서에.
- **환급금(해약환급금) 표가 봉인 PDF에 원시 하위 표로 렌더되는 것**은 3B 렌더러 범위가 맞고, 봉인 문서의 가독성 결함이므로 Phase 8에서 고친다. 단, 고치는 방법에 제약이 있다 — 아래 지시문 §3.
