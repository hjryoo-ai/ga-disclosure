## 0. 설계의 대전제

1. **확인서는 계약 체결 전에 완성되는 불변 문서다.** 봉인(seal) 이후 어떤 필드도 바뀌지 않는다. 정정은 **새 버전 발급(supersede) + 이전 버전 링크**로만 한다. 이것은 엔진의 "취소분개 + 재계산" 원칙을 문서에 옮긴 것이다.
2. **룰은 코드가 아니라 데이터다.** 서식 항목과 필수 여부, 최소 비교 개수(현행 3), 등급 임계치(현행 5단계), 순위·동점 규칙, 추천사유 코드, 필수 서명자 집합, 대상 계약 판정, 보존기간 — 전부 유효기간(effective date)을 가진 버전 데이터다. 확인서에는 **발급 시점에 적용된 룰 버전 ID가 박제**되고, 룰 해석은 엔진과 같은 규약(기준일 필수·단건 해석·Ambiguous fail-fast)을 따른다.
3. **돈에 관한 산출은 엔진이 한다.** 판매수수료 등급·순위는 엔진 API가 산출한 결과를 **스냅샷**으로 받아 표기한다. 워크플로 코드 어디에도 수수료율을 비교·정렬·분류하는 로직을 두지 않는다(아키텍처 테스트로 금지). 워크플로가 하는 것은 엔진 결과의 **정합성 검증과 표시**뿐이다.
4. **증거는 재현 가능해야 한다.** 확인서 = 정규화 JSON + 렌더된 PDF + 각각의 SHA-256 + 룰 버전 + 산출 스냅샷 ID. 서명은 사람이 아니라 **문서 해시에 귀속**된다. 감사 로그는 append-only 해시체인이며, 변조는 검증 명령 한 번으로 드러난다.
5. **테넌트 격리는 구조로 강제한다.** 포털과 동일한 3중 격리(컨텍스트·아키텍처 테스트·PostgreSQL RLS).
6. **고객 정보는 확인서 기재와 서명 전달에 필요한 최소만 다룬다.** 본 시스템은 CRM이 아니다(3순위 범위). 고객 식별은 `customer_ref`로 하고, 연락처는 원격 서명 링크 발송에만 쓰며 암호화 저장한다.
7. **시스템은 추천사유를 대신 쓰지 않는다.** 등급·순위·상품 정보는 자동으로 채우되, "왜 이 상품을 추천했는가"는 설계사가 직접 선택·기재한다. 자동 채움 문구는 불완전판매 시비의 씨앗이다.

### 1.4 정본 발급처 문제

협회 시스템으로 생성한 확인서는 법령 요건 충족이 "인정"되는 반면 자체 시스템은 GA가 스스로 적정성을 입증해야 한다. 어느 쪽이든 **워크플로·보관·감사·준법 점검**은 GA 몫이다. 따라서 본 시스템은 두 모드를 지원한다(D-2): 정본을 직접 발급하는 **SELF 모드**, 협회 시스템이 발급한 확인서를 수입해 보관·추적하는 **ASSOC 모드**. v1은 SELF 모드를 완전히 구현하고 ASSOC는 어댑터 인터페이스만 정의한다.

### 1.5 서명·확인의 법적 근거 (2026.9 조사 결과, D-9·D-10의 근거)

| 근거 | 내용 | 설계 귀결 |
|---|---|---|
| 전자서명법 제3조 | ① 전자서명은 전자적 형태라는 이유만으로 서명·서명날인·기명날인의 효력이 부인되지 않는다 ② 법령 또는 당사자 약정으로 전자서명을 선택하면 서명 효력을 가진다. 2020년 개정으로 공인전자서명 제도가 폐지됐고, 인정 전자서명인증사업자(KISA 임의인증)만 남았다 | 특정 인증수단이 법정 요건이 아니다. 대신 **어떤 전자서명도 법정 진정성립 추정을 받지 않으므로** 진정성립은 증거로 입증해야 한다 → 증거 패키지(§6.5)·해시 귀속·외부 타임스탬프가 설계의 핵심 |

## 2. 범위

### 2.1 v1 포함

- 워크플로 전 단계(§6.1): 작성 → 비교표 구성 → 등급·순위 산출 → 추천사유 → 봉인·발급 → 서명(고객·설계사·관리자) → 완료·보관
- 상품 카탈로그·유사상품군·추천가능 보험사 패널(§5), 임시등록 상품 경로
- 엔진 등급·순위 API 연동과 스냅샷(§4.1), 정합성 검증(§6.3)
- 검증 룰 엔진(§6.2, 룰=데이터) + 서식 템플릿(항목·필수·표시 순서 = 데이터)
- 봉인: 정규화 JSON·PDF/A 렌더·해시·확인서 번호·해시체인(§6.4)
- 서명 채널 3종: 현장 터치 서명, 원격 링크(SMS/알림톡 어댑터, v1은 콘솔 출력 스텁), 종이 서명 스캔 업로드(§6.5)
- 정정(supersede)·무효(void)(§6.6), 감사 로그 해시체인·검증 CLI(§6.7)
- 준법 콘솔: 징구율, 미징구·오류·기한초과 큐, 협회 점검 리포트, 룰 버전 관리(§6.8)
- 청약 게이트 API(§4.4), 아웃박스 이벤트 발행(§4.5, 포털 알림·3순위 CRM용)
- 멀티테넌시·인증·인가, 데모 테넌트

### 2.2 v1 제외 (후속)

자동차보험 확인서, 가입설계서 생성(보험사 시스템 영역), 협회 시스템 실연동(어댑터 스텁만), 공인·간편 전자서명 사업자 연동(어댑터만), CRM(3순위 — `customer_ref`로 인터페이스만), 보장분석, 확인서 다국어, 오프라인 작성(현장 네트워크 두절 시 임시 저장은 §14 #7).

### 2.3 컴플라이언스 경계 (설계 제약)

- 시스템은 의무 이행을 **돕고 기록**한다. 이행 여부의 최종 판단과 협회·당국 대응은 GA 준법감시 조직의 책임이며, 화면 어디에도 "법령 요건 충족"을 시스템이 단언하는 문구를 두지 않는다.
- 등급·순위의 산정 기준(임계치·모수·기간)과 서식 항목의 정본은 외부에 있다. 시스템은 "어떤 기준이 와도 데이터 교체만으로 대응"하는 구조를 증명하는 것으로 완료 기준을 삼는다.
- 확인서에는 등급·순위만 인쇄된다. **수수료율 수치·GA 내부 지급률은 확인서에도 화면에도 나오지 않는다.** 스냅샷은 평균 대비 비율과 등급·순위만 저장하고 원 수치는 엔진 `snapshotId`로만 역추적한다.
- 시뮬레이션·비교표는 **고객 설명용**이지만, 고객 화면(서명 페이지)은 봉인된 문서만 보여준다. 작성 중인 초안은 고객에게 노출되지 않는다.

### 3.1 아키텍처 결정 (Decision Record)

| ID | 결정 | 근거 | 기각한 대안 |
|---|---|---|---|
| D-1 | **별도 서비스·별도 DB** (`ga-disclosure`). 포털·엔진과는 계약(API·이벤트)으로만 결합. 웹은 포털 PWA 안의 라우트로 통합, 백엔드 공통 규약은 `platform-core` 라이브러리로 공유 | 포털은 "읽기 전용 투영"이 정체성이고 본 시스템은 쓰기 트랜잭션·고객 PII·불변 문서 저장이 본체다. 보안 등급과 보존 정책이 다르다. 설계사는 앱 하나만 쓰므로 프론트는 합친다 | 포털에 모듈 추가 — 읽기 모델 재구축(seq 0 replay) 원칙과 쓰기 워크플로가 한 DB에 섞임 |
| D-2 | **정본 발급처 모드**: `SELF`(자체 발급) / `ASSOC`(협회 시스템 발급 + 본 시스템은 준비·추적·보관·감사). 테넌트 파라미터, `IssuerPort` 어댑터 | 협회 시스템의 "요건 충족 인정"을 활용하려는 GA와 자체 발급으로 현장 흐름을 끊지 않으려는 GA가 공존한다 | SELF만 — 협회 인정을 원하는 GA에 판매 불가. ASSOC만 — 협회 시스템 API 공개 여부가 외부 변수 |
| D-3 | **등급·순위는 엔진 동기 API 산출·스냅샷**. 워크플로 내 수수료율 연산 금지(ArchUnit) | 대전제 3. 엔진이 이미 `RankingService`/`GradingPolicy`를 갖고 있고, 두 곳에서 산출하면 숫자가 어긋난다 | 협회 공시 데이터를 워크플로가 직접 읽어 등급 계산 — 엔진 원장과 불일치, 정책 버전 이중 관리 |
| D-4 | **확인서 불변 + 버전 + 해시체인. 서명은 문서 해시에 귀속** | 사후 점검·민원의 유일한 방어 자료. "서명 후 내용이 바뀌지 않았다"를 수학적으로 증명 | 서명 후 수정 허용 + 수정 이력 — 이력의 진위를 다시 증명해야 함 |
| D-5 | **상품 카탈로그는 외부 정본의 캐시** + 임시등록 경로 | 보험사·협회가 상품 정보 제공 주체이고 등록 지연이 현실(※ 임시등록) | 자체 상품 마스터를 정본으로 — 보험사 정보와 어긋날 때 책임 소재 불명 |
| D-6 | **PostgreSQL(RLS·JSONB) + S3 호환 오브젝트 스토리지(Object Lock/WORM)** | 문서 본문·서명 이미지·PDF는 DB 밖에서 불변 보관, 메타·해시는 DB | 전부 DB — 대용량 바이너리·보존 정책 분리 곤란 |
| D-7 | **서명 채널은 `SignatureChannel` 어댑터** (TOUCH_PAD / REMOTE_LINK / PAPER_SCAN / CERTIFIED_ESIGN 예약). 법적 효력 수준은 파라미터·미결정 | 현장 태블릿, 원격, 종이가 모두 쓰이는 이행기 | 단일 채널 — 현장 적응 실패 |
| D-8 | **청약 게이트는 조회 API로 제공, 강제 수준은 파라미터(BLOCK/WARN/OFF)** | 청약 시스템은 보험사·GA별로 다르다. 게이트를 우리가 막는 게 아니라 "확인서 완료 여부"를 답해 주면 상대가 막는다 | 청약 시스템 직접 연동 — 범위 초과 |
| D-9 | **관리자 확인은 기본 필수(`managerConfirmMode=REQUIRED`)**, OIDC 인증된 관리자의 승인 행위를 관리자 서명으로 기록. 완료(COMPLETED)는 관리자 확인 후에만. 게이트는 `pendingRoles`를 함께 응답하고 `gateRequiresManager`(기본 true)로 청약 진행 허용 시점을 테넌트가 정한다 | §1.5: 협회 표준서식이 현행 3자 서명을 요구하고 면제 건의 수용 근거 없음. 관리자는 내부 사용자라 SSO 인증만으로 고객보다 강한 신원 귀속이 생기므로 별도 서명 채널이 필요 없다 | 관리자 확인 생략 기본 — 협회 점검에서 "표준서식 미충족"으로 방어 불가. 관리자 수기 서명 강제 — 현장 지연만 늘고 증거력 차이 없음 |
| D-10 | **고객 서명은 일반 전자서명(전자서명법 §2②)을 기본으로 하고, 효력은 인증수단이 아니라 증거 패키지로 확보한다.** 원격 링크 기본 본인확인 = 1회용 링크 소유 + 생년월일 전체, 현장 서명 = 대면 확인 + 열람 완료 증거. 인정 전자서명인증사업자 연동(`CERTIFIED_ESIGN`)은 어댑터로 두고 테넌트 선택(v2) | §1.5: 보험업법·금소법이 일반 전자서명을 확인 방법으로 명시하고, 공인전자서명 폐지 후 어떤 수단도 법정 추정력이 없어 결국 "위·변조 불가 + 시점 + 신원 귀속" 증거가 효력을 좌우한다. 협회 연계 시스템도 SMS 링크 서명이 관행 | 인정 인증서 강제 — 고객 이탈·비용 대비 법적 이득 없음. 본인확인 없는 링크 서명 — 설계사 대리 서명 위험 |

### 3.3 모듈 구성 (Gradle 멀티모듈)

```
ga-disclosure/
├── contracts/                 # 엔진 API(openapi), 이벤트 스키마(events/v1), 룰 데이터 스키마(rules/v1)
├── platform-core              # (공유, Spring·DB 무의존) TenantContext, Won/Ratio/Ym/TenantId/AgentId 값객체, ArchUnit 공통 규칙 라이브러리
├── platform-spring            # (공유, Spring 의존) RLS 세션 바인딩(TenantSessionBinder), TenantScopedRepository, OIDC 리소스 서버 설정, 요청 필터
├── platform-canonical         # (공유, Spring 무의존) RFC 8785 JCS 정규화·SHA-256 해시(Canonicalizer). 룰 번들 해시·봉인·체인이 공용
├── disclosure-domain          # 애그리게이트(Disclosure, Item, Recommendation, Signature), 상태 열거형, 값객체. 의존성 없음
├── disclosure-rules           # 룰 버전 해석기(기준일 단건·Ambiguous fail-fast), 검증 룰 실행기, 서식 템플릿 모델. DB 무의존
├── disclosure-workflow        # 유스케이스(작성·구성·산출·봉인·서명·완료·정정·무효), 포트 인터페이스
├── disclosure-seal            # JCS 정규화, 렌더러(HTML→PDF/A), 해시·체인·채번
├── disclosure-sign            # 서명 세션, 채널 어댑터, 증거 패키징
├── disclosure-audit           # 감사 이벤트, 체인, 앵커, verify
├── disclosure-compliance      # 대상 계약 판정, 징구율, 큐, 리포트, 룰 거버넌스(번들 배포·승인·활성화 배치·번들 대사, §6.8)
├── disclosure-infra           # PostgreSQL(Spring Data JDBC)·Flyway·RLS, S3 어댑터, 엔진 클라이언트, 스텁 어댑터
├── disclosure-app             # Spring Boot 조립, 보안, 스케줄러
├── disclosure-demo            # 데모 테넌트·카탈로그·룰 시드, 엔진 스텁
└── web/                       # 포털 PWA 저장소에 라우트 추가(별도 패키지 `@ga/disclosure-ui`)
```

의존 방향: `app → api → workflow/compliance → rules/seal/sign/audit → domain → platform-core`. `rules`·`seal`·`audit`·`compliance`는 `platform-canonical`도 의존한다(Phase 1 신설). `platform-spring`은 `infra`·`api`·`app`만 의존한다. **`infra`는 포트-어댑터 방향으로 `workflow`·`rules`·`sign`·`audit`·`compliance`가 선언한 포트 인터페이스를 구현하므로 그 모듈들을 참조할 수 있고, 반대로 그 모듈들은 `infra`를 알지 못한다.** `infra`를 참조할 수 있는 모듈은 `app`뿐이다(Phase 0 확정). `rules`·`domain`·`seal`(렌더러 제외)·`platform-core`는 Spring·DB 무의존. 두 플랫폼 모듈은 `com.ga.platform` 그룹으로 발행하며, **본 저장소의 구현이 기준 구현(reference)이다** — 포털은 자체 작성하지 않고 이 아티팩트를 소비한다(포털 Phase 0 지시문 개정 필요).

### 3.4 데이터 흐름 4종

1. **작성 경로(동기, 설계사)**: 초안 생성 → 유사상품군 선택 → 카탈로그에서 상품 3개 이상 선택(임시등록 포함) → 엔진 등급·순위 산출(스냅샷) → 추천사유 입력 → 검증 룰 실행 → 봉인(번호·해시·PDF) → 서명 수집 → 완료. 모든 전이는 감사 로그 + 같은 트랜잭션.
2. **서명 경로(고객, 비로그인)**: 원격 링크 발송 → 1회용 토큰으로 서명 페이지 → 봉인 PDF 열람 → 본인확인(파라미터) → 서명 → 증거 저장 → 설계사에 알림.
3. **연동 경로**: 청약 시스템이 게이트 조회 → `COMPLETED` 확인서 존재 여부와 번호 응답. 계약 체결 후 `PolicyLinked`로 증권번호 연결. 아웃박스 이벤트를 포털(알림)·CRM(3순위)이 pull.
4. **점검 경로(배치)**: 매일 대상 계약(엔진/CRM에서 수신) 대비 완료 확인서를 대사 → 징구율·미징구 큐 갱신 → 체인 무결성 검증 → 앵커 저장 → 운영 알림.

## 4. 통합 계약 (Integration Contract v1)

`contracts/`에 OpenAPI·JSON Schema로 두고 양쪽 CI에서 검증한다. 버전·호환성 규칙은 포털 설계서 §4.5와 동일(필드 추가 호환, 삭제·의미 변경은 version 증가, 상위 버전 수신 시 정지).

### 4.1 엔진 API — 등급·순위 산출

```
POST /internal/v1/disclosure/commission-grades
{
  "tenantId": "T1",
  "asOfDate": "2026-09-23",
  "productGroupCode": "PG-HEALTH-SIMPLE-NR",          // 유사상품군(외부 코드 체계)
  "products": [
    { "productKey": "INS-A:PRD-1001", "insurerCode": "INS-A" },
    { "productKey": "INS-B:PRD-2044", "insurerCode": "INS-B" },
    { "productKey": "INS-C:PRD-3120", "insurerCode": "INS-C" }
  ]
}
→
{
  "snapshotId": "GRD-20260923-000481",
  "gradingPolicyVersionId": "GRADING-2026-07",         // 5단계 임계치·모수·기간 정의 버전
  "rankingPolicyVersionId": "RANK-2026-07",            // 세트 내 순위·동점 규칙 버전
  "tieBreak": "SHARED_RANK",                          // rankingPolicy가 정한 동점 처리: SHARED_RANK(동순위 병기, 1-2-2-4) | STRICT(정책의 2차 기준으로 순위 분리, 1..m 유일)
  "basis": { "groupAvgSource": "ASSOC_DISCLOSURE|ENGINE_LEDGER", "period": "2026Q2", "groupPopulation": 27 },
  "results": [
    { "productKey": "INS-A:PRD-1001", "status": "OK", "ratioToAvg": "0.84", "grade": "LOW",       "gradeLabel": "낮음",     "gradeOrdinal": 2, "rankInSet": 1, "tie": false },
    { "productKey": "INS-C:PRD-3120", "status": "OK", "ratioToAvg": "1.02", "grade": "MID",       "gradeLabel": "보통",     "gradeOrdinal": 3, "rankInSet": 2, "tie": false },
    { "productKey": "INS-B:PRD-2044", "status": "OK", "ratioToAvg": "1.37", "grade": "VERY_HIGH", "gradeLabel": "매우높음", "gradeOrdinal": 5, "rankInSet": 3, "tie": false },
    { "productKey": "INS-D:TEMP-7",   "status": "UNAVAILABLE", "reason": "NO_RATE_DATA" }   // 등급·순위·비율 필드는 null이 아니라 **부재**
  ],
  "generatedAt": "2026-09-23T10:15:30+09:00"
}
```

**응답 계약 확정(Phase 0 심사, 2026-09-29)**
- `results[]`는 `status`로 분기하는 `oneOf`다. `OK`는 `ratioToAvg`·`grade`·`gradeLabel`·`gradeOrdinal`·`rankInSet`·`tie` 전부 필수, `UNAVAILABLE`은 `reason`만 필수이고 위 6개 필드를 **가질 수 없다**(`additionalProperties: false`). `reason` 값 목록은 엔진 데이터(예: `NO_RATE_DATA`, `NOT_IN_GROUP`, `TEMP_PRODUCT`)이며 워크플로는 문자열로 보관·표시만 한다.
- 순위는 `OK` 항목만으로 매긴다. `OK` 항목이 m개면 `STRICT`에서는 `rankInSet`이 1..m의 순열, `SHARED_RANK`에서는 `rankInSet`을 오름차순 정렬한 r₁..rₘ이 r₁=1, rₖ ∈ {rₖ₋₁, k}(경쟁 순위)를 만족하고 같은 값을 가진 항목은 전부 `tie=true`다. 워크플로는 `tieBreak` 값에 따라 둘 중 한 검사를 적용한다(§6.3 (ii)).
- **`ratioToAvg` 불변 약속**: 엔진은 `snapshotId`별 결과를 영속 저장하고, 같은 `snapshotId`를 다시 조회하면 `ratioToAvg`를 포함한 모든 문자열 필드를 **바이트 단위로 동일하게** 돌려준다. 정책 버전이 바뀌어도 기존 스냅샷의 문자열은 재포맷하지 않는다. 이것이 봉인 해시 재현의 전제이며 엔진 provider 계약 테스트로 고정한다(`GET /internal/v1/disclosure/commission-grades/{snapshotId}` 조회 API 포함).

- 등급은 **유사상품군 전체** 대비, 순위는 **요청한 세트 안**에서 매긴다(규정의 정의 그대로). 순위는 등급과 단조 관계여야 하며(같은 세트에서 낮은 등급이 더 나쁜 순위를 가질 수 없음) 워크플로가 이를 재검증한다(§6.3). 재검증에는 엔진이 정책 데이터에서 내려주는 `gradeOrdinal`(수수료가 낮을수록 작은 정수)만 쓴다 — 워크플로는 등급 코드의 의미·개수를 알지 못한다.
- `ratioToAvg`는 **표시·보관용 불투명 문자열**이다. 워크플로는 이를 숫자로 바꾸거나 비교하지 않는다(아키텍처 테스트로 금지).
- 수수료율 원 수치는 응답에 **없다**. 필요 시 엔진 `snapshotId`로 준법 권한자가 엔진에서 조회한다.
- `UNAVAILABLE`은 임시등록·미공시 상품 등 산출 불가를 뜻한다. 워크플로는 이를 "산출불가"로 표기하고 관리자 확인을 강제한다(§6.2 R-GRADE-UNAVAILABLE).
- 동점(`tie=true`) 처리 규칙은 `rankingPolicy` 데이터(예: 동순위 병기 / 보험료 낮은 순)이며 확인서에는 정책이 정한 표기로 인쇄된다.

**엔진 저장소 변경(별도 PR, Phase E3)**: ① `GradingPolicy`를 5단계 임계치(130/110/90/70%)·모수·기간이 **전부 데이터**인 버전 레코드로 재정의(Phase 15 리뷰 지적 반영, 3분위 고정 구현 제거) ② `RankingService`에 "세트 내 순위" 입력 추가 및 동점 정책(`tieBreak`) 데이터화 ③ 위 API 컨트롤러 + 스냅샷 영속 저장 + `snapshotId` 재조회 API + provider 계약 테스트(재조회 바이트 동일 포함) ④ 임계치 교체(예: 4단계로 변경) 시 코드 변경 0임을 증명하는 테스트.

### 4.3 협회 시스템 어댑터 (`IssuerPort`, ASSOC 모드)

### 4.4 청약 게이트 API (본 시스템 제공)

```
GET /internal/v1/disclosures/gate?customerRef=…&productKey=…&asOf=…
→ { "required": true, "status": "COMPLETED|PENDING|NONE", "pendingRoles": ["MANAGER"], "gateSatisfied": false,
    "disclosureNo": "T1-2026-000481", "completedAt": null, "gateMode": "BLOCK|WARN|OFF", "ruleVersionId": "DISC-2026-07" }
```

`required`는 대상 계약 판정 룰(§6.8)로 결정한다. `gateSatisfied`는 `gateRequiresManager=true`이면 COMPLETED일 때만, `false`이면 고객·설계사 서명이 끝난 시점부터 true가 된다(관리자 확인은 이후에도 반드시 완료돼야 하며 미완료 시 LATE 플래그). 청약 시스템(또는 3순위 CRM)은 `gateMode`에 따라 진행을 막거나 경고한다. 계약 체결 후 `POST /internal/v1/disclosures/{no}/policy-link { policyNo, contractDate }`로 연결하며 이 연결은 확인서 본문이 아니라 **메타데이터**이므로 봉인 불변성과 충돌하지 않는다.

### 4.5 아웃박스 이벤트 (본 시스템 발행)

`DisclosureCreated`, `DisclosureSealed`, `SignatureCaptured(role)`, `DisclosureCompleted`, `DisclosureVoided`, `DisclosureSuperseded`, `PolicyLinked`, `ComplianceFlagRaised(type)`. 포털은 이 중 `SignatureCaptured(CUSTOMER)`·`DisclosureCompleted`·`ComplianceFlagRaised`를 알림으로 파생하고, CRM(3순위)은 고객 타임라인에 붙인다. 발행 방식·피드 API·Envelope는 포털 설계서 §4.1과 동일 규약.

## 5. 데이터 모델 (PostgreSQL)

모든 테넌트 테이블은 `tenant_id`를 첫 컬럼으로 갖고 PK·인덱스에 포함한다. RLS·세션 바인딩은 포털과 동일. 본문 문서·PDF·서명 이미지는 오브젝트 스토리지에 두고 DB에는 키와 해시만 둔다.

```sql
-- 테넌트·신원 (포털과 같은 형태, 별도 DB에 독립 보유)
CREATE TABLE tenant (
  tenant_id        TEXT PRIMARY KEY,
  name             TEXT NOT NULL,
  engine_base_url  TEXT NOT NULL,                 -- 테넌트별 엔진 인스턴스
  status           TEXT NOT NULL,                 -- ACTIVE/PAUSED
  large_ga         BOOLEAN NOT NULL,              -- 설계사 500인 이상 여부(대상 판정 입력)
  issuer_mode      TEXT NOT NULL DEFAULT 'SELF',  -- SELF/ASSOC (D-2)
  gate_mode        TEXT NOT NULL DEFAULT 'WARN',  -- BLOCK/WARN/OFF (D-8)
  params           JSONB NOT NULL DEFAULT '{"gateRequiresManager": true}'  -- 사규 파라미터: gateRequiresManager(기본 true, D-9), managerScope, tsaProfile ...
);
CREATE TABLE identity_link (              -- IdP subject ↔ 설계사/관리자. agent_id는 여기서만 결정된다
  tenant_id TEXT, subject TEXT, agent_id TEXT NOT NULL, roles TEXT[] NOT NULL, org_path TEXT NOT NULL,
  PRIMARY KEY (tenant_id, subject)
);

-- 룰·서식 (룰 = 데이터)
CREATE TABLE rule_version (
  tenant_id TEXT, rule_version_id TEXT,            -- 예: DISC-2026-07
  scope TEXT NOT NULL,                              -- GLOBAL(규제) / TENANT(사규)
  apply_from DATE NOT NULL, apply_to DATE,
  status TEXT NOT NULL,                             -- DRAFT/APPROVED/ACTIVE/RETIRED
  approved_by TEXT, approved_at TIMESTAMPTZ,
  body JSONB NOT NULL,                              -- 부록 D 구조: minCompare, signerSet, reasonCodes, gradeRequired, subjectRule, retention...
  source_bundle_id TEXT, bundle_hash TEXT,          -- (V4) GLOBAL 복제본의 출처 번들과 body의 SHA-256(JCS). GLOBAL이면 NOT NULL(CHECK)
  PRIMARY KEY (tenant_id, rule_version_id)
);
-- GLOBAL 룰의 저장 방식(Phase 0 심사 확정): 규제 룰은 `contracts/rules/bundles/`의 번들 파일이 정본이고, 배포 명령이
-- 각 테넌트에 **같은 rule_version_id로 복제**한다. RLS를 예외 없이 유지하기 위해 시스템 테넌트·무테넌트 테이블을 두지 않는다.
-- 불변 규칙(트리거): body·apply_from·source_bundle_id·bundle_hash는 scope='TENANT'이고 status='DRAFT'일 때만 수정 가능(GLOBAL은 항상 불변).
-- apply_to는 NULL→값 한 번만 쓸 수 있다(후속 룰 배포가 선행 룰을 닫는 경로). status는 DRAFT→APPROVED→ACTIVE→RETIRED 순방향만.
-- 활성화는 일 배치(주입된 Clock): APPROVED이고 apply_from ≤ 오늘이면 ACTIVE, ACTIVE이고 apply_to ≤ 오늘이면 RETIRED. 배타 제약이 ACTIVE 겹침을 막으므로
-- 후속 번들은 `supersedes`로 선행 룰의 apply_to를 자기 apply_from으로 닫은 뒤 삽입된다(같은 트랜잭션).
-- 준법 배치가 매일 bundle_hash = SHA-256(JCS(body))를 재계산해 번들과 대조하고 불일치는 ComplianceFlag(RULE_DRIFT).
-- TENANT 룰은 GLOBAL 룰이 `tenantOverridable`로 열어 둔 키만 덮어쓸 수 있다(§6.2).
-- 해석 대상은 기준일에 "시행 중이었던" 룰이다: status ∈ {ACTIVE, RETIRED}이고 [apply_from, apply_to)가 기준일을 포함.
-- (RETIRED를 포함해야 경계일 이후에도 과거 상담일의 확인서를 같은 룰로 해석할 수 있다. APPROVED는 활성화 배치 전이므로 제외.)
-- 같은 scope·기준일에 2건이면 해석기는 Ambiguous로 실패한다(엔진과 동일 규약).
-- 추가로 DB가 겹침 자체를 막는다(btree_gist, V4에서 RETIRED까지 확장 — 과거 기준일의 해석이 사후에 바뀌지 않는다):
--   EXCLUDE USING gist (tenant_id WITH =, scope WITH =, daterange(apply_from, apply_to, '[)') WITH &&) WHERE (status IN ('ACTIVE','RETIRED'))
-- 엔진에서 "개시일이 다른 겹침이 유니크 인덱스를 통과한다"고 지적된 틈을 범위 배타 제약으로 닫는다.

CREATE TABLE form_template (
  tenant_id TEXT, template_id TEXT, template_type TEXT NOT NULL,   -- STANDARD / AUTO(예약)
  version INT NOT NULL, apply_from DATE NOT NULL, apply_to DATE,
  fields JSONB NOT NULL,        -- [{code, label, required, source(CATALOG|ENGINE|AGENT|SYSTEM), order, render}]
  layout JSONB NOT NULL,        -- 렌더러가 읽는 섹션·열 배치
  pending_confirmation JSONB NOT NULL DEFAULT '[]',   -- (V4) 정본 확인 전 자리표시 [{ref: TODO(confirm#N), note}]. 필드가 아니며 인쇄·필수 판정 대상이 아니다
  source_bundle_id TEXT, bundle_hash TEXT,            -- (V4) 번들 출처면 NOT NULL(둘 다), 테넌트 작성본이면 NULL
  PRIMARY KEY (tenant_id, template_id, version)
);
-- 번들 출처 템플릿은 불변(apply_to만 NULL→값 1회). 테넌트 작성본은 status가 없으므로 apply_from > 오늘(Asia/Seoul)인 동안만 수정 가능.
-- 같은 template_type의 적용 구간은 DB가 겹침을 막는다(EXCLUDE, V4). 번들 해시 = SHA-256(JCS({fields, layout, pendingConfirmation})).

-- 카탈로그(외부 정본의 캐시)
CREATE TABLE product_group (
  tenant_id TEXT, group_code TEXT, name TEXT NOT NULL, line TEXT NOT NULL,   -- LIFE/NONLIFE
  apply_from DATE NOT NULL, apply_to DATE, source TEXT NOT NULL,
  PRIMARY KEY (tenant_id, group_code)
);
CREATE TABLE product_catalog (
```

**불변식(테스트·DB 트리거로 상시 검증)**
- `status ∉ {DRAFT, COMPARED, GRADED, REASONED}`인 확인서의 `disclosure_item`·`recommendation`·헤더 본문 컬럼은 UPDATE 불가, 같은 부모에 `disclosure_item`·`recommendation` INSERT·DELETE 불가(트리거 + 애플리케이션 이중).
- 봉인 이후 상태(`SEALED`~`EXPIRED`)에서 가변 상태(`DRAFT`~`REASONED`)로의 `status` UPDATE는 거부한다. 막지 않으면 `status='DRAFT'`로 되돌린 뒤 본문을 고치는 우회가 생긴다. `superseded_by_id`는 NULL→값 한 번만 쓸 수 있다.
- `signature.signed_doc_hash = disclosure.canonical_hash`이고 부모 `status ∈ {SEALED, PARTIALLY_SIGNED}`일 때만 INSERT 허용. 불일치 해시, 봉인 전, `VOID`·`EXPIRED`·`SUPERSEDED`·`COMPLETED` 문서에 대한 서명은 거부.
- `audit_log.entry_hash`는 직전 `entry_hash`와 본문으로 재계산 시 일치. `verify` 명령이 전 구간 검사.
- 활성 `rule_version`은 scope·기준일당 정확히 1건(DB 배타 제약 + 해석기 fail-fast 이중).
- `disclosure_item`의 추천 상품 수 ≥ `rule.minCompare`이고 보험사 코드가 서로 다름 (봉인 시점 검증, 봉인 후 불변).

## 6. 핵심 로직

### 6.1 상태기계

```
DRAFT ─(항목 ≥ min, 검증 R-*)→ COMPARED ─(엔진 스냅샷)→ GRADED ─(추천사유)→ REASONED
   ─(검증 전건 통과 + 봉인)→ SEALED ─(서명 수집)→ PARTIALLY_SIGNED ─(서명자 집합 충족)→ COMPLETED
어느 단계든: → VOID (사유·승인)          SEALED 이후: → SUPERSEDED (새 버전 DRAFT 생성·복제)
SEALED/PARTIALLY_SIGNED에서 sign_deadline 경과: → EXPIRED (재발급만 가능)
```

| 전이 | 조건 | 부수 효과 |
|---|---|---|
| DRAFT→COMPARED | 항목 수·보험사 상이·상품군 일치·패널 포함 검증 | — |
| COMPARED→GRADED | 엔진 응답 수신, 순위-등급 단조성 검증, `UNAVAILABLE` 항목은 플래그 | `grade_snapshot_id` 저장, 항목에 등급·순위 복사 |
| GRADED→REASONED | 추천 항목마다 사유 코드 ≥ 1, OTHER면 텍스트 필수 | — |
| REASONED→SEALED | 전 검증 룰 통과(오버라이드는 관리자 승인 + 플래그) | 룰 버전 확정, 채번, JCS 해시, PDF/A 렌더, PDF 해시, 체인 연결, 스토리지 저장(Object Lock) |
| SEALED→PARTIALLY_SIGNED→COMPLETED | 서명자 집합(`rule.signerSet`, 관리자 필수 여부 파라미터)과 순서(`signOrder`) 충족 | SIGNED_PDF·EVIDENCE_ZIP 생성, `retention_until` 계산, 이벤트 발행 |
| 항목 변경 시도(GRADED 이후) | 항목이 바뀌면 스냅샷 무효 | 자동으로 COMPARED로 되돌리고 재산출 요구(등급이 상품과 어긋나는 상태를 만들지 않는다) |
| 스냅샷 노후 | `sealed_at − generatedAt > rule.snapshotMaxAgeDays` | 봉인 거부, 재산출 요구 |

### 6.2 검증 룰 (룰 = 데이터, `rule_version.body.validations`)

| ID | 내용 | 실패 시 |
|---|---|---|
| R-MIN-COMPARE | 추천 상품 수 ≥ `minCompare`(현행 3) | 봉인 불가 |
| R-DISTINCT-INSURER | 추천 상품의 보험사가 서로 다름 | 봉인 불가 |
| R-SAME-GROUP | 모든 항목이 헤더의 유사상품군에 속함 | 봉인 불가 |
| R-PANEL | 보험사가 `insurer_panel`(기준일 유효)에 존재 | 봉인 불가 |
| R-GRADE-REQUIRED | `tenant.largeGa=true`이면 추천 항목 전부 등급·순위 존재 | 봉인 불가(UNAVAILABLE은 아래) |
| R-GRADE-UNAVAILABLE | `UNAVAILABLE` 항목은 "산출불가·사유" 표기 + 관리자 확인 필수 + 플래그 | 오버라이드 경로만 |
| R-RANK-MONOTONIC | 세트 내 순위가 등급 순서와 단조 | 스냅샷 거부, 엔진 이상 신호 |
| R-REASON | 추천 항목마다 사유 코드 ≥ 1, OTHER는 텍스트 필수, 텍스트 길이 상한 | 봉인 불가 |
| R-TEMP-PRODUCT | `temp_product`는 `quote_doc_no` 필수 + 관리자 확인 + 플래그 | 오버라이드 경로만 |
| R-REQUESTED | `requested_by_customer` 항목은 최소 비교 개수에 산입 가능하되 사유 코드에 `CUSTOMER_REQUEST` 자동 부가 | — |
| R-SIGNER-SET | 서명자 집합·순서·기한 | 완료 불가 |
| R-FIELD-REQUIRED | 템플릿 `required=true` 항목값 존재 | 봉인 불가 |

룰 본문(부록 D)은 JSON이며 실행기는 `ruleId → 평가 함수` 레지스트리다. **새 룰은 레지스트리에 평가 함수를 추가하고 데이터로 활성화**하며, 기존 룰의 파라미터 변경(3→4개 등)은 데이터만 바꾼다.

**룰 해석(Phase 0 심사 확정).** 기준일(상담일)로 `scope=GLOBAL`과 `scope=TENANT`를 **각각** 단건 해석한다(각 scope에서 2건이면 Ambiguous 실패, GLOBAL 0건이면 실패, TENANT 0건은 정상). 유효 룰 = GLOBAL body 위에 TENANT body를 덮되, **GLOBAL body의 `tenantOverridable` 목록에 있는 키만** 덮어쓸 수 있다. 목록에 없는 키를 TENANT 룰이 가지면 해석은 실패한다(조용히 무시하지 않는다). 덮어쓰기는 최상위 키 단위이며 깊은 병합은 하지 않는다. 결과에는 두 버전 ID가 함께 박제된다(`disclosure.rule_version_id`, `tenant_rule_version_id`). 어떤 키를 테넌트에 열어 줄지는 규제 룰(번들) 데이터가 정하므로, "사규가 규제를 완화할 수 없다"는 원칙도 코드가 아니라 데이터로 표현된다(예: `minCompare`는 목록에 없고 `signDeadlineDays`·`remoteLinkTtlHours`·`channels`는 있음). 서식 항목 12개의 구체 목록은 협회 표준서식이 정본이므로 `form_template.fields`로 관리하고 코드에 항목명을 두지 않는다(하드코딩 금지, 엔진 공시 서식 원칙과 동일).

### 6.3 등급·순위 표기 규칙

- 기준일 = 상담일(`consult_date`). 엔진 요청에 기준일과 상품군을 넘기고, 응답의 정책 버전 2종·`snapshotId`·`basis`를 헤더에 저장, 항목에는 등급·라벨·순위·비율만 복사한다.
- 확인서에는 **등급 라벨과 순위만** 인쇄. 비율·수치·정책 버전은 준법 화면과 증거 패키지에만 포함.
- 정합성 검증: (i) 응답 상품 집합 = 요청 집합 (ii) `OK` 항목 m개에 대해 `tieBreak=STRICT`면 `rankInSet`이 1..m 순열, `SHARED_RANK`면 경쟁 순위 조건(§4.1)과 동일 순위 항목의 `tie=true` (iii) 순위-등급 단조(`rankInSet` 오름차순일 때 `gradeOrdinal`이 감소하지 않음; 동순위끼리는 `gradeOrdinal`이 같아야 함) (iv) 정책 버전·`tieBreak`가 워크플로 룰 버전이 허용하는 목록에 포함 (v) `UNAVAILABLE` 항목에 등급·순위 필드가 없음. 하나라도 실패하면 스냅샷을 버리고 `ComplianceFlag(GRADE_INCONSISTENT)`.
- 항목이 추가·삭제되면 세트가 바뀌므로 순위가 달라진다 → 자동 재산출(§6.1). 4번째 이상 항목(고객 요청 등)도 세트에 포함해 순위를 다시 받는다.
- 산출불가 항목의 인쇄 문구는 템플릿 데이터(`render.unavailableText`).

### 6.4 봉인(Seal)

1. 룰 버전·템플릿 버전 확정(기준일 해석, Ambiguous면 실패).
2. 본문을 **정규화 JSON(RFC 8785 JCS)** 으로 직렬화 → `canonical_hash = SHA-256`.
3. 확인서 번호 채번(테넌트별 연도 시퀀스, 예: `T1-2026-000481`).
4. 템플릿 `layout`으로 HTML 렌더 → **PDF/A** 변환 → `pdf_hash`. PDF에는 확인서 번호·룰 버전·`canonical_hash` 일부(QR)를 인쇄해 종이와 원본을 잇는다.
5. `chain_hash = H(prev_chain_hash || canonical_hash || pdf_hash)`, `chain_seq` = 테넌트 봉인 시퀀스.
6. CANONICAL_JSON·PDF를 스토리지에 저장(Object Lock, 보존기간 = `retention_until`), DB 커밋, 감사 로그 SEAL.
7. 렌더는 **결정론적**이어야 한다: 같은 canonical JSON + 같은 템플릿 버전 → 같은 PDF 바이트(폰트 임베드·타임스탬프 고정). 이것이 "재렌더로 원본 검증" 테스트의 전제다.

### 6.5 서명

- 세션 생성 시 `signed_doc_hash`가 고정된다. 서명은 그 해시에 대해서만 유효하며 다른 버전에는 붙지 않는다.
- **효력의 원천은 인증수단이 아니라 증거다(D-10).** 서명 1건의 증거 = 서명 대상 해시 + 서명 행위 데이터(터치 스트로크 또는 스캔 이미지) + 본인확인 결과 + 열람 완료 사실 + 시각·기기·IP + 세션 발급·소비 이력. 전부 `signature`·`audit_log`에 남고 EVIDENCE_ZIP에 묶인다.
- **TOUCH_PAD**(현장 대면): 설계사 기기에서 고객이 봉인 PDF를 끝까지 열람한 뒤 서명. 본인확인 = 설계사의 대면 확인 체크(설계사 계정에 귀속) + 열람 스크롤 완료. 서명 스트로크(좌표·시각 시퀀스)를 이미지와 함께 저장한다(붙여넣기 이미지와 구분).
- **REMOTE_LINK**(비대면): 고객 연락처로 1회용 링크(`token_hash`만 저장, 만료 `rule.remoteLinkTtlHours`). 기본 본인확인 = **링크 소유(발송 번호 기록) + 생년월일 전체 입력**. 실패 N회 시 세션 폐기. 발송 번호는 `customer_ref.phone_enc`에서만 가져오고 설계사가 임의 번호로 발송할 수 없다.
- **대리 서명 탐지**: 같은 기기 지문·IP에서 서로 다른 고객의 REMOTE_LINK 서명이 반복되거나, 링크 발송 후 비정상적으로 짧은 시간에 서명이 완료되면 `ComplianceFlag(SIGNATURE_DEVICE_REUSE)`를 올린다. 임계치는 룰 데이터.
- **PAPER_SCAN**: 인쇄본 서명 후 설계사가 스캔 업로드. QR로 원본 매칭(해시 접두 검사) 후 서명 레코드 생성, 관리자 확인 강제(이행기 채널, 테넌트가 비활성 가능).
- **CERTIFIED_ESIGN**(v2, 테넌트 선택): 인정 전자서명인증사업자 어댑터. 인증서·영수증을 증거에 추가. 법정 요건이 아니라 신원 귀속 강화 옵션이다.
- **AGENT 서명**: 설계사 본인 OIDC 세션에서 확인·서명(터치 서명 또는 승인 클릭, 테넌트 파라미터). 신원 귀속은 SSO에 있다.
- **MANAGER 확인(D-9)**: 관리자 OIDC 세션에서 확인서 상세를 열람한 뒤 승인. 이 승인 행위를 관리자 서명으로 기록하며(`method=SSO_APPROVAL`), 예외 플래그(산출불가·임시등록·오버라이드·종이 스캔)가 있는 건은 사유 확인 체크가 추가로 필요하다. 관리자 부재 시 사후 확인을 허용하되 `signDeadlineDays` 안에 끝나지 않으면 EXPIRED, 청약 진행 허용 시점은 `gateRequiresManager`(§4.4).
- 순서·집합은 데이터: 기본 `CUSTOMER → AGENT → MANAGER`, `managerConfirmMode = REQUIRED`(기본)`|OPTIONAL|OFF`. 협회 면제 건의가 수용되면 데이터 변경만으로 대응한다.
- 완료 시 서명 이미지·증거를 합성한 SIGNED_PDF와 증거 패키지(EVIDENCE_ZIP: canonical JSON, PDF, 서명 레코드·스트로크, 본인확인 결과, 스냅샷, 룰 버전, 감사 로그 발췌, 앵커 참조, 해시 목록)를 생성·보관한다.

### 6.6 정정과 무효

- **SUPERSEDE**: 봉인 후 오류 발견 시 새 버전 DRAFT를 복제 생성(`supersedes_id`), 이전 버전은 `SUPERSEDED`로 표시되고 그대로 보관된다. 서명은 이전 버전에 남고 새 버전은 다시 받는다. 사유 필수, 감사 기록.
- **VOID**: 상담 취소 등. 사유 필수, `SEALED` 이후 무효는 관리자 승인. 무효 문서도 삭제하지 않는다(보존기간까지).
- 어떤 경로로도 봉인된 본문은 바뀌지 않는다(§5 불변식). "삭제"라는 동작은 시스템에 존재하지 않고, 보존기간 도래 후 파기 배치만 있다(§9).

### 6.7 감사 로그와 체인

- 모든 상태 전이, 항목 편집, 엔진 호출, 검증 결과(실패 포함), 열람·인쇄·다운로드·내보내기, 서명, 관리·준법 행위, 룰 승인이 `audit_log`에 기록된다. 업무 트랜잭션과 **같은 트랜잭션**.
- 테넌트별 단일 시퀀스 + 해시체인. 일 1회 `audit_anchor`에 헤드 해시를 고정하고, **외부 타임스탬프(RFC 3161 TSA) 어댑터를 v1에 포함해 기본 활성**으로 둔다(어떤 전자서명도 법정 추정력이 없으므로 "그 시점에 그 문서가 존재했다"는 제3자 증거가 서명 효력을 떠받친다, §1.5). TSA 사업자 선택·비용은 테넌트 몫이며 미설정 시 내부 앵커만 남긴다.
- `verify --tenant X [--from-seq]`: 체인 전 구간 재계산, `document_artifact` 해시와 스토리지 실물 대조, 확인서 `chain_hash` 연속성 검사. 불일치 → `ComplianceFlag(CHAIN_BROKEN)` + 운영 알림.

### 6.8 준법 점검

- **대상 계약 판정** `subjectRule`(데이터): 테넌트 `largeGa`, 상품군 대상 여부(자동차 등 제외), 체결일 ≥ 룰 시행일, 채널 조건. `subject_policy`는 엔진 `PolicyEventObserved`/청약 링크/CRM에서 채운다.
- **징구율** = 완료 확인서가 연결된 대상 계약 / 대상 계약 (기간·조직·설계사·상품군 축). 정의는 룰 데이터(`kpi.collectionRate`)이며 화면에 정의 버전을 표기한다.
- **큐**: MISSING(대상인데 확인서 없음), LATE(체결일 이후 완료), GRADE_UNAVAILABLE, TEMP_PRODUCT, VALIDATION_OVERRIDE, EXPIRED, CHAIN_BROKEN. 각 플래그는 담당·기한·해소 기록.
- **리포트**: 협회·당국 점검 대응용 내보내기(기간·조직별 징구율, 예외 목록, 표본 확인서 증거 패키지). 내보내기는 감사 기록 + 워터마크.
- **룰 승인 흐름**: DRAFT → 준법 승인(APPROVED) → 시행일 도래 시 ACTIVE. 시행일 전 미승인 룰이 있으면 운영 경보. 규제(GLOBAL) 룰은 번들 배포 시 APPROVED로 복제된다. 배포·승인·활성화 배치·번들 대사는 `disclosure-compliance`의 서비스이며 전부 `audit_log`에 같은 트랜잭션으로 남는다(Phase 1은 운영자 CLI, 인가·스케줄은 Phase 6).

### 6.9 청약 게이트

`gateMode`(BLOCK/WARN/OFF)는 테넌트 파라미터. 본 시스템은 답만 하고 막는 것은 호출자다(D-8). 응답에는 룰 버전을 포함해 "왜 필요/불필요로 판정됐는지"가 남는다.

## 8. 화면 설계 (모바일 우선, 텍스트 와이어)

**설계사 흐름 (5단계, 상단 스텝 표시)**

1. **고객·상품군**: 고객 선택/신규(이름·연락처 최소) · 상담일 · 유사상품군(생/손보 탭) · 정본 모드 배지(SELF/ASSOC)
2. **비교표 구성**: 보험사 패널 칩 → 상품 검색·선택(≥3, 서로 다른 보험사 카운터) · 임시등록 추가(※, 발행번호 필수) · "고객이 요청한 보험사" 토글 · 항목 표(템플릿 항목, 카탈로그 기본값 자동 채움·수정 가능·수정 시 출처 배지 AGENT)
3. **등급·순위**: [산출] → 각 열에 등급 라벨·순위 표시(읽기 전용) · 산출불가는 사유 배지 + "관리자 확인 필요" · 스냅샷 시각·유효기한 · 항목이 바뀌면 자동 회색화·재산출 버튼
4. **추천사유**: 추천 상품별 체크(보장수준/보험료/가입목적/기타) · 기타 텍스트 · 검증 결과 패널(통과/실패/오버라이드 요청)
5. **봉인·서명**: 미리보기(PDF) → [발급] → 확인서 번호 · 서명 카드 3장(고객/설계사/관리자) · 채널 선택(현장 서명/링크 발송/종이 스캔) · 진행 상태 · 완료 시 증거 패키지 다운로드

**고객 서명 페이지**: 확인서 번호·발급 GA·설계사명 · PDF 전체 열람(끝까지 스크롤해야 서명 활성) · 본인확인 입력 · 서명 패드 · 완료 화면(사본 다운로드 링크, 유효기간) · 고정 문구는 템플릿 데이터.

**관리자**: 확인 대기 목록(예외 사유 배지) · 상세(비교표·등급·추천사유·검증 로그) · 확인 서명/반려(사유).

**준법 콘솔(데스크톱)**: 징구율 카드(기간·조직 필터, 정의 버전) · 큐 탭(MISSING/LATE/…) · 확인서 검색·열람(전 건 감사) · 리포트 내보내기 · 룰 버전 목록·시행 예정·승인 · 체인 검증 결과.

접근성·현장성: 터치 44px, 표는 가로 스크롤 컨테이너, 저사양 기기 번들 상한, 고객 서명 페이지는 JS 최소·폰트 임베드(외부 요청 없음).

## 9. 보안·개인정보·멀티테넌시

- **인증·인가**: 포털과 동일 OIDC. 고객은 1회용 토큰(서명 세션)만. 설계사 self 조회는 `agent_id` 소유 확인서만, 관리자는 `org_path` 접두, 준법은 테넌트 전체(전 건 `VIEW` 감사).
- **테넌트 격리 3중**: 컨텍스트·아키텍처 테스트·RLS. 오브젝트 스토리지 키도 `tenant_id/` 접두 + 버킷 정책.
- **개인정보 최소화**: 고객 이름·연락처는 컬럼 암호화(KMS 키, 테넌트별 키 권장), 확인서 PDF 안의 고객명은 서식 요구 범위. 주민번호·주소·계좌는 수신하지 않는다. 화면·로그는 마스킹. 서명 이미지는 개인정보로 취급(암호화 저장, 열람 감사).
- **보존·파기**: `retention_until` = 완료일(또는 계약일) + `rule.retentionYears`(법정 보존기간은 §14 #3 확인 후 데이터로 설정, 예시값 5년). 도래 시 파기 배치 → 스토리지 삭제 + DB 본문 삭제 + **파기 기록은 감사 로그에 남김**(해시만 잔존). 미체결 상담 확인서의 보존은 §14 #3.
- **불변 저장**: Object Lock(Compliance 모드) 기간 = 보존기간. 운영자도 기간 내 삭제 불가.
- **서비스 간**: 엔진 호출 서비스 토큰(운영 mTLS), 청약 게이트·이벤트 피드는 내부망 한정.
- **DB 롤**: `disclosure_migrator`(스키마 소유, Flyway 전용), `disclosure_app`(DML만, RLS 적용), `disclosure_operator`(V4, 운영자 CLI의 `--tenants all` 전용 — `tenant.tenant_id` 컬럼 SELECT와 이 롤 전용 `tenant_directory` 정책만 가진다. 테넌트 데이터 작업은 테넌트마다 `disclosure_app`으로 바인딩해 수행한다). 세 롤 모두 NOBYPASSRLS.
- **레이트 리밋**: 서명 링크 발송 설계사당 시간당 N회, 본인확인 실패 N회 폐기, 엔진 산출 요청 확인서당 분당 N회.

## 12. 구현 로드맵 (Claude Code 작업 순서)

각 Phase는 독립 머지 가능, 완료 기준은 테스트로 증명. `E-`는 엔진 저장소 작업.

- **Phase 0 — 골격·플랫폼 공유**: 저장소, Gradle 모듈, `platform-core`·`platform-spring` 확보(포털 Phase 0 산출물이 있으면 이식, 없으면 같은 규격으로 신규 작성 후 `com.ga.platform`으로 발행 — 포털 소비는 후속 PR), Flyway(스키마·RLS·불변 트리거·배타 제약), Testcontainers, ArchUnit(테넌트 조건·수수료율 연산·double 금지), `contracts/` 초기. *완료 기준: tenant 조건 없는 저장소 메서드 실패, RLS 미설정 세션 0행, 봉인 상태 본문 UPDATE가 DB에서 거부, 서명 해시 불일치 INSERT 거부, 겹치는 ACTIVE 룰 INSERT 거부, 수수료율 비교 코드 삽입 시 아키텍처 테스트 실패.* 상세는 `docs/phase-00-지시문.md`.
- **Phase 1 — 룰·서식 데이터**: V4(`rule_version` 번들 컬럼·GLOBAL 불변 트리거, `disclosure.tenant_rule_version_id`), 룰 번들·배포 명령, 기준일 해석기(scope별 단건·Ambiguous fail-fast·`tenantOverridable` 병합), 검증 룰 실행기·레지스트리, `form_template` 저장소·해석, 부록 D 시드. *완료 기준: 최소 개수·서명자 집합·항목 목록을 데이터만 바꿔 동작 변경(코드 diff 0) 테스트, 겹치는 ACTIVE 룰 삽입 시 해석 실패, 허용되지 않은 키를 덮어쓰는 TENANT 룰 해석 실패, GLOBAL 복제본 body UPDATE 거부, 번들 해시 불일치 검출.* 상세는 `docs/phase-01-지시문.md`.
- **Phase 2 — 카탈로그·패널·고객 참조**: `ProductCatalogPort` 파일 어댑터, 유사상품군, 보험사 패널, 임시등록, `customer_ref` 암호화. *완료 기준: 기준일별 패널·상품 유효기간 테스트, 암호화 컬럼 평문 노출 0(로그 스캔).*
- **Phase E3 — 엔진 등급·순위 API**: §4.1 변경 4건. *완료 기준: 5단계 임계치 데이터 교체 테스트, 세트 내 순위·동점 정책 테스트, provider 계약 테스트, 응답에 수수료율 원 수치 부재 검증.*
- **Phase 3 — 워크플로 코어·봉인**: 상태기계, 항목 구성, 스냅샷·정합성 검증, 추천사유, 봉인(JCS·채번·PDF/A·체인·Object Lock). 선행 소과제: PDF 변환기 후보 비교(결정론·PDF/A·한글 폰트). *완료 기준: 상태기계 속성 테스트(불법 전이 0), 봉인 후 UPDATE 트리거 거부, 동일 입력 재렌더 바이트 동일, 항목 변경 시 자동 COMPARED 회귀.*

- **Phase 8 — 데모·통합 실행**: 부록 B 시드, 엔진 스텁, docker compose, README, DB 헬스 지표 복원(`DatabaseHealthIndicator`: 테이블에 닿지 않는 `SELECT 1`을 전용 커넥션으로 실행하는 **유일한 허용 예외**, 아키텍처 규칙 허용 목록에 FQN으로 등재). *완료 기준: `docker compose up` 후 데모 설계사로 확인서 1건을 끝까지 완료하고 준법 콘솔에 징구율 반영, `/actuator/health`가 DB 단절을 DOWN으로 보고.*
- **Phase 9(후속)** — ASSOC 어댑터 실연동, 전자서명 사업자, 자동차보험 템플릿, CRM 연계, 오프라인 초안.

| 6 | 봉인 | SEALED | 번호 T1-2026-000481, canonical/pdf/chain 해시, Object Lock |
| 7 | 고객 현장 서명 → 설계사 서명 → 관리자 확인 | PARTIALLY_SIGNED → COMPLETED | 서명 3건 모두 signed_doc_hash 일치, SIGNED_PDF·EVIDENCE_ZIP |
| 8 | 청약 시스템 게이트 조회 | — | COMPLETED·번호 응답 |
| 9 | 계약 체결 → policy-link | — | subject_policy MATCHED, 징구율 반영 |

**A-2. 임시등록 상품** — 2단계에서 B사 상품이 카탈로그에 없음 → 임시등록(※, 발행번호 입력) → 등급 UNAVAILABLE → R-GRADE-UNAVAILABLE로 관리자 확인 필수 + 플래그 TEMP_PRODUCT/GRADE_UNAVAILABLE → 봉인은 오버라이드 승인 후.

**A-3. 봉인 후 오류** — 보험료 오기 발견 → SUPERSEDE → v2 DRAFT 복제(스냅샷은 재산출) → 재봉인·재서명. v1은 SUPERSEDED로 보관, v2 헤더에 `supersedes_id`.

**A-4. 규정 변경** — 2027-01-01부터 최소 비교 개수 4, 관리자 확인 OFF인 룰 DISC-2027-01 승인 → 2026-12-31 상담 확인서는 3개·관리자 필수, 2027-01-01 상담은 4개·관리자 생략. 코드 변경 없음.

**A-5. 변조 시도** — 운영자가 DB에서 `disclosure_item.field_values` 직접 UPDATE → 트리거 거부. 트리거 우회 가정 시 `verify`가 canonical_hash 불일치를 해당 확인서에서 검출, CHAIN_BROKEN 플래그.

## 부록 C. 포트폴리오 관점 메모

README에서 강조할 것: ① 규제 문서를 **불변 문서 + 룰 버전 박제 + 해시체인**으로 만든 이유와 그 효과(사후 점검·민원 재현) ② 등급·순위를 "다시 계산하지 않고 스냅샷으로 받는" 경계와 정합성 검증(엔진과 같은 원칙의 재사용) ③ 임계치·항목·서명자 같은 규정 세부를 데이터로 두고 "코드 diff 0" 테스트로 증명한 것 ④ 서명이 사람이 아니라 문서 해시에 귀속된다는 규약 ⑤ 정본 발급처 모드(SELF/ASSOC)로 협회 시스템과 공존하는 설계. 엔진·포털과 동일하게 AI 협업 방법론(설계서 → Phase 지시 → 증거 기반 수용)을 한 섹션으로 기록한다.
