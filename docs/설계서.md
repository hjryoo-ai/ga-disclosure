## 0. 설계의 대전제

1. **확인서는 계약 체결 전에 완성되는 불변 문서다.** 봉인(seal) 이후 어떤 필드도 바뀌지 않는다. 정정은 **새 버전 발급(supersede) + 이전 버전 링크**로만 한다. 이것은 엔진의 "취소분개 + 재계산" 원칙을 문서에 옮긴 것이다.
2. **룰은 코드가 아니라 데이터다.** 서식 항목과 필수 여부, 최소 비교 개수(현행 3), 등급 임계치(현행 5단계), 순위·동점 규칙, 추천사유 코드, 필수 서명자 집합, 대상 계약 판정, 보존기간 — 전부 유효기간(effective date)을 가진 버전 데이터다. 확인서에는 **발급 시점에 적용된 룰 버전 ID가 박제**되고, 룰 해석은 엔진과 같은 규약(기준일 필수·단건 해석·Ambiguous fail-fast)을 따른다.
3. **돈에 관한 산출은 엔진이 한다.** 판매수수료 등급·순위는 엔진 API가 산출한 결과를 **스냅샷**으로 받아 표기한다. 워크플로 코드 어디에도 수수료율을 비교·정렬·분류하는 로직을 두지 않는다(아키텍처 테스트로 금지). 워크플로가 하는 것은 엔진 결과의 **정합성 검증과 표시**뿐이다.
4. **증거는 재현 가능해야 한다.** 확인서 = 정규화 JSON + 렌더된 PDF + 각각의 SHA-256 + 룰 버전 + 산출 스냅샷 ID. 서명은 사람이 아니라 **문서 해시에 귀속**된다. 감사 로그는 append-only 해시체인이며, 변조는 검증 명령 한 번으로 드러난다.
5. **테넌트 격리는 구조로 강제한다.** 포털과 동일한 3중 격리(컨텍스트·아키텍처 테스트·PostgreSQL RLS).
6. **고객 정보는 확인서 기재와 서명 전달에 필요한 최소만 다룬다.** 본 시스템은 CRM이 아니다(3순위 범위). 고객 식별은 `customer_ref`로 하고, 연락처는 원격 서명 링크 발송에만 쓰며 암호화 저장한다.
7. **시스템은 추천사유를 대신 쓰지 않는다.** 등급·순위·상품 정보는 자동으로 채우되, "왜 이 상품을 추천했는가"는 설계사가 직접 선택·기재한다. 자동 채움 문구는 불완전판매 시비의 씨앗이다.

### 1.4 정본 발급처 문제

협회 시스템으로 생성한 확인서는 법령 요건 충족이 "인정"되는 반면 자체 시스템은 GA가 스스로 적정성을 입증해야 한다. 어느 쪽이든 **워크플로·보관·감사·준법 점검**은 GA 몫이다. 따라서 본 시스템은 두 모드를 지원한다(D-2): 정본을 직접 발급하는 **SELF 모드**, 협회 시스템이 발급한 확인서를 수입해 보관·추적하는 **ASSOC 모드**. v1은 SELF 모드를 완전히 구현하고 ASSOC는 어댑터 인터페이스만 정의한다.

## 2. 범위

### 2.1 v1 포함

- 워크플로 전 단계(§6.1): 작성 → 비교표 구성 → 등급·순위 산출 → 추천사유 → 봉인·발급 → 서명(고객·설계사·관리자) → 완료·보관
- 상품 카탈로그·유사상품군·추천가능 보험사 패널(§5), 임시등록 상품 경로
- 엔진 등급·순위 API 연동과 스냅샷(§4.1), 정합성 검증(§6.3)
- 검증 룰 엔진(§6.2, 룰=데이터) + 서식 템플릿(항목·필수·표시 순서 = 데이터)

### 2.3 컴플라이언스 경계 (설계 제약)

- 시스템은 의무 이행을 **돕고 기록**한다. 이행 여부의 최종 판단과 협회·당국 대응은 GA 준법감시 조직의 책임이며, 화면 어디에도 "법령 요건 충족"을 시스템이 단언하는 문구를 두지 않는다.
- 등급·순위의 산정 기준(임계치·모수·기간)과 서식 항목의 정본은 외부에 있다. 시스템은 "어떤 기준이 와도 데이터 교체만으로 대응"하는 구조를 증명하는 것으로 완료 기준을 삼는다.
- 확인서에는 등급·순위만 인쇄된다. **수수료율 수치·GA 내부 지급률은 확인서에도 화면에도 나오지 않는다.** 스냅샷은 평균 대비 비율과 등급·순위만 저장하고 원 수치는 엔진 `snapshotId`로만 역추적한다.
- 시뮬레이션·비교표는 **고객 설명용**이지만, 고객 화면(서명 페이지)은 봉인된 문서만 보여준다. 작성 중인 초안은 고객에게 노출되지 않는다.

```
├── disclosure-sign            # 세션·채널·증거 수집: 서명 세션·토큰, 본인확인 정책, 채널 어댑터, 대리 서명 탐지(v1.9)
```

의존 방향: `app → api → workflow/compliance → rules/seal/sign/audit → domain → platform-core`(v1.8: `seal`은 서식 결속을 렌더러와 R-FIELD-REQUIRED가 함께 쓰므로 `rules`를 참조한다 — 둘 다 Spring 무의존, 역방향 없음). `rules`·`seal`·`audit`·`compliance`는 `platform-canonical`도 의존한다(Phase 1 신설). (v1.9, 4 계획 승인 Q6) **seal = 문서 산출물(canonical·PDF·서명본·증거 패키지) 생성, sign = 세션·채널·증거 수집** — 증거 패키지 빌더가 seal에 있으므로 레이어 규칙을 넓히지 않는다. `platform-spring`은 `infra`·`api`·`app`만 의존한다. **`infra`는 포트-어댑터 방향으로 `workflow`·`rules`·`sign`·`audit`·`compliance`가 선언한 포트 인터페이스를 구현하므로 그 모듈들을 참조할 수 있고, 반대로 그 모듈들은 `infra`를 알지 못한다.** `infra`를 참조할 수 있는 모듈은 `app`뿐이다(Phase 0 확정). DB 접근은 `TenantScopedRepository`를 통하며, **직접 접근 허용 목록은 닫힌 FQN 열거이고, 각 항목은 테넌트 데이터를 읽지 않으며 전용 롤을 쓴다**(현재 목록은 §9). `rules`·`domain`·`seal`(렌더러 제외)·`platform-core`는 Spring·DB 무의존. (v1.9) `sign`도 Spring·DB·환경 무의존이다(난수는 포트, 시각은 인자 — 빌드 `verifySpringFree` 대상). 두 플랫폼 모듈은 `com.ga.platform` 그룹으로 발행하며, **본 저장소의 구현이 기준 구현(reference)이다** — 포털은 자체 작성하지 않고 이 아티팩트를 소비한다(포털 Phase 0 지시문 개정 필요).

(v1.11, 5 계획 승인 Q1) Phase 5의 배치는 레이어 규칙을 넓히지 않는다. 조정(트랜잭션·포트 호출)만 `workflow`에 둔다: `anchor.AnchorJob`, `retention.{DestructionJob, LegalHoldService}`, `verify.{TenantVerifier, ReceiptExporter}`. 순수 계산은 `audit`에 둔다: 머클 트리·잎 규격, 체인 걷기, TSA 포트·수락·검증·스텁, 보고서 모델, `verify package`. `verify` 패키지는 생산자(`seal`·`workflow`)·DB·Spring·네트워크 의존이 0이다(ArchUnit `verifyPackageIsIndependentOfTheProducerAndOfEveryEnvironment`). 파기 판정 `RetentionDecision`은 `sign.retention`(순수)에 기존 `RetentionAnchors`와 함께 있다. DB 함수 호출기 `infra.retention.DestroyerGateway`는 직접 DB 접근 허용 목록의 현재 항목이다(§9).

### 3.4 데이터 흐름 4종

1. **작성 경로(동기, 설계사)**: 초안 생성 → 유사상품군 선택 → 카탈로그에서 상품 3개 이상 선택(임시등록 포함) → 엔진 등급·순위 산출(스냅샷) → 추천사유 입력 → 검증 룰 실행 → 봉인(번호·해시·PDF) → 서명 수집 → 완료. 모든 전이는 감사 로그 + 같은 트랜잭션.
2. **서명 경로(고객, 비로그인)**: 원격 링크 발송 → 1회용 토큰으로 서명 페이지 → 봉인 PDF 열람 → 본인확인(파라미터) → 서명 → 증거 저장 → 설계사에 알림.
3. **연동 경로**: 청약 시스템이 게이트 조회 → `COMPLETED` 확인서 존재 여부와 번호 응답. 계약 체결 후 `PolicyLinked`로 증권번호 연결. 아웃박스 이벤트를 포털(알림)·CRM(3순위)이 pull.
4. **점검 경로(배치)**: 매일 대상 계약(엔진/CRM에서 수신) 대비 완료 확인서를 대사 → 징구율·미징구 큐 갱신 → 체인 무결성 검증 → 앵커 저장 → 운영 알림.

## 4. 통합 계약 (Integration Contract v1)

`contracts/`에 OpenAPI·JSON Schema로 두고 양쪽 CI에서 검증한다. 버전·호환성 규칙은 포털 설계서 §4.5와 동일(필드 추가 호환, 삭제·의미 변경은 version 증가, 상위 버전 수신 시 정지).

**계약 변경 순서(Phase 2 심사 §3-2, v1.7).** 이 저장소의 `contracts/`가 정본이다. (ⅰ) 이 저장소에서 계약만 담은 작은 PR을 merge commit으로 병합 → (ⅱ) 엔진이 `contracts/UPSTREAM`을 **그 병합 커밋**으로 갱신하고 복사본·`CHECKSUMS`를 재검사한다. UPSTREAM은 항상 이 저장소 `main`에서 도달 가능한 커밋을 가리킨다(브랜치 커밋 금지 — squash·재작성으로 사라질 수 있다). "UPSTREAM이 main의 조상인가" 검사를 엔진 CI에 두는 것은 선택이다(원격 조회 필요). 추가형 변경(새 오류 코드·선택 필드)은 심사 없이 계약 PR에 넣을 수 있고, `OK`/`UNAVAILABLE`의 형태나 `ratioToAvg`·`tieBreak`·`rankInSet` 의미에 닿는 변경은 심사 뒤에 한다.

**응답 계약 확정(Phase 0 심사, 2026-09-29)**
- `results[]`는 `status`로 분기하는 `oneOf`다. `OK`는 `ratioToAvg`·`grade`·`gradeLabel`·`gradeOrdinal`·`rankInSet`·`tie` 전부 필수, `UNAVAILABLE`은 `reason`만 필수이고 위 6개 필드를 **가질 수 없다**(`additionalProperties: false`). `reason` 값 목록은 엔진 데이터(예: `NO_RATE_DATA`, `NOT_IN_GROUP`)이며 워크플로는 문자열로 보관·표시만 한다.
- 순위는 `OK` 항목만으로 매긴다. `OK` 항목이 m개면 `STRICT`에서는 `rankInSet`이 1..m의 순열, `SHARED_RANK`에서는 `rankInSet`을 오름차순 정렬한 r₁..rₘ이 r₁=1, rₖ ∈ {rₖ₋₁, k}(경쟁 순위)를 만족하고 같은 값을 가진 항목은 전부 `tie=true`다. 워크플로는 `tieBreak` 값에 따라 둘 중 한 검사를 적용한다(§6.3 (ii)).
- **`ratioToAvg` 불변 약속**: 엔진은 `snapshotId`별 결과를 영속 저장하고, 같은 `snapshotId`를 다시 조회하면 `ratioToAvg`를 포함한 모든 문자열 필드를 **바이트 단위로 동일하게** 돌려준다. 정책 버전이 바뀌어도 기존 스냅샷의 문자열은 재포맷하지 않는다. 이것이 봉인 해시 재현의 전제이며 엔진 provider 계약 테스트로 고정한다(`GET /internal/v1/disclosure/commission-grades/{snapshotId}` 조회 API 포함).

- **오류 응답(계약 1.1.0, 2026-09-29 E3 계획 승인)**: 400(요청 형식·상품군·기준일), 401(서비스 토큰), 403(요청 `tenantId` ≠ 엔진 인스턴스 테넌트 — 엔진은 테넌트별 인스턴스), 409(정책 버전 모호), 422(`NO_POLICY`·`POLICY_SELF_CHECK_FAILED` — 스냅샷을 만들지 않은 명시 오류), GET 404. 본문은 `Problem{code, message, details?}`.
- **계약 1.2.0(2026-09-30, 엔진 E3 요청 1~4)**: POST 400 코드 `AS_OF_IN_FUTURE`(기준일이 엔진의 오늘보다 뒤)·`UNKNOWN_PRODUCT_GROUP`, POST 422 코드 `INVALID_POLICY`(정책 데이터 결함), GET 500 `SNAPSHOT_INTEGRITY`(저장 원문 해시 불일치 — 손상된 원문을 반환하지 않는다). GET 403은 "토큰은 유효하나 인가 거부(역할 없음)"이고 다른 테넌트의 스냅샷은 404다(GET에는 테넌트 입력이 없다). 워크플로 엔진 클라이언트는 422를 정책 부재·결함으로 일반 처리한다(스냅샷 미생성, 명시 오류).
- **상품 키 규칙(계약 1.2.0, Phase 2 심사 §3-1·3A 계획 Q1)**: `productKey` = `{insurerCode}:{상품 코드}`, 패턴 `^[A-Z0-9][A-Z0-9-]{0,7}:[A-Za-z0-9][A-Za-z0-9._-]{0,30}$`, 40자 이하(엔진 원장 상품 키 폭이 기준). `insurerCode`는 `^[A-Z0-9][A-Z0-9-]{0,7}$`. `disclosure-domain`의 `ProductKey`·`InsurerCode`, 카탈로그 파일 스키마, 엔진 요청 검증(400)이 같은 규칙을 쓴다.
- **임시등록 상품은 요청하지 않는다(Phase 2 심사 §3-5).** 엔진 도메인에 없는 상품이라 키를 지어 보내면 충돌 위험만 있다. 워크플로가 로컬에서 `UNAVAILABLE(reason=TEMP_PRODUCT, source=LOCAL)`로 표기하고 순위 세트에서 제외한다(엔진이 `OK` 항목만으로 순위를 매기는 규칙과 같다). 응답 집합 = 요청 집합 검사(§6.3 (i))는 **임시등록을 제외한 항목**, 즉 요청한 항목에만 적용한다. 엔진은 `TEMP_PRODUCT` 사유를 내지 않는다.

- 등급은 **유사상품군 전체** 대비, 순위는 **요청한 세트 안**에서 매긴다(규정의 정의 그대로). 순위는 등급과 단조 관계여야 하며(같은 세트에서 낮은 등급이 더 나쁜 순위를 가질 수 없음) 워크플로가 이를 재검증한다(§6.3). 재검증에는 엔진이 정책 데이터에서 내려주는 `gradeOrdinal`(수수료가 낮을수록 작은 정수)만 쓴다 — 워크플로는 등급 코드의 의미·개수를 알지 못한다.
- `ratioToAvg`는 **표시·보관용 불투명 문자열**이다. 워크플로는 이를 숫자로 바꾸거나 비교하지 않는다(아키텍처 테스트로 금지).
- 수수료율 원 수치는 응답에 **없다**. 필요 시 엔진 `snapshotId`로 준법 권한자가 엔진에서 조회한다.
- `UNAVAILABLE`은 미공시·상품군 밖 등 산출 불가를 뜻한다(엔진 출처). 임시등록 상품의 로컬 `UNAVAILABLE(TEMP_PRODUCT)`도 같은 표기를 쓴다. 워크플로는 이를 "산출불가"로 표기하고 관리자 확인을 강제한다(§6.2 R-GRADE-UNAVAILABLE).
- 동점(`tie=true`) 처리 규칙은 `rankingPolicy` 데이터(예: 동순위 병기 / 보험료 낮은 순)이며 확인서에는 정책이 정한 표기로 인쇄된다.

**엔진 저장소 변경(별도 PR, Phase E3)**: ① `GradingPolicy`를 5단계 임계치(130/110/90/70%)·모수·기간이 **전부 데이터**인 버전 레코드로 재정의(Phase 15 리뷰 지적 반영, 3분위 고정 구현 제거) ② `RankingService`에 "세트 내 순위" 입력 추가 및 동점 정책(`tieBreak`) 데이터화 ③ 위 API 컨트롤러 + 스냅샷 영속 저장 + `snapshotId` 재조회 API + provider 계약 테스트(재조회 바이트 동일 포함) ④ 임계치 교체(예: 4단계로 변경) 시 코드 변경 0임을 증명하는 테스트.

**엔진 클라이언트(v1.7, Phase 3A).** `GradeSnapshotPort`(워크플로 포트)의 어댑터 `EngineGradeClient`(infra)는 ① 요청을 계약 요청 스키마로 자기 검증 ② 전송 ③ 상태 코드가 200이 아니면 명시 오류(`EngineUnavailableException`, 코드 `ENGINE_<상태>[_<Problem.code>]` — 예: `ENGINE_422_NO_POLICY`) ④ 엄격 UTF-8·중복 키 거부 JSON ⑤ **수신 즉시 계약 응답 스키마 검증**(oneOf 분기·`additionalProperties: false`) ⑥ 도메인 매핑(`ratioToAvg`는 `RatioLabel` 문자열 그대로) ⑦ `GradeConsistencyCheck`(§6.3)를 차례로 거친다. ⑤~⑦ 중 하나라도 실패하면 스냅샷을 만들지 않고 거부(위반 목록)다 — 워크플로가 `GRADE_INCONSISTENT` 플래그를 올리고 상태는 유지된다. 전송은 JDK `HttpClient`(추가 의존성 없음)이고, 산출 POST는 멱등이 아니므로 **재시도는 연결 실패(연결 거부·연결 타임아웃)에만**, 요청을 보낸 뒤의 타임아웃이나 응답을 받은 뒤의 오류는 재시도하지 않는다(연결·요청 타임아웃·최대 시도는 설정값). 서비스 토큰은 `EngineCredentialPort`(3A: 배포 설정 `ga.engine.credentials.<TENANT>`, `tenant.params`에 두지 않는다 → Phase 8에서 Phase 2 볼트 구현으로 교체)에서 받고 로그·예외에 넣지 않는다. 엔진 주소는 `tenant.engine_base_url`. 엔진 호출은 DB 트랜잭션 밖에서 한다(§6.2). 데모는 같은 클라이언트에 프로세스 안 스텁 전송(부록 B)을 끼운다 — 응답은 운영과 같은 검증을 거친다.

### 4.2 상품 카탈로그 공급 (`ProductCatalogPort`)

| 메서드 | 설명 |
|---|---|
| `listGroups(asOf)` | 유사상품군 목록(코드·명칭·생/손보 구분·유효기간) |
| `searchProducts(groupCode, insurerCode?, keyword, asOf)` | 상품 목록(상품키·보험사·상품명·판매기간·기본 보험료 예시·해약환급예시 표·비교 항목 기본값) |
| `getProduct(productKey, asOf)` | 상세 |

구현 어댑터: v1은 **파일/시드 기반**(협회·보험사 제공 파일을 가정한 CSV/JSON 수입기). 실제 연동은 어댑터 교체.

**파일 수입 규약(Phase 2 확정).** 파일 형식은 `contracts/catalog/v1/catalog-file.schema.json`(종류 `PRODUCT_GROUPS`·`INSURER_PANEL`·`PRODUCTS`, `source`, `asOf`, `rows`). 수입은 종류별 **전체 스냅샷**이다: 파일의 행은 upsert, 파일에서 사라진 열린 행은 `asOf`로 유효기간을 닫는다(삭제하지 않는다). 같은 테넌트·종류·파일 SHA-256은 NOOP, 마지막 수입보다 이른 `asOf`는 거절한다. 행마다 `source`·`source_ref`(`{파일명}@sha256:{hex}`)·`synced_at`을 남기고, 수입 1건은 `catalog_import` 1행과 감사 `CATALOG_IMPORT`(행별 before/after/end 변경 목록)다. 카탈로그 테이블은 현재 값만 갖고 변경 이력은 감사 로그가 보유한다. 유효기간은 룰과 같은 반개구간 `[from, to)`이며 조회는 전부 기준일 필수다(`listGroups(asOf)`, `searchProducts(…, asOf)`, `getProduct(key, asOf)`; 패널은 `InsurerPanelPort.isOnPanel(insurer, asOf)`로 `R-PANEL`이 사용). 운영자 CLI `catalog import --tenant --file`, 관리 API `POST /admin/v1/catalog/import`(Phase 6). 임시등록 상품은 카탈로그 밖에서 `disclosure_item.temp_product = true`로 설계사가 직접 입력하고 **가입설계서 발행번호**를 필수로 기록한다. 임시등록 항목은 상품키가 없고(`product_key` NULL) 엔진에 보내지 않는다(§4.1).

**상품 키 규칙(v1.7).** 파일의 `productKey`·`insurerCode`는 엔진 계약 1.2.0과 같은 패턴·길이(키 40자, 보험사 코드 8자)를 따른다. 규칙에 맞지 않는 키는 **자르지 않고 거부**하며, 문제 목록에 행 위치(`/products/{i}/productKey`)를 적어 파일 전체를 한 번에 실패시킨다.

### 4.3 협회 시스템 어댑터 (`IssuerPort`, ASSOC 모드)

`prepare(disclosureDraft) → assocRequestId`, `importIssued(assocRequestId) → {assocDocNo, pdf, signedAt…}`, `status(assocRequestId)`. v1은 인터페이스와 스텁만. ASSOC 모드에서 본 시스템의 상태기계는 `PREPARED → ISSUED_EXTERNAL → IMPORTED → COMPLETED`로 축약되고, 봉인·서명은 외부 문서를 **증빙으로 수입**하는 형태가 된다(해시체인·감사·보관·징구율은 동일).

### 4.4 청약 게이트 API (본 시스템 제공)

```
GET /internal/v1/disclosures/gate?customerRef=…&productKey=…&asOf=…
→ { "required": true, "status": "COMPLETED|PENDING|NONE", "pendingRoles": ["MANAGER"], "gateSatisfied": false,
    "disclosureNo": "T1-2026-000481", "completedAt": null, "gateMode": "BLOCK|WARN|OFF", "ruleVersionId": "DISC-2026-07" }
```

`required`는 대상 계약 판정 룰(§6.8)로 결정한다. (v1.9, 4 계획 승인 Q7) `gateRequiresManager`의 출처는 **룰 데이터 하나**다 — GLOBAL 기본값을 사규(TENANT 룰)가 덮어쓸 수 있고(`tenantOverridable`), `tenant.params`에는 두지 않는다(V8이 키를 제거). (v1.9) 산식은 순수 함수(`disclosure-sign` `GateFunction`)이고 `pendingRoles`는 signerSet 순서, 봉인 전·VOID·SUPERSEDED·EXPIRED는 해당 없음(`NONE`)·불충족이다. `gateSatisfied`는 `gateRequiresManager=true`이면 COMPLETED일 때만, `false`이면 고객·설계사 서명이 끝난 시점부터 true가 된다(관리자 확인은 이후에도 반드시 완료돼야 하며 미완료 시 LATE 플래그). 청약 시스템(또는 3순위 CRM)은 `gateMode`에 따라 진행을 막거나 경고한다. 계약 체결 후 `POST /internal/v1/disclosures/{no}/policy-link { policyNo, contractDate }`로 연결하며 이 연결은 확인서 본문이 아니라 **메타데이터**이므로 봉인 불변성과 충돌하지 않는다.

### 4.5 아웃박스 이벤트 (본 시스템 발행)

`DisclosureCreated`, `DisclosureSealed`, `SignatureCaptured(role)`, `DisclosureCompleted`, `DisclosureVoided`, `DisclosureSuperseded`, `PolicyLinked`, `ComplianceFlagRaised(type)`. 포털은 이 중 `SignatureCaptured(CUSTOMER)`·`DisclosureCompleted`·`ComplianceFlagRaised`를 알림으로 파생하고, CRM(3순위)은 고객 타임라인에 붙인다. 발행 방식·피드 API·Envelope는 포털 설계서 §4.1과 동일 규약.

(v1.9, 4 계획 승인 Q13) 8개 이벤트는 전부 **그 상태 변경과 같은 트랜잭션**에서 `outbox_event`에 적재한다 — 3A 생성·플래그, 3B 봉인·무효·정정 경로도 포함한다(피드가 아직 없다는 것이 누락이 보이지 않는 이유이므로 지금 넣는다). `seq`는 테넌트 안에서 갭 없이 1씩 증가하고(계약 envelope) `outbox_head` 행 잠금으로 직렬화한다 — 잠금 순서의 마지막(확인서 → 카운터 → 체인 머리 → 아웃박스 머리). 적재하는 envelope 전체(타입별 payload 포함)를 `contracts/events/v1` 스키마로 검증하고 위반은 명령 오류다. `seq`는 트랜잭션 범위 어드바이저리 잠금(테넌트 키)으로 직렬화한다 — 첫 이벤트는 머리 행이 아직 없어 행 잠금으로 직렬화할 수 없다. `ComplianceFlagRaised`는 플래그 저장소가 플래그를 **새로 열 때** 적재한다(워크플로·준법 배치 어느 경로든 한 곳을 지난다, 이미 열린 플래그 재사용은 이벤트 아님). 포트(`OutboxPort`)와 payload 생성기는 워크플로·준법이 함께 쓰므로 `disclosure-audit`에 둔다. 행은 지우지 않고 발행 시각만 한 번 기록한다(V8 GD106). 사유 텍스트·고객 개인정보는 payload에 싣지 않는다(계약 설명과 같다).

## 5. 데이터 모델 (PostgreSQL)

모든 테넌트 테이블은 `tenant_id`를 첫 컬럼으로 갖고 PK·인덱스에 포함한다. RLS·세션 바인딩은 포털과 동일. 본문 문서·PDF·서명 이미지는 오브젝트 스토리지에 두고 DB에는 키와 해시만 둔다.

```sql
-- 테넌트·신원 (포털과 같은 형태, 별도 DB에 독립 보유)
CREATE TABLE tenant (
  tenant_id        TEXT PRIMARY KEY,
  name             TEXT NOT NULL,
  engine_base_url  TEXT NOT NULL,                 -- 테넌트별 엔진 인스턴스
  status           TEXT NOT NULL,                 -- ACTIVE/PAUSED
  large_ga         BOOLEAN NOT NULL,              -- 설계사 500인 이상 여부(대상 판정 입력)
  issuer_mode      TEXT NOT NULL DEFAULT 'SELF',  -- SELF/ASSOC (D-2)
  gate_mode        TEXT NOT NULL DEFAULT 'WARN',  -- BLOCK/WARN/OFF (D-8)
  params           JSONB NOT NULL DEFAULT '{}'    -- 사규 파라미터: managerScope, tsaProfile ... (V8: gateRequiresManager 제거 — 룰 데이터 키, 승인 Q7)
);
CREATE TABLE identity_link (              -- IdP subject ↔ 설계사/관리자. agent_id는 여기서만 결정된다
  tenant_id TEXT, subject TEXT, agent_id TEXT NOT NULL, roles TEXT[] NOT NULL, org_path TEXT NOT NULL,
  PRIMARY KEY (tenant_id, subject)
);

-- 룰·서식 (룰 = 데이터)
CREATE TABLE rule_version (
  tenant_id TEXT, rule_version_id TEXT,            -- 예: DISC-2026-07
  scope TEXT NOT NULL,                              -- GLOBAL(규제) / TENANT(사규)
  apply_from DATE NOT NULL, apply_to DATE,
  status TEXT NOT NULL,                             -- DRAFT/APPROVED/ACTIVE/RETIRED
  approved_by TEXT, approved_at TIMESTAMPTZ,
  body JSONB NOT NULL,                              -- 부록 D 구조: minCompare, signerSet, reasonCodes, gradeRequired, subjectRule, retention...
  source_bundle_id TEXT, bundle_hash TEXT,          -- (V4) GLOBAL 복제본의 출처 번들과 body의 SHA-256(JCS). GLOBAL이면 NOT NULL(CHECK)
  PRIMARY KEY (tenant_id, rule_version_id)
);
-- GLOBAL 룰의 저장 방식(Phase 0 심사 확정): 규제 룰은 `contracts/rules/bundles/`의 번들 파일이 정본이고, 배포 명령이
-- 각 테넌트에 **같은 rule_version_id로 복제**한다. RLS를 예외 없이 유지하기 위해 시스템 테넌트·무테넌트 테이블을 두지 않는다.
-- 불변 규칙(트리거): body·apply_from·source_bundle_id·bundle_hash는 scope='TENANT'이고 status='DRAFT'일 때만 수정 가능(GLOBAL은 항상 불변).
-- apply_to는 NULL→값 한 번만 쓸 수 있다(후속 룰 배포가 선행 룰을 닫는 경로). status는 DRAFT→APPROVED→ACTIVE→RETIRED 순방향만.
-- 활성화는 일 배치(주입된 Clock): APPROVED이고 apply_from ≤ 오늘이면 ACTIVE, ACTIVE이고 apply_to ≤ 오늘이면 RETIRED.
-- 적용 구간이 이미 끝난(apply_to ≤ 오늘) APPROVED 룰은 활성화하지 않고 ComplianceFlag(RULE_ACTIVATION_MISSED, HIGH, 대상 = 룰)를 올린다
-- (같은 대상의 열린 플래그는 하나 — 배치를 다시 돌려도 복제되지 않는다). 배타 제약이 ACTIVE 겹침을 막으므로
-- 후속 번들은 `supersedes`로 선행 룰의 apply_to를 자기 apply_from으로 닫은 뒤 삽입된다(같은 트랜잭션).
-- 준법 배치가 매일 bundle_hash = SHA-256(JCS(body))를 재계산해 번들과 대조하고 불일치는 ComplianceFlag(RULE_DRIFT).
-- 번들 파일은 한 번 배포되면 고치지 않는다(새 rule_version_id). 예외: 번들 **형식**(스키마) 변경은 첫 운영 배포 전에만 제자리 수정할 수 있다
-- (Phase 2의 `validations` 객체화·`exceptionApproval`·`masking` 추가가 이 경우). 운영 배포된 번들 ID는 contracts/rules/released-bundles.txt에
-- 본문 해시와 함께 등재되고, 등재된 번들이 사라지거나 SHA-256(JCS(body))가 바뀌면 테스트(ReleasedBundlesAreFrozenTest)가 실패한다.
-- TENANT 룰은 GLOBAL 룰이 `tenantOverridable`로 열어 둔 키만 덮어쓸 수 있다(§6.2).
-- 해석 대상은 기준일에 "시행 중이었던" 룰이다: status ∈ {ACTIVE, RETIRED}이고 [apply_from, apply_to)가 기준일을 포함.
-- (RETIRED를 포함해야 경계일 이후에도 과거 상담일의 확인서를 같은 룰로 해석할 수 있다. APPROVED는 활성화 배치 전이므로 제외.)
-- 같은 scope·기준일에 2건이면 해석기는 Ambiguous로 실패한다(엔진과 동일 규약).
-- 추가로 DB가 겹침 자체를 막는다(btree_gist, V4에서 RETIRED까지 확장 — 과거 기준일의 해석이 사후에 바뀌지 않는다):
--   EXCLUDE USING gist (tenant_id WITH =, scope WITH =, daterange(apply_from, apply_to, '[)') WITH &&) WHERE (status IN ('ACTIVE','RETIRED'))
-- 엔진에서 "개시일이 다른 겹침이 유니크 인덱스를 통과한다"고 지적된 틈을 범위 배타 제약으로 닫는다.

CREATE TABLE form_template (
  tenant_id TEXT, template_id TEXT, template_type TEXT NOT NULL,   -- STANDARD / AUTO(예약)
  version INT NOT NULL, apply_from DATE NOT NULL, apply_to DATE,
  fields JSONB NOT NULL,        -- [{code, label, labelRef?, required, source(CATALOG|ENGINE|AGENT|SYSTEM), order, section(HEADER|COMPARISON),
                                --   render{scope, bind, readOnly?, unavailableText?}}] — (v1.8) bind = 항목 ↔ 값 결속(닫힌 어휘, §6.2)
  layout JSONB NOT NULL,        -- 렌더러가 읽는 배치: {title, sections[{code, orientation, label?, columnsPerTable?, fields[]}]}(v1.8)
  pending_confirmation JSONB NOT NULL DEFAULT '[]',   -- (V4) 정본 확인 전 자리표시 [{ref: TODO(confirm#N), note}]. 필드가 아니며 인쇄·필수 판정 대상이 아니다
  source_bundle_id TEXT, bundle_hash TEXT,            -- (V4) 번들 출처면 NOT NULL(둘 다), 테넌트 작성본이면 NULL
  PRIMARY KEY (tenant_id, template_id, version)
);
-- 번들 출처 템플릿은 불변(apply_to만 NULL→값 1회). 테넌트 작성본은 status가 없으므로 apply_from > 오늘(Asia/Seoul)인 동안만 수정 가능.
-- 같은 template_type의 적용 구간은 DB가 겹침을 막는다(EXCLUDE, V4). 번들 해시 = SHA-256(JCS({fields, layout, pendingConfirmation})).

-- 카탈로그(외부 정본의 캐시)
-- (V5) 세 테이블 공통: source·source_ref('{파일명}@sha256:{hex}')·synced_at 필수, 유효기간 반개구간 [from, to)(CHECK to ≥ from,
-- 빈 구간 [x, x)는 "개시 전 철회"), DELETE·TRUNCATE 거부(GD070 — 파일에서 사라진 행은 기간을 닫는다), line ∈ {LIFE, NONLIFE}.

CREATE TABLE compliance_flag (
  tenant_id TEXT, flag_id UUID, type TEXT NOT NULL,     -- MISSING/LATE/GRADE_UNAVAILABLE/TEMP_PRODUCT/VALIDATION_OVERRIDE/CHAIN_BROKEN/...
  disclosure_id UUID, policy_no TEXT, agent_id TEXT, severity TEXT NOT NULL,

-- (V5) 같은 대상의 열린 플래그는 하나: UNIQUE (tenant_id, type, target_kind, target_id) WHERE resolved_at IS NULL AND target_id IS NOT NULL.
```

**불변식(테스트·DB 트리거로 상시 검증)**
- `status ∉ {DRAFT, COMPARED, GRADED, REASONED}`인 확인서의 `disclosure_item`·`recommendation`·헤더 본문 컬럼은 UPDATE 불가, 같은 부모에 `disclosure_item`·`recommendation` INSERT·DELETE 불가(트리거 + 애플리케이션 이중).
- 봉인 이후 상태(`SEALED`~`EXPIRED`)에서 가변 상태(`DRAFT`~`REASONED`)로의 `status` UPDATE는 거부한다. 막지 않으면 `status='DRAFT'`로 되돌린 뒤 본문을 고치는 우회가 생긴다. `superseded_by_id`는 NULL→값 한 번만 쓸 수 있다.
- `signature.signed_doc_hash = disclosure.canonical_hash`이고 부모 `status ∈ {SEALED, PARTIALLY_SIGNED}`일 때만 INSERT 허용. 불일치 해시, 봉인 전, `VOID`·`EXPIRED`·`SUPERSEDED`·`COMPLETED` 문서에 대한 서명은 거부.
- `audit_log.entry_hash`는 직전 `entry_hash`와 본문으로 재계산 시 일치. `verify` 명령이 전 구간 검사.
- 활성 `rule_version`은 scope·기준일당 정확히 1건(DB 배타 제약 + 해석기 fail-fast 이중).
- `disclosure_item`의 추천 상품 수 ≥ `rule.minCompare`이고 보험사 코드가 서로 다름 (봉인 시점 검증, 봉인 후 불변).
- (v1.8) 확인서 번호는 테넌트·연도별 1부터 빈 번호 없이 연속이고, 봉인 체인은 테넌트별 `chain_seq` 1..n 갭 없이 `chain_hash`가 재계산과 일치한다(V7 카운터·체인 머리·GD095 + `SealChainIT`·`NumberingIT`).
- (v1.8) 봉인 산출물·문서 키는 봉인된 확인서에만 생기고 지워지지 않는다. 키 파기 뒤에는 어떤 사본도 복호화되지 않는다(GD092·GD093 + `ArtifactEncryptionIT`).

## 6. 핵심 로직

### 6.1 상태기계

```
DRAFT ─(항목 ≥ min, 검증 R-*)→ COMPARED ─(엔진 스냅샷)→ GRADED ─(추천사유)→ REASONED
   ─(검증 전건 통과 + 봉인)→ SEALED ─(서명 수집)→ PARTIALLY_SIGNED ─(서명자 집합 충족)→ COMPLETED
어느 단계든: → VOID (사유·승인)          SEALED 이후: → SUPERSEDED (새 버전 DRAFT 생성·복제)
SEALED/PARTIALLY_SIGNED에서 sign_deadline 경과: → EXPIRED (재발급만 가능)
```

| 전이 | 조건 | 부수 효과 |
|---|---|---|
| DRAFT→COMPARED | 항목 수·보험사 상이·상품군 일치·패널 포함 검증 | — |
| COMPARED→GRADED | 엔진 응답 수신, 순위-등급 단조성 검증, `UNAVAILABLE` 항목은 플래그 | `grade_snapshot_id` 저장, 항목에 등급·순위 복사 |
| GRADED→REASONED | 추천 항목마다 사유 코드 ≥ 1, OTHER면 텍스트 필수 | — |
| REASONED→SEALED | 전 검증 룰 통과(오버라이드는 관리자 승인 + 플래그) | 룰 버전 확정, 채번, JCS 해시, PDF/A 렌더, PDF 해시, 체인 연결, 스토리지 저장(Object Lock) |
| SEALED→PARTIALLY_SIGNED→COMPLETED | 서명자 집합(`rule.signerSet`, 관리자 필수 여부 파라미터)과 순서(`signOrder`) 충족 | SIGNED_PDF·EVIDENCE_ZIP 생성, `retention_until` 계산, 이벤트 발행 |
| 항목 변경 시도(GRADED 이후) | 항목이 바뀌면 스냅샷 무효 | 자동으로 COMPARED로 되돌리고 재산출 요구(등급이 상품과 어긋나는 상태를 만들지 않는다) |
| 스냅샷 노후 | `sealed_at − generatedAt > rule.snapshotMaxAgeDays` | 봉인 거부, 재산출 요구 |

**상태 × 명령 표(v1.7, 정본).** 아래 `state-table` 블록이 전이표의 정본이다. 코드(`DisclosureStateTable`, EnumMap)와 양방향 전수 대조를 `DisclosureStateTableTest`가 이 파일을 파싱해 한다 — 사람이 읽기 좋게 고치다 형식이 깨지지 않도록 마크다운 표가 아니라 CSV(`state,command,result`, 결과가 여럿이면 `|`)로 둔다. 표에 없는 (상태, 명령)은 `IllegalTransition`이다. 명령 어휘는 `REPLACE_ITEMS, COMPARE, APPLY_SNAPSHOT, SET_RECOMMENDATIONS, SEAL, SIGN, COMPLETE, EXPIRE, VOID, SUPERSEDE, REBASE`이고 상담일 변경 명령은 없다(새 초안을 만든다). 3A가 앞의 넷을, 3B가 `SEAL`·`VOID`·`SUPERSEDE`·`REBASE`를 구현했다. `SIGN`·`COMPLETE`·`EXPIRE`는 표에만 있고 구현하는 Phase(4)가 테스트의 "구현된 명령" 목록을 늘린다.

- `REBASE`(v1.8, 3A 수용심사 §3-8·3B 계획 승인 Q3): 소급 배포로 고정 룰·서식이 상담일 재해석과 달라진 산출 전후 초안(COMPARED·GRADED·REASONED)을 새 해석으로 다시 고정한다. 스냅샷·추천사유를 버리고, 새 룰의 COMPARE 단계 검증을 통과하면 COMPARED, 오버라이드 불가 실패가 있으면 DRAFT다(COMPARED는 "비교 검증을 통과한 상태"라는 불변식을 지키고 막다른 상태를 만들지 않는다). `RULE_SUPERSEDED_DRAFT` 열린 플래그가 있을 때만 허용하는 명령이다(임의 재기준 금지). 옛 승인은 삭제되지 않고 룰 버전 귀속으로 무효가 된다.

- `REPLACE_ITEMS`: DRAFT에서는 검증 없이 교체한다(작성 중). COMPARED 이후에서는 교체한 항목으로 COMPARE 단계 검증을 다시 통과해야 하고, 산출 이후(GRADED·REASONED)면 스냅샷과 추천사유를 버리고 COMPARED로 돌아간다(항목 집합이 바뀌면 순위·사유의 대상이 바뀐다).
- `APPLY_SNAPSHOT`(재산출 포함, 3A 계획 Q5): COMPARED·GRADED·REASONED에서 허용, 결과는 GRADED, 추천사유는 버린다(이전 사유를 되살려 채우지 않는다 — 절대 규칙 7).
- 전이의 검증 조건: 각 명령은 그 단계(`COMPARE`·`GRADE`·`REASON`)의 룰 검증을 **적용 후 모습**에 대해 돌린다. `overridable=false` 실패가 하나라도 있으면 거부(상태 불변). `overridable=true` 실패는 중간 단계에서 전이를 막지 않고 준법 플래그와 감사만 남긴다 — 관리자 승인(`review`) 확인은 봉인(SEAL) 조건이다(3A 계획 Q2).

### 6.2 검증 룰 (룰 = 데이터, `rule_version.body.validations`)

| R-REQUESTED | `requested_by_customer` 항목은 최소 비교 개수에 산입 가능하되 사유 코드에 `CUSTOMER_REQUEST` 자동 부가 | — |

룰 본문(부록 D)은 JSON이며 실행기는 `ruleId → 평가 함수` 레지스트리다. **새 룰은 레지스트리에 평가 함수를 추가하고 데이터로 활성화**하며, 기존 룰의 파라미터 변경(3→4개 등)은 데이터만 바꾼다.

**검증 단계(Phase 1 심사 확정).** `validations`는 객체 배열 `[{ "id": "R-MIN-COMPARE", "stages": ["COMPARE", "SEAL"] }, …]`이다. 단계 어휘는 코드가 분기하는 닫힌 열거 `ValidationStage {COMPARE, GRADE, REASON, SEAL, COMPLETE}`(§6.1 전이와 1:1)이고, 어느 규칙을 어느 단계에서 돌리는지는 데이터다. 실행기는 `run(stage)`로 그 단계에 나열된 규칙만 **데이터에 적힌 순서대로** 실행한다. 기본값은 없다 — `stages`가 비었거나 같은 ID가 두 번 나오면 룰 해석이 실패하고, 레지스트리에 없는 ID는 어느 단계를 돌리든 `UNKNOWN_VALIDATION`으로 실패한다. SEAL 단계가 이전 단계의 규칙을 다시 도는 것은 의도(방어적 재검증)다.

**서식 결속 `render.bind`(v1.8, 3A 수용심사 §3-1 — v1.7의 출처별 판정을 대체).** 서식 항목마다 어느 값에 묶이는지를 닫힌 어휘 `bind`로 데이터에 적는다. 코드는 항목 코드를 모르고 `bind`로만 분기하며, 렌더러와 R-FIELD-REQUIRED가 **같은 함수**(`BindingResolver`)로 값을 찾는다 — "존재 판정"과 "인쇄 값"이 갈라질 수 없다. 검증 시점의 단면은 애그리게이트가, 렌더 시점의 단면은 봉인 본문(canonical)이 제공한다.

| bind | scope · source | 값 | 존재 판정 |
|---|---|---|---|
| `HEADER_DISCLOSURE_NO` | DOCUMENT · SYSTEM | 확인서 번호(canonical 밖, 봉인이 발급) | 검증 시점에는 "발급 예정"으로 존재 |
| `HEADER_CONSULT_DATE` | DOCUMENT · SYSTEM | 상담일 `yyyy-MM-dd` | 항상 |
| `HEADER_AGENT` | DOCUMENT · SYSTEM | 설계사 | 항상 |
| `HEADER_CUSTOMER_NAME` | DOCUMENT · SYSTEM | 고객 성명(봉인 때 복호화해 canonical에) | 검증 시점에는 "봉인 예정"으로 존재(복호화 가능 여부는 봉인 조건 ⑥) |
| `HEADER_PRODUCT_GROUP` | DOCUMENT · CATALOG | 상담일 카탈로그의 상품군 이름 | 상품군이 있으면 |
| `PANEL_INSURERS` | DOCUMENT · SYSTEM | 상담일 위탁 패널 보험사 이름 목록 | 패널이 비어 있지 않으면 |
| `ITEM_INSURER_NAME` | ITEM · CATALOG | 항목 보험사의 패널 이름 | 그 보험사가 상담일 패널에 있으면 |
| `ITEM_PRODUCT_NAME` | ITEM · CATALOG | 상품명 | 항상 |
| `CATALOG_DEFAULT` | ITEM · CATALOG | `field_values[code]`(카탈로그 기본값 복사 또는 임시등록 입력) | 값이 있으면(출처 무관) |
| `AGENT_INPUT` | ITEM · AGENT | `field_values[code]` | 출처가 설계사 입력인 값만 — **추천사유로 대체되지 않는다** |
| `ENGINE_GRADE_LABEL` · `ENGINE_RANK` | ITEM · ENGINE | OK면 라벨·순위, 산출불가면 `unavailableText` | 등급 복사본이 있으면 |
| `ENGINE_UNAVAILABLE_TEXT` | ITEM · ENGINE | 산출불가 문구와 사유, 산출된 항목은 빈 칸 | 등급 복사본이 있으면 |
| `RECOMMENDATION` | ITEM · AGENT | 추천 항목: 사유 라벨들 + 텍스트, 비추천 항목: 빈 칸 | 추천 항목은 사유 ≥ 1, 비추천은 그 판단이 값 |

카탈로그 상품을 담을 때 카탈로그 `defaults`에서 복사하는 것은 `CATALOG_DEFAULT` 결속 항목의 같은 코드 값뿐이고, 설계사가 입력할 수 있는 항목은 `AGENT_INPUT`(임시등록은 `CATALOG_DEFAULT`도)이다. 서식 스키마가 결속마다 허용 scope·source를 강제하고, 서식 항목은 `section`으로 문서 식별부(`HEADER` — 확인서 번호·상담일·설계사·고객 성명 결속만)와 비교 항목(`COMPARISON`)으로 나뉜다. 식별부는 비교 항목 수 산정·`pendingConfirmation`과 섞지 않으며, 라벨이 정본 확인 전 가정이면 `labelRef: TODO(confirm#2)`로 표시한다(3B 계획 승인 Q2). 배치(`layout`)는 모든 항목을 섹션 하나에 정확히 한 번 담고(번들 로더가 검사), 비교표 섹션은 표당 열 수 `columnsPerTable`도 데이터로 가진다. 값 표기는 로케일 없는 원문이다(승인 Q10) — 천 단위 구분 같은 표시 서식은 서식 데이터(`render.format`, Phase 7)로만 둔다.

**트랜잭션과 감사(v1.7, 3A 계획 Q6·승인 B2).** "각 유스케이스는 하나의 트랜잭션"은 **상태 변경과 그 감사가 한 트랜잭션**이라는 뜻이다. 명령은 행을 `FOR UPDATE`로 잠그고 애그리게이트로 적용한 뒤 저장·감사(`DISCLOSURE_VALIDATE`·`DISCLOSURE_TRANSITION`)·플래그를 같은 트랜잭션에 쓴다. 엔진 호출만 트랜잭션 밖이다 — 짧은 읽기 트랜잭션에서 요청(임시등록 제외 상품키·기준일·상품군)과 그 지문을 만들고, 호출 뒤 쓰기 트랜잭션에서 다시 잠가 지금 확인서의 요청 지문과 대조한다. HTTP 대기 동안 커넥션·행 잠금을 쥐지 않기 위해서다. 실패는 다음처럼 기록한다.

| 종류 | 예 | 처리 |
|---|---|---|
| 업무 거부(예상된 결과) | 단계 검증의 오버라이드 불가 실패, 엔진 응답의 스키마·정합성 위반, 엔진 호출 중 항목 변경(`GRADE_STALE`) | 업무 트랜잭션이 **정상 커밋**한다. 감사(`DISCLOSURE_VALIDATE`·`GRADE_FETCH`·`DISCLOSURE_REJECT`)와 플래그(`GRADE_INCONSISTENT`)가 남고 상태는 바뀌지 않는다. 호출자에게는 결과 객체(거부 사유·검증 결과·엔진 위반 목록) |
| 명령 오류(예외) | 표 밖 명령(`IllegalTransition`), 룰 해석 실패, 엔진 연결 실패·오류 응답(422 등)·타임아웃, 입력 전제 위반, 예기치 않은 오류 | 업무 트랜잭션은 **롤백**한다. 그 뒤 **같은 테넌트 컨텍스트**의 별도 트랜잭션으로 `COMMAND_FAILED` 1행(명령·대상·예외 종류·오류 코드)을 남긴다. 메시지는 넣지 않는다(입력값이 섞일 수 있다, 절대 규칙 6). 기록 자체가 실패하면 원 예외에 suppressed로 붙이고 ERROR 로그 |
| 테넌트 미바인딩 | 테넌트 없이 호출된 명령 | 감사 대상이 아니다(RLS 밖에 쓸 곳이 없다). 원 예외만 전파 — 401·기동 오류로 매핑 |

**오버라이드 가능한 실패(v1.7, 3A 계획 Q2·Q3).** 중간 단계(COMPARE·GRADE·REASON)에서 `overridable=true` 실패는 전이를 막지 않는다 — 준법 플래그 `VALIDATION_OVERRIDE`(대상 `DISCLOSURE_RULE`/`{확인서}/{규칙 ID}`, 열린 플래그 재사용)와 감사만 남긴다. 관리자 승인 확인은 봉인(SEAL) 조건이다: 승인(`review`)은 (확인서, 규칙, 실패 대상의 `SHA-256(JCS)`)에 귀속되고, 봉인 판정(`SealGate`)은 오버라이드 불가 실패 전부와 대상 해시가 맞는 승인이 없는 오버라이드 가능 실패를 막는다. 대상이 바뀌면(예: 다른 발행번호의 임시등록) 승인은 효력이 없고, 재산출해도 같은 대상(같은 산출불가 집합)이면 유지된다 — "서명은 문서 해시에 귀속"과 같은 원리다. 대상은 R-TEMP-PRODUCT가 임시등록 {보험사, 상품명, 발행번호}의 집합, R-GRADE-UNAVAILABLE이 산출불가 {항목, 사유, 출처}의 집합이다(항목 순서 무관). 승인 기록은 봉인 전에만 가능하고(GD080) 수정·삭제가 없다(GD030). 인가(`exceptionApproval.role`)는 Phase 6.

**룰 해석(Phase 0 심사 확정).** 기준일(상담일)로 `scope=GLOBAL`과 `scope=TENANT`를 **각각** 단건 해석한다(각 scope에서 2건이면 Ambiguous 실패, GLOBAL 0건이면 실패, TENANT 0건은 정상). 유효 룰 = GLOBAL body 위에 TENANT body를 덮되, **GLOBAL body의 `tenantOverridable` 목록에 있는 키만** 덮어쓸 수 있다. 목록에 없는 키를 TENANT 룰이 가지면 해석은 실패한다(조용히 무시하지 않는다). 덮어쓰기는 최상위 키 단위이며 깊은 병합은 하지 않는다. 결과에는 두 버전 ID가 함께 박제된다(`disclosure.rule_version_id`, `tenant_rule_version_id`). 어떤 키를 테넌트에 열어 줄지는 규제 룰(번들) 데이터가 정하므로, "사규가 규제를 완화할 수 없다"는 원칙도 코드가 아니라 데이터로 표현된다(예: `minCompare`는 목록에 없고 `signDeadlineDays`·`remoteLinkTtlHours`·`channels`는 있음). 서식 항목 12개의 구체 목록은 협회 표준서식이 정본이므로 `form_template.fields`로 관리하고 코드에 항목명을 두지 않는다(하드코딩 금지, 엔진 공시 서식 원칙과 동일).

### 6.3 등급·순위 표기 규칙

- 기준일 = 상담일(`consult_date`). 엔진 요청에 기준일과 상품군을 넘기고, 응답의 정책 버전 2종·`snapshotId`·`basis`를 헤더에 저장, 항목에는 등급·라벨·순위·비율만 복사한다.
- 확인서에는 **등급 라벨과 순위만** 인쇄. 비율·수치·정책 버전은 준법 화면과 증거 패키지에만 포함.
- 정합성 검증: (i) 응답 상품 집합 = 요청 집합(요청 = 임시등록을 제외한 항목, §4.1) (ii) `OK` 항목 m개에 대해 `tieBreak=STRICT`면 `rankInSet`이 1..m 순열, `SHARED_RANK`면 경쟁 순위 조건(§4.1)과 동일 순위 항목의 `tie=true` (iii) 순위-등급 단조(`rankInSet` 오름차순일 때 `gradeOrdinal`이 감소하지 않음; 동순위끼리는 `gradeOrdinal`이 같아야 함) (iv) 정책 버전·`tieBreak`가 워크플로 룰 버전이 허용하는 목록에 포함 (v) `UNAVAILABLE` 항목에 등급·순위 필드가 없음. 하나라도 실패하면 스냅샷을 버리고 `ComplianceFlag(GRADE_INCONSISTENT)`.
- 항목이 추가·삭제되면 세트가 바뀌므로 순위가 달라진다 → 자동 재산출(§6.1). 4번째 이상 항목(고객 요청 등)도 세트에 포함해 순위를 다시 받는다.
- 산출불가 항목의 인쇄 문구는 템플릿 데이터(`render.unavailableText`).

### 6.4 봉인(Seal)

1. 룰 버전·템플릿 버전: **초안 생성 때 상담일로 한 번 해석해 고정한 ID를 로드**한다(v1.7 — 상담일은 바뀌지 않으므로 봉인 때 재해석과 결과가 같다). 예외는 소급 배포(초안 생성 뒤 `apply_from ≤ 상담일`인 GLOBAL·TENANT 새 버전 배포)뿐이다 — 3B는 봉인 조건에 "상담일 재해석 결과 = 고정 ID"를 넣고, 다르면 봉인 거부 + `compliance_flag(RULE_SUPERSEDED_DRAFT)`. 재기준(rebase: COMPARED로 회귀 + 새 ID 고정) 명령은 3B가 정의한다(3A 계획 승인 B1). (v1.9, 4 계획 승인 Q1 — 3B 일탈 D1 유지) **로더는 시작일만 본다, 봉인이 막는다**: 고정 버전 로드는 `apply_from ≤ 상담일`만 확인한다. 소급 배포가 고정 버전의 `apply_to`를 상담일 이전으로 닫아도 그 초안은 읽히고(읽히지 않으면 판정·거부·재기준조차 못 하는 막다른 상태가 된다), 그 버전으로의 봉인은 10항 ①②가 거부한다. 로더는 그 대신 두 가지를 확인한다(승인 Q1): 고정 버전은 시행된 적이 있어야 하고(`ACTIVE`·`RETIRED`, scope 일치, 시작일 ≤ 상담일 — 아니면 `PINNED_VERSION_NOT_IN_FORCE`), 로드한 유효 본문의 해시가 고정 때(생성·정정 새 버전·재기준) 감사에 기록한 `ruleBodyHash`와 같아야 한다(다르거나 기록이 없으면 명령 오류 `RULE_PINNED_BODY_MISMATCH` — 불변 트리거의 싼 이중 검사).
2. 본문을 **정규화 JSON(RFC 8785 JCS)** 으로 직렬화 → `canonical_hash = SHA-256`. (v1.8) 본문 구성의 정본은 `contracts/seal/v1/canonical.schema.json`이다: `canonicalVersion: 1`, 테넌트·확인서 ID·버전·`supersedesId`·설계사·`customerRef`·성명·상담일·상품군{코드, 이름}·정본 모드·고정 버전{룰, 사규, 서식 ID·버전}·스냅샷 헤더{ID, 정책 2종, `tieBreak`, `basis`, `generatedAt`}·패널{코드, 이름}·항목(item_no 순 — 상품키·보험사·상품명·상품군·임시등록·발행번호·추천·고객 요청·`fieldValues {코드: 값}`·등급 복사본(OK: 등급·라벨·서수·순위·비율 원문·동점 / 산출불가: 출처·사유)·추천사유{사유[{코드, 라벨}], 텍스트}). 번호·상태·봉인 시각·해시·체인·메타 컬럼·출처(origin)·전화·생년월일·등록 키는 넣지 않는다(스키마 금지 키). 최상위는 항상 객체, 모든 객체는 닫혀 있고 선택 값은 `null`, 정수는 ±(2^53−1), 소수 없음. 패널·상품군 이름·사유 라벨은 고정 룰·서식·상담일 카탈로그에서 해석한 **문자열 결과**를 넣는다 — 렌더러의 입력이 canonical + 서식 + 번호로 닫히고, 라벨이 나중에 바뀌어도 봉인 본문은 그때 문구를 보존한다(3B 계획 승인 Q11).
3. 확인서 번호 채번(테넌트별 연도 시퀀스, 예: `T1-2026-000481`). (v1.8) 연도 = **봉인일(Asia/Seoul) 연도**(3B 계획 승인 Q5). `(tenant, year)` 카운터 행 `INSERT … ON CONFLICT DO UPDATE SET seq = seq + 1 RETURNING seq`를 봉인 트랜잭션 안에서 한 번 — 번호 선할당 없음, 봉인이 실패하면 번호도 롤백(무결번, 3A 수용심사 §3-4).
4. 템플릿 `layout`과 `bind`로 HTML 렌더 → **PDF/A-2b** 변환 → `pdf_hash`. (v1.8) 각주(모든 쪽)에 확인서 번호 · `canonical_hash` 앞 12자 · 쪽/전체 쪽을 **텍스트**로 인쇄해 종이와 원본을 잇는다(QR은 §14 #9 미결정). 비율(`ratioToAvg`)은 인쇄하지 않는다(§6.3). 문서 제목·섹션 이름·항목 라벨은 서식 데이터이고 렌더러에 문구 리터럴이 없다(`NoFieldCodeLiteralsTest`).
5. `chain_hash = H(prev_chain_hash || canonical_hash || pdf_hash)`, `chain_seq` = 테넌트 봉인 시퀀스.
6. CANONICAL_JSON·PDF를 스토리지에 저장(Object Lock, 보존기간 = `retention_until`), DB 커밋, 감사 로그 SEAL. (v1.8 순서, 3A 수용심사 §3-5) 문서 키로 암호화 → 업로드(**잠금 없음**) → DB 커밋 → **커밋 후** `PutObjectRetention`(COMPLIANCE, 기한 = `retention_until` 당일 끝 Asia/Seoul) → `retention_applied_at` 기록. 커밋이 실패하면 잠금 없는 잔여물만 남아 잔여물 정리(`artifacts gc`)가 지우고, 잠금 적용이 실패하면 행이 `retention_applied_at IS NULL`로 남아 재적용(`artifacts reconcile`)이 건다. 보존기한은 봉인 때 봉인일 + `retentionYears`로 정하고 이후 연장만 한다(승인 Q6, DB GD094 — 저장소도 연장만 허용). (v1.9, 3B 수용심사 §3-3) 일반식은 `retention_until = max(현재, max(앵커 날짜 + retentionYears))`이고 앵커는 룰 `retentionAnchors`(SEAL = 봉인일, COMPLETION = 완료일 KST, CONTRACT_DATE = 계약일) 중 날짜가 생긴 것이다 — 봉인 때는 SEAL만 있으므로 위와 같고, 완료·계약 연결 때 다시 계산해 늘어나면 모든 산출물·증거 객체에 잠금을 다시 건다.
7. 렌더는 **결정론적**이어야 한다: 같은 canonical JSON + 같은 템플릿 버전 + 같은 번호 → 같은 PDF 바이트(폰트 임베드·타임스탬프 고정). 이것이 "재렌더로 원본 검증" 테스트의 전제다. (v1.8) 렌더러·canonical 패키지는 벽시계·`Clock`·난수·기본 로케일·시간대를 읽지 않는다(아키텍처 규칙). 라이브러리가 매번 바꾸는 세 지점은 입력에서 파생해 고정한다: ① 문서 정보 `/CreationDate`·`/ModDate` = 상담일 00:00 +09:00(고정 오프셋 객체, 시스템 시간대 DB 미사용) ② XMP는 라이브러리 산출물을 고치지 않고 통째로 새로 쓴다(`pdfaid` 2/B, `dc:title` = 서식 제목 = 정보 `/Title`, `pdf:Producer` = `ga-disclosure-renderer/1` = 정보 `/Producer`, 세 날짜 = 상담일 `T00:00:00+09:00`) ③ 트레일러 `/ID` = `[h[0..16), h[0..16)]`, `h = SHA-256(ASCII(canonical_hash) ‖ ASCII(disclosure_no))`. 골든 3건의 canonical·PDF SHA-256을 로컬 macOS에서 만들어 커밋하고 CI Linux가 같은 값을 내야 통과한다(`SealGoldenTest`). CI `pdfa-verify` 잡이 골든 PDF를 veraPDF PDF/A-2b로 검증한다(실패 0).
8. **고객 성명(v1.7, Phase 2 심사 §3-4)**: 봉인 본문에는 고객 **성명만** 들어간다(v1.8: 봉인 유스케이스만 복호화한다 — 감사 `CUSTOMER_VIEW`(사유 `SEAL`), 성명 원문을 꺼내는 곳은 canonical 빌더뿐(아키텍처 허용 목록), 렌더러에는 복호화 경로가 없다)(연락처·생년월일·`customer_ref` 밖의 식별정보는 넣지 않는다). 확인서는 고객에게 교부되는 문서이고 서명자가 누구인지 문서 자체가 말해야 증거이며, 성명을 PDF에만 넣고 canonical에서 빼면 7항의 결정론이 깨진다. 봉인 산출물(canonical JSON·PDF·증거 패키지)은 오브젝트 스토리지에 **테넌트 키로 암호화**(SSE-KMS 또는 클라이언트 측 봉투 암호화 — 어댑터가 정한다)해 저장하고, 산출물 열람은 전 건 감사한다.
9. **PDF 변환기(v1.7, 3A 계획 승인 §3 — 3B 선결정)**: openhtmltopdf 1.1.x(JVM 안, PDF/A-2b; v1.8 구현 1.1.87 + PDFBox 3.0.7, 전이 의존 중 Boot BOM이 관리하는 commons-logging은 BOM 버전). 문서 정보 날짜·XMP 날짜·`/ID` 시드를 전부 봉인 입력(canonical 해시·확인서 번호)에서 파생해 벽시계를 참조하지 않는다. sRGB ICC 프로파일과 폰트(NanumGothic, OFL — 라이선스 파일 포함)는 저장소에 동봉하고 빌드 때 내려받지 않는다. CI(Linux)와 로컬(macOS arm64)의 PDF SHA-256 일치가 3B 완료 기준이며, ICC·폰트를 고정해도 어긋나면 WeasyPrint 사이드카로 전환하고 결정 기록에 남긴다. 후보 비교 실측은 `verification/pdf-candidates/`.
10. **봉인 조건과 트랜잭션(v1.8, 3A 수용심사 §3-2·3B 계획 §3).** 조건은 전부 **업무 거부**이고 **단락 없이 전부 평가**해 목록으로 돌려준다(싼 것부터): ① `RULE_SUPERSEDED` 상담일 재해석 룰(GLOBAL·TENANT) ≠ 고정 ② `TEMPLATE_SUPERSEDED` 상담일 재해석 서식 ≠ 고정(①·②면 `RULE_SUPERSEDED_DRAFT` 플래그) ③ `SNAPSHOT_STALE` 산출 뒤 `snapshotMaxAgeDays` 경과 ④ `VALIDATION_BLOCKED` SEAL 단계 오버라이드 불가 실패 ⑤ `APPROVAL_MISSING` 고정 룰 버전 2종에 귀속된 승인이 없는 오버라이드 가능 실패 ⑥ `CUSTOMER_NAME_UNAVAILABLE` 성명을 풀 수 없음(키 상태만 보고 복호화하지 않는다). 거부는 상태·번호·카운터·체인·키·산출물·저장소를 바꾸지 않고 감사 `DISCLOSURE_SEAL_REJECTED` **1행**(거부 코드 전부·검증 결과·판정 룰의 정체·플래그 ID)만 남긴다. 성공 경로는 한 쓰기 트랜잭션(제한 시간 기본 60초)이고 잠금 순서는 언제나 **확인서 행 → 카운터 행 → 체인 머리 행**(승인 Q7): 성명 복호화(감사 `CUSTOMER_VIEW`, 사유 `SEAL`) → 봉인 본문·해시 → 채번 → 렌더 → 문서 키·암호화 → 업로드 → 체인 → 봉인 컬럼 → 키·산출물 기록 → 체인 머리 이동 → 감사 `DISCLOSURE_SEAL`(검증 결과는 이 행에 — 별도 검증 행 없음) → 오버라이드 플래그 해소(승인 있음 `APPROVED`·해소자 = 승인자, 더는 실패하지 않음 `RESOLVED_AT_SEAL`·`SYSTEM`) → 커밋. 예외(룰 해석 실패·복호화 실패·스키마 위반·저장소 오류)는 명령 오류(롤백 + `COMMAND_FAILED`). DB는 봉인되는 순간 번호 = 그 연도 카운터의 현재 값, 번호 연도 = 봉인 시각의 서울 연도, 체인 = 머리 + 1·식을 다시 검사한다(V7 GD095).

### 6.5 서명

- 세션 생성 시 `signed_doc_hash`가 고정된다. 서명은 그 해시에 대해서만 유효하며 다른 버전에는 붙지 않는다. (v1.9 V8, 3B 수용심사 §3-1) 세션은 **고객 서명에만** 쓰고 발급 때 `signed_doc_hash`·`signed_pdf_hash` 두 해시를 고정한다(GD101). 서명은 두 해시 모두에 귀속되고(GD022·GD102), 고객 서명은 그 확인서의 OPEN 세션을 거쳐야 하며(GD103), 역할은 고정 룰의 `signerSet`에 있어야 한다(GD104).
- **세션·토큰(v1.9, 4 계획 §2)**: 토큰 = `{tenantId}~{base64url(256비트)}`(승인 Q4 — 테넌트 접두는 비밀이 아니고 공개 엔드포인트가 RLS 바인딩 전에 테넌트를 알기 위한 것), 저장은 토큰 전체 ASCII의 SHA-256뿐이다. 난수는 포트(`TokenSource`)로 받는다. 형식 오류·없는 테넌트·틀린 토큰·닫힌 세션은 **같은 거부**다(B2, 같은 응답·지연은 Phase 6). TOUCH_PAD·PAPER_SCAN 토큰은 설계사 기기 앱이 쥐고, REMOTE_LINK 토큰만 고객에게 나간다. 세션 만료 = min(발급 + TTL, 서명 기한 끝) — TTL은 REMOTE_LINK `remoteLinkTtlHours`, TOUCH_PAD·PAPER_SCAN `sessionTtlMinutes`. 서명 기한 끝 = (봉인일 KST + `signDeadlineDays`) 23:59:59.999999 KST. 세션 상태 전이표(정본, `SessionStateTableTest`가 코드 표와 양방향 전수 대조):

```session-state-table
state,event,result
OPEN,OPEN_VIEW,OPEN
OPEN,IDENTITY_PASS,OPEN
OPEN,IDENTITY_FAIL,OPEN|REVOKED
OPEN,CAPTURE,USED
OPEN,TTL_ELAPSED,EXPIRED
OPEN,REISSUE,REVOKED
OPEN,DOCUMENT_VOID,REVOKED
OPEN,DOCUMENT_SUPERSEDE,REVOKED
OPEN,DOCUMENT_EXPIRE,REVOKED
```

  닫힌 상태(USED·EXPIRED·REVOKED)는 어떤 사건도 받지 않는다(표 밖 = 거부, 세션 불변 — DB GD101 이중화). IDENTITY_FAIL은 실패 횟수가 `identityCheck.maxFailures`에 닿으면 REVOKED(`IDENTITY_FAILED`). TTL 경과는 접근 때 판정해 업무 거부하고 상태 기록은 만료 배치·재발급이 한다. 본인확인은 룰 `identityCheck[channel]`의 수단을 **전부** 통과해야 하고 결과만 남는다(입력값은 어디에도 남지 않는다).
- **채널과 행위(v1.9, 4 계획 승인 Q3)**: 채널 = 서명자에게 도달한 경로(TOUCH_PAD·REMOTE_LINK·PAPER_SCAN·CERTIFIED_ESIGN·**SSO**), `method` = 행위(`DRAWN` 터치 자필·`UPLOADED_SCAN` 종이 스캔·`SSO_APPROVAL` 승인 클릭). 설계사·관리자는 언제나 `SSO`이고 룰 `channels`(고객 채널의 활성·관리자 검토 여부)의 대상이 아니다.
- **효력의 원천은 인증수단이 아니라 증거다(D-10).** 서명 1건의 증거 = 서명 대상 해시 + 서명 행위 데이터(터치 스트로크 또는 스캔 이미지) + 본인확인 결과 + 열람 완료 사실 + 시각·기기·IP + 세션 발급·소비 이력. 전부 `signature`·`audit_log`에 남고 EVIDENCE_ZIP에 묶인다. (v1.9 V8, 승인 Q2) 증거 객체(스트로크·이미지·스캔)는 `signature_evidence`에 1객체 1행으로 남고, 확인서 문서 키로 암호화한다(DB가 같은 확인서의 살아 있는 키만 받는다, GD105 — 문서 키를 파기하면 증거도 읽을 수 없다).
- **TOUCH_PAD**(현장 대면): 설계사 기기에서 고객이 봉인 PDF를 끝까지 열람한 뒤 서명. 본인확인 = 설계사의 대면 확인 체크(설계사 계정에 귀속) + 열람 스크롤 완료. 서명 스트로크(좌표·시각 시퀀스)를 이미지와 함께 저장한다(붙여넣기 이미지와 구분).
- **REMOTE_LINK**(비대면): 고객 연락처로 1회용 링크(`token_hash`만 저장, 만료 `rule.remoteLinkTtlHours`). 기본 본인확인 = **링크 소유(발송 번호 기록) + 생년월일 전체 입력**. 실패 N회 시 세션 폐기. 발송 번호는 `customer_ref.phone_enc`에서만 가져오고 설계사가 임의 번호로 발송할 수 없다.
- **대리 서명 탐지**: 같은 기기 지문·IP에서 서로 다른 고객의 REMOTE_LINK 서명이 반복되거나, 링크 발송 후 비정상적으로 짧은 시간에 서명이 완료되면 `ComplianceFlag(SIGNATURE_DEVICE_REUSE)`를 올린다. 임계치는 룰 데이터. (v1.9, 4 계획 §5) 대상은 **REMOTE_LINK 고객 서명뿐**이다(TOUCH_PAD는 설계사 기기 1대로 여러 고객이 서명하는 것이 정상). 기기 지표 = 같은 지문으로 같은 **KST 달력일**에 서명한 서로 다른 고객 수(이번 포함) ≥ `sameDeviceDistinctCustomersPerDay`, IP 지표 = 같은 식 ≥ `sameIpDistinctCustomersPerDay`(선택 키 — 없으면 끔, 이동통신 NAT, 승인 Q8), 시간 지표 = 발송→서명 초 < `minSecondsFromSendToSign`. 탐지는 서명을 막지 않고, 감사에는 지표·값·임계치만 남긴다(지문·IP 원값 없음).
- **PAPER_SCAN**: 인쇄본 서명 후 설계사가 스캔 업로드. QR로 원본 매칭(해시 접두 검사) 후 서명 레코드 생성, 관리자 확인 강제(이행기 채널, 테넌트가 비활성 가능). (v1.9, 승인 Q5) 룰 `channels` 값은 `{enabled, requiresManagerReview}` 객체 — 활성은 `channels.PAPER_SCAN.enabled`, 관리자 검토는 `channels.PAPER_SCAN.requiresManagerReview`.
- **CERTIFIED_ESIGN**(v2, 테넌트 선택): 인정 전자서명인증사업자 어댑터. 인증서·영수증을 증거에 추가. 법정 요건이 아니라 신원 귀속 강화 옵션이다.
- **AGENT 서명**: 설계사 본인 OIDC 세션에서 확인·서명(터치 서명 또는 승인 클릭, 테넌트 파라미터). 신원 귀속은 SSO에 있다. (v1.9) 채널 `SSO`, 행위는 룰 `agentSignMethod`(`DRAWN`|`SSO_APPROVAL`, 사규 덮어쓰기).
- **MANAGER 확인(D-9)**: 관리자 OIDC 세션에서 확인서 상세를 열람한 뒤 승인. 이 승인 행위를 관리자 서명으로 기록하며(`method=SSO_APPROVAL`), 예외 플래그(산출불가·임시등록·오버라이드·종이 스캔)가 있는 건은 사유 확인 체크가 추가로 필요하다. 관리자 부재 시 사후 확인을 허용하되 `signDeadlineDays` 안에 끝나지 않으면 EXPIRED, 청약 진행 허용 시점은 `gateRequiresManager`(§4.4). (v1.9) 채널 `SSO`. 사유 확인 대상은 그 확인서의 플래그 **전부**(열림·닫힘)이고, 확인한 플래그 ID를 서명 레코드 `acknowledged_flags`에 남긴다(승인 Q9).
- 순서·집합은 데이터: 기본 `CUSTOMER → AGENT → MANAGER`, `managerConfirmMode = REQUIRED`(기본)`|OPTIONAL|OFF`. 협회 면제 건의가 수용되면 데이터 변경만으로 대응한다. (v1.9, 승인 Q11) `OPTIONAL` = PARTIALLY_SIGNED 동안 관리자가 확인할 수 있고 완료 뒤에는 없다(DB도 OPTIONAL의 MANAGER 서명은 signerSet 밖이어도 받는다, GD104). SEQUENTIAL에서 MANAGER가 마지막이면 OPTIONAL은 사실상 기회가 없으므로 테넌트에는 REQUIRED 또는 OFF를 권한다.
- **관리자 서명과 예외 승인은 별개다(Phase 1 심사 확정).** `managerConfirmMode`는 **모든 확인서에 붙는 관리자 서명**(signerSet의 MANAGER)만 다스린다. 산출불가·임시등록·검증 오버라이드의 **예외 승인**은 서명이 아니라 별도의 검토 기록이며 `managerConfirmMode`와 무관하게 항상 필요하다. 승인 역할은 룰 데이터 `exceptionApproval: { "role": "MANAGER" }`(GLOBAL 전용, `tenantOverridable`에 넣을 수 없음 — 스키마가 거부). 따라서 OFF 테넌트에서 관리자는 문서마다 서명하지 않지만 예외 건은 승인한다(`POST /api/v1/reviews/{id}/confirm`, §7). 예외 승인은 `compliance_flag.resolution` + `audit_log`에 남는다.
- 완료 시 서명 이미지·증거를 합성한 SIGNED_PDF와 증거 패키지(EVIDENCE_ZIP: canonical JSON, PDF, 서명 레코드·스트로크, 본인확인 결과, 스냅샷, 룰 버전, 감사 로그 발췌, 앵커 참조, 해시 목록)를 생성·보관한다.
- **서명본 PDF(v1.9, 3B 수용심사 §3-2)**: 봉인 PDF 원본 바이트 뒤에 서명 외관 페이지(역할·경로·방법·서명 시각·본인확인 결과·서명 이미지 표, 원본 PDF SHA-256 — 문구는 서식 `layout.signaturePage`)를 **증분 갱신**으로 붙인다. 원본은 서명본의 바이트 접두라서 `pdf_hash`로 서명본 안의 원본을 언제나 다시 확인할 수 있다. **암호학적 PAdES 서명이 아니다** — 증거력은 봉인 체인과 증거 패키지에 있다. 결정론은 봉인 PDF(§6.4 7항)와 같은 방식이고 지점이 하나 더 있다: ① 서명 페이지는 같은 구성(PDF/A-2b, 동봉 폰트·ICC)으로 만들어 **한 번 저장해 다시 읽은 뒤** 폼 XObject로 복제한다(저장 전 복제는 폰트 서브셋이 임베드되지 않는다) ② 정보 `/ModDate`·XMP `ModifyDate`·`MetadataDate` = 마지막 서명 시각(초, +09:00), XMP는 고정 템플릿으로 다시 쓴다 ③ `/ID` 첫 원소는 원본 그대로, 둘째 원소는 문서 ID 시드 = SHA-256(ASCII(pdf_hash) ‖ JCS(서명 요약 — 이미지는 해시만))의 앞 8바이트(시드가 없으면 시각 기반이라 매번 바뀐다). 골든(`signed-01`)의 SHA-256을 로컬에서 만들고 CI가 같은 값을 내야 하며, CI `pdfa-verify`가 서명본 골든도 veraPDF로 검사한다.
- **증거 패키지(v1.9, 4 계획 §4)**: `manifest.json`(JCS, 스키마 `contracts/seal/v1/evidence-manifest.schema.json` — 닫힌 객체) 다음에 경로 순으로 `audit.jsonl`(이 확인서 대상 감사 행, seq 순, `entry_hash` 포함 — 완료 감사 행 직전까지, 매니페스트 `toSeq`가 경계), `canonical.json`, `disclosure-signed.pdf`, `disclosure.pdf`, `signatures/{순번}-{역할}.json`(결과·시각·기기·IP·두 해시·세션·열람 증거·사유 확인 플래그·종이 대조). 매니페스트 `files`가 나머지 엔트리 전부의 해시·길이를 경로 순으로 담아 매니페스트 해시가 패키지를 묶는다. **스트로크·이미지·스캔 원본은 넣지 않고** 해시만 둔다. 앵커 참조는 Phase 5 전까지 `null`. (v1.11, 5 계획 §8.1) `anchor` = 완료 트랜잭션에서 읽은, 그 시점에 이미 있던 그 테넌트의 최신 일일 앵커 `{anchorSeq, anchorDate, leafHash, sealChainSeq, auditSeq}`(없으면 `null`). 스키마는 추가형이라 `null`도 계속 유효하다. 패키지는 다시 만들지 않으며, 이후의 증명은 영수증 내보내기가 잇는다. ZIP은 STORED(Deflate 출력은 플랫폼 zlib에 따라 다를 수 있다), 엔트리 DOS 시각 1980-01-01 00:00:02(00:00:00은 JDK의 "1980 이전" 표지라 시스템 시간대로 계산한 확장 타임스탬프가 붙는다), extra 필드·주석 없음 — 같은 입력이면 어느 환경에서든 같은 바이트다. 패키지 검증기는 저장소 없이 매니페스트·엔트리 해시를 다시 확인한다.
- **서명 유스케이스(v1.9, 4 계획 §7)**: 세션·본인확인은 `SignSessionService`, 서명 수집·완료는 `SignService`(둘 다 확인서 로더·명령 실행기를 함께 쓰므로 `workflow.disclosure`), 포트·기록 형식은 `workflow.sign`.
  - **잠금 순서**: 확인서 행 → 세션 행(토큰 해시로 세션을 잠그지 않고 찾은 뒤 확인서를 잠그고 세션을 잠근다). 계획 §7.1의 "세션 → 확인서"를 뒤집었다 — 무효·정정·만료는 확인서를 잠근 뒤 세션을 취소하므로 반대 순서면 교착이 생긴다(V8 머리말의 잠금 순서와 같은 방향).
  - **토큰 경로 거부**: 형식 오류·없는 테넌트·모르는 토큰·닫힌 세션·TTL 경과는 전부 `SignTokenRejected` 하나다(승인 B2). 사유 코드는 감사 `SIGN_SESSION_DENIED`에만 남기고(별도 트랜잭션), 접두의 테넌트 행이 없으면 남기지 않는다(감사 로그에는 테넌트 외래 키가 없다 — 위조 접두로 없는 테넌트 이름의 행을 만들 수 없게). 그 밖의 서명 검사는 업무 거부 코드(`SignRejection`: 채널·본인확인·순서·해시·기한·서명자 집합·중복·담당 설계사·서명 방식·관리자 확인 OFF·사유 확인 누락·종이 대조·검토 역할)를 단락 없이 전부 모아 `DISCLOSURE_REJECT` 1행에 싣는다.
  - **서명 시각**: 확인서마다 엄격히 증가한다 — max(시계를 µs로 자른 값, 직전 서명 + 1µs). 같은 시각 두 서명은 저장 뒤 순서가 정해지지 않고 여러 인스턴스의 시계 차이는 뒤 서명을 앞 시각으로 만들 수 있다(확인서 행 잠금이 서명을 직렬화하므로 이 시각이 커밋 순서다). 애그리게이트도 엄격 증가를 불변식으로 지킨다.
  - **원격 링크**: REMOTE_LINK 토큰은 설계사에게 돌려주지 않는다. 커밋 뒤 별도 트랜잭션에서 번호를 복호화(감사 `CUSTOMER_PHONE_READ`, 목적 REMOTE_LINK, 참조 = 세션 ID)해 `NotifyPort.sendSignLink(번호, 토큰)`로 보내고 발송 시각을 1회 기록한다(번호가 없으면 보내지 않고 사실만 남긴다). 링크 URL은 배포 설정이라 통지 구현이 만든다.
  - **본인확인 기록**: 서명 레코드 `identity_check`는 그 채널 룰이 요구한 수단의 통과 결과이고 `at`은 서명 시각이다(시도별 시각·실패는 감사 `SIGN_IDENTITY_CHECK`). PAPER_SCAN의 수단은 룰 데이터 `identityCheck.PAPER_SCAN = [AGENT_FACE_TO_FACE]`(담당 설계사가 대면으로 받은 종이 서명임을 확인)다.
  - **완료**: COMPLETE 단계 검증이 **전부 통과**(완료에는 승인 경로가 없으므로 오버라이드 가능 실패도 막는다)하고 열린 `PAPER_SCAN_REVIEW`가 없을 때만이다. 서명 외관의 이미지는 DRAWN 서명만이다(종이 스캔·승인 클릭은 이미지 없이 방법 표기). 완료 트랜잭션은 봉인과 같은 제한 시간을 쓴다(증거 객체·산출물을 올리므로 잔여물 정리 유예의 전제가 같다).

### 6.6 정정과 무효

- **SUPERSEDE**: 봉인 후 오류 발견 시 새 버전 DRAFT를 복제 생성(`supersedes_id`), 이전 버전은 `SUPERSEDED`로 표시되고 그대로 보관된다. 서명은 이전 버전에 남고 새 버전은 다시 받는다. 사유 필수, 감사 기록. (v1.8) 봉인 이후 상태에서만, 행위자 역할 = 고정 룰의 `exceptionApproval.role`(아니면 업무 거부 `ROLE_REQUIRED`, 인가 자체는 Phase 6). 새 버전 = 버전 + 1, 같은 고객·설계사·상품군·상담일, 항목 **입력만** 복제(등급 복사본·추천사유는 복제하지 않는다 — 재산출·재입력, 절대 규칙 7). 룰·서식은 **원본 상담일로 다시 해석**해 고정한다(원본 고정 뒤 소급 배포가 있었다면 새 버전은 새 룰). 원본 산출물·키·잠금은 그대로. 사유 텍스트는 감사에 SHA-256·길이만(자유 텍스트 — 개인정보가 섞일 수 있다; 저장 컬럼은 Phase 4 질문). (v1.9 V8, 3B 수용심사 §2-2) 사유 = 고정 룰 `supersedeReasons`의 코드(닫힌 목록) + 선택 텍스트(`requiresText` 코드는 필수, 길이 ≤ `lifecycleReasonTextMaxLength`)이고 원본 행 `supersede_reason_code`·`supersede_reason_text`에 한 번 쓴다(GD100). 감사에는 코드와 텍스트 길이만. 감사: 원본 `DISCLOSURE_SUPERSEDE`, 새 버전 `DISCLOSURE_CREATE`(`supersedesId`).
- **VOID**: 상담 취소 등. 사유 필수, `SEALED` 이후 무효는 관리자 승인. 무효 문서도 삭제하지 않는다(보존기간까지). (v1.8) 가변 상태는 설계사, 봉인 이후는 `exceptionApproval.role`. 봉인 후 무효는 번호·봉인 컬럼·산출물·잠금을 유지한다(번호 재사용 없음, 승인 Q8). 사유는 `void_reason` 컬럼에, 감사에는 길이만. (v1.9 V8) 사유 = 고정 룰 `voidReasons` 코드 + 선택 텍스트, `void_reason_code`·`void_reason_text`에 한 번 쓴다(GD100). 감사에는 코드와 텍스트 길이만. 업무 거부 `REASON_CODE_UNKNOWN`(목록 밖)·`REASON_TEXT_REQUIRED`·`REASON_TEXT_TOO_LONG`. V8 이전 행은 코드 `MIGRATED_V8`(옛 무효 원문은 텍스트로 옮기고, 정정은 원문이 저장된 적 없다).
- **REBASE(v1.8, 3A 수용심사 §3-8)**: `RULE_SUPERSEDED_DRAFT` 열린 플래그가 있을 때만(아니면 업무 거부 `REBASE_NOT_ALLOWED`). 상담일 재해석 결과를 새로 고정하고 스냅샷·추천사유를 버린다. 새 룰의 COMPARE 검증 통과면 COMPARED, 아니면 DRAFT(승인 Q3). 옛 승인은 지우지 않으며 룰 버전 귀속으로 효력을 잃는다. 플래그는 `REBASED`로 닫힌다. 고정 룰 로드는 "상담일에 시작해 있었던 버전"만 요구한다 — 소급 GLOBAL 배포가 고정 버전의 `apply_to`를 상담일 이전으로 닫아도 그 초안은 판정·거부·재기준을 할 수 있다(막다른 상태 금지).
- **플래그 해소(v1.8, 3A 수용심사 §3-7)**: 무효·정정은 열린 `VALIDATION_OVERRIDE`·`RULE_SUPERSEDED_DRAFT`를 `SUPERSEDED_BY_DOCUMENT_STATE`로 닫고, `GRADE_INCONSISTENT`(엔진 이상 신호)는 남긴다. 봉인은 `APPROVED`·`RESOLVED_AT_SEAL`, 재기준은 `REBASED`. 해소마다 감사 `FLAG_RESOLVE`. (v1.9, Phase 4) 무효·정정·만료는 `PAPER_SCAN_REVIEW`(완료를 막던 검토)도 문서 상태로 닫는다. `IDENTITY_FAILED`·`SIGNATURE_DEVICE_REUSE`·`SIGN_EXPIRED`는 사후 점검 신호라 남긴다.
- **서명 진행 중 무효·정정(v1.9, 4 계획 §7.4, 3B 수용심사 §3-5)**: 같은 트랜잭션에서 그 확인서의 OPEN 서명 세션을 전부 REVOKED(`DOCUMENT_VOIDED`·`DOCUMENT_SUPERSEDED`)로 닫는다(토큰은 그 뒤 같은 거부). 받은 서명은 원본에 남고 새 버전으로 이월하지 않는다 — 새 버전은 봉인 뒤 세션을 새로 발급받는다(정정본에 옛 토큰으로 서명할 수 없다, 세션은 발급 때 원본의 두 해시에 고정돼 있다).
- **만료 배치(v1.9, 4 계획 §7.4)**: `ExpireService.run(asOf)` — SEALED·PARTIALLY_SIGNED 확인서마다 트랜잭션 1개로 다시 잠가 판정 시각이 서명 기한 끝(봉인일 KST + 고정 룰 `signDeadlineDays`의 23:59:59.999999 KST)을 지났으면 EXPIRED, OPEN 세션 전부 REVOKED(`DOCUMENT_EXPIRED`), 플래그 `SIGN_EXPIRED`, 감사 `DISCLOSURE_EXPIRE`(이전 상태·기한·판정 시각·닫은 세션). 받은 서명은 남고 만료 문서에는 더 서명할 수 없다(상태표). 이어서 TTL이 지난 OPEN 세션을 EXPIRED로 기록한다(접근 때는 거부만 — 세션 상태표). 문서 사건(무효·정정·만료)으로 닫히는 세션은 TTL이 지났어도 REVOKED(사건 사유)다 — 세션 만료는 서명 기한 끝을 넘지 않으므로 문서 만료 때 열린 세션은 언제나 TTL이 지나 있고, 닫힌 원인은 문서다. 재발급만 TTL이 지난 세션을 EXPIRED로 기록한다. 판정 시각은 운영자가 정하며(CLI `disclosure expire --as-of`, 기본 = 시계) 감사에 실제 시각과 함께 남는다. 다시 돌리면 NOOP. 스케줄 등록은 Phase 6.
- 어떤 경로로도 봉인된 본문은 바뀌지 않는다(§5 불변식). "삭제"라는 동작은 시스템에 존재하지 않고, 보존기간 도래 후 파기 배치만 있다(§9). (v1.10) 불변은 보존기간 중의 약속이다. 보존기간이 끝난 확인서는 파기 함수만이 지정 개인정보 컬럼을 NULL로 바꾸며 번호·상태·해시·시각·체인은 묘비로 남는다.

### 6.7 감사 로그와 체인

- 모든 상태 전이, 항목 편집, 엔진 호출, 검증 결과(실패 포함), 열람·인쇄·다운로드·내보내기, 서명, 관리·준법 행위, 룰 승인이 `audit_log`에 기록된다. 업무 트랜잭션과 **같은 트랜잭션**.
- 테넌트별 단일 시퀀스 + 해시체인. 일 1회 `audit_anchor`에 헤드 해시를 고정하고, **외부 타임스탬프(RFC 3161 TSA) 어댑터를 v1에 포함해 기본 활성**으로 둔다(어떤 전자서명도 법정 추정력이 없으므로 "그 시점에 그 문서가 존재했다"는 제3자 증거가 서명 효력을 떠받친다, §1.5). TSA 사업자 선택·비용은 테넌트 몫이며 미설정 시 내부 앵커만 남긴다.
- **일일 앵커(v1.11, 5 계획 §2·§8.1, 4 수용심사 결정 1~3)**: 위 문장의 `audit_anchor`·"테넌트 몫"은 다음으로 대체됐다. 매일(KST) 테넌트마다 앵커 레코드(봉인 체인 머리·감사 체인 머리, `anchor` 테이블)를 만들고, 그 날짜의 영수증 없는 앵커 전부를 잎으로 **머클 루트 하나**를 만들어 TSA 토큰을 받는다(TSA는 일일 루트에만 — 플랫폼 단위, §14 #4). 각 테넌트에는 자기 잎의 경로와 루트·토큰을 담은 영수증(`anchor_receipt`)만 쓴다 — 테넌트 없는 배치 테이블은 없다. TSA가 실패해도 봉인·서명·완료는 막지 않고 앵커만 남으며, 다음 실행이 같은 날짜의 둘째 배치로 잇는다. 규격의 정본은 아래 블록이고 `MerkleSpecTableTest`가 코드 상수와 양방향 대조한다.

```merkle-spec
key,value
hash,SHA-256
leafPrefix,00
nodePrefix,01
padPrefix,02
padLabel,ga-disclosure/anchor/pad/v1
leafInput,JCS(anchorDate|anchorSeq|auditHead|auditSeq|sealChainHead|sealChainSeq|tenantId|v)
recordVersion,1
leafOrder,leafHashUnsignedAscending
depthKey,anchoring.treeDepth
defaultDepth,16
maxDepth,24
maxLeaves,2^depth
pathOrder,leafToRoot
pathSide,bit(leafIndex;level)=0 -> sibling right
imprint,root
```

  잎·노드·패딩의 접두가 서로 달라 잎을 노드로·노드를 잎으로 내미는 두 번째 원상 공격이 성립하지 않는다. 깊이가 고정이라 경로 길이는 테넌트 수와 무관하다. **한계**: 패딩이 상수라서 경로의 형제 중 전부-패딩 부분트리 상수의 위치로 점유 슬롯 수의 **상한**을 추정할 수 있다 — 정확한 수와 다른 테넌트의 잎·머리 값은 드러나지 않는다. DB는 잎(V9 GD110)과 영수증 경로 → 루트(GD111)를 같은 식으로 다시 계산한다.
- **앵커 배치(v1.11, 5 계획 §8.1, 승인 Q12)**: `AnchorJob.run(테넌트 목록, 날짜 = 오늘 KST, 행위자)`. 테넌트 목록은 CLI가 테넌트 디렉터리에서 준다(workflow는 compliance를 모른다).
  - **A단계**: 테넌트마다 REPEATABLE READ 트랜잭션 하나에서 진행한다. 그 날짜 앵커가 있으면 NOOP이고, 지난 날짜를 뒤늦게 고정하지 않는다(`DATE_NOT_AFTER_LATEST`, GD110도 거부). 같은 스냅샷에서 봉인 체인 머리와 감사 머리를 읽어 앵커를 쓰고 감사 `ANCHOR_CREATED`(대상 `ANCHOR`, ID = 날짜)를 남긴다. 그 행의 seq가 `audit_seq + 1`이다. 스냅샷 뒤 다른 커밋과 부딪히면 감사 seq 유일성 위반(23505) 또는 직렬화 실패로 롤백되고, 그 테넌트만 처음부터 다시 한다. 상한은 5회이고 보고서 `retries`에 센다. 충돌 번역은 저장소 계층이 번역한 스프링 예외로 한다(`java.sql` 비참조).
  - **B단계**: 영수증 없는 앵커 전부(지난 날짜 포함)를 날짜별로 묶어 트리를 만들고 TSA에 보낸 뒤, 테넌트 트랜잭션마다 영수증과 `ANCHOR_RECEIPT_STORED`를 쓴다. 깊이는 각 테넌트가 그 날짜에 해석한 GLOBAL `anchoring.treeDepth`이다. 테넌트끼리 다르면 그 날짜는 `TREE_DEPTH_DISAGREES`(fail-fast)이고, 잎이 넘치면 `TREE_FULL`, 룰을 해석하지 못한 테넌트는 `RULE_UNRESOLVED`로 빠진다.
  - 보고서는 `created`·`unchanged`·`retries`·`batches[]`(날짜·배치 ID·루트·깊이·잎 수·`second`·genTime)·`receipts`·`failures[]`(단계·테넌트·날짜·코드)이다. `second`는 이 실행 전에 만들어져 고정되지 못한 앵커를 담은 배치이다.
- **TSA(v1.11, 5 계획 §3, 4 수용심사 승인 ①)**: 포트 `TimestampAuthorityPort`는 DER `TimeStampReq` → DER `TimeStampResp` 전송만 한다(BC 타입 없음). 구현은 로컬 스텁(`LocalStubTsa`)과 HTTP(`HttpTimestampAuthority`, `application/timestamp-query`) 두 가지다. 요청 생성과 응답 수락은 `TimestampClient` 한 곳이 한다.
  - 요청: imprint `{SHA-256, 루트}`(다시 해시하지 않는다), 63비트 양수 nonce(`NonceSource` 포트), `certReq=true`, 정책 OID 없음.
  - 수락 조건: 상태 granted(·withMods), 토큰 nonce = 요청 nonce, `TimestampVerifier`가 VALID. 어긋나면 `TimestampFailure`이고 영수증을 쓰지 않는다.
  - 검증(`TimestampVerifier`, 순서대로): imprint = 루트 → 서명자 EKU = `id-kp-timeStamping` 하나, critical → CMS 서명·ESSCertID(v2) 결속·genTime 시점 인증서 유효 → 설정된 신뢰 앵커로 PKIX 경로(폐기 확인 끔, 기준 시각 genTime). 앞의 셋이 어긋나면 `INVALID`, 신뢰 앵커가 없거나 경로가 닿지 않으면 `UNTRUSTED`(통과 아님).
  - 저장된 토큰의 nonce는 보고만 한다. 요청 nonce는 따로 저장하지 않는다.
  - 일련번호·nonce는 수로 다루지 않고 ASN.1 내용 옥텟의 소문자 hex로만 옮긴다. 수용·검증 쪽은 BigInteger를 쓰지 않는다. BC 생성 API가 BigInteger를 요구하는 스텁만 허용 목록에 있다.
  - BC 보안 제공자는 전역 등록하지 않고, 서명·경로 검증은 JCA 기본 제공자로 한다.
  - `org.bouncycastle..` 참조는 `audit.tsa`·`audit.tsa.stub`에서만 허용한다(ArchUnit). 버전은 1.86으로 카탈로그와 락에 고정하고 서드파티 목록(`docs/third-party.md`)에 둔다.
  - 스텁은 ECDSA P-256 자체 서명 인증서를 쓴다(EKU timeStamping critical, KeyUsage digitalSignature critical). genTime과 CMS signingTime은 모두 주입된 `Clock`에서 온다.
  - 스텁 키 수명: 테스트는 실행마다 새로 만든다(유효 1일). 데모는 저장소 밖 `tsa-stub.p12`(권한 600, 비밀번호는 비밀이 아니다)를 처음 한 번 만들고 재사용하며, 신뢰 앵커는 `tsa-trust.pem`으로 내보낸다(승인 Q11).
- **체인 걷기(v1.11)**: `verify`는 체인을 커서로 흘려 읽는다. `AuditChainWalker`·`SealChainWalker`는 갭·단절·내용 변조를 모으고, 미리 지정한 checkpoint seq(앵커의 `auditSeq`·`sealChainSeq`)에서 **다시 계산한** 머리만 기억해 앵커와 대조한다. 단절 뒤에는 저장된 해시로 이어 걸어 같은 단절을 한 번만 보고한다. 봉인 체인 식은 `SealChain.next` 하나를 봉인(생산)과 검증·앵커(소비)가 함께 쓴다. 영수증 구간은 직전 앵커의 seq·머리에서 시작한다.
- `verify --tenant X [--from-seq]`: 체인 전 구간 재계산, `document_artifact` 해시와 스토리지 실물 대조, 확인서 `chain_hash` 연속성 검사. 불일치 → `ComplianceFlag(CHAIN_BROKEN)` + 운영 알림.
- **검증(v1.11, 5 계획 §4·§8.2~8.4, 4 수용심사 결정 4, 승인 Q1·Q13)**: 위 줄은 다음 두 명령과 영수증 내보내기로 구체화됐다.
  - **보고서**: 스키마는 `contracts/verify/v1/verify-report.schema.json`(닫힌 객체), 직렬화는 JCS이다. 결과 MATCH는 종료 0이고, 발견이 하나라도 있으면 MISMATCH로 종료 2이다. 입력 오류(손상 ZIP·패키지 아님·영수증 스키마 위반·신뢰 앵커 형식)는 보고서 없이 `{code, message}`로 종료 3이다.
    - 발견 코드는 지시문 13개에 `SIGNATURE_BINDING_MISMATCH`·`AUDIT_ENTRY_MISMATCH`·`DESTRUCTION_UNAUDITED`·`RECEIPT_NOT_COVERING`을 더했고, 스키마 열거와 코드 열거를 테스트가 대조한다.
    - 결론은 `existedBefore`(외부 증명 상한 = 덮는 토큰의 genTime)와 `sealedAfter{anchorDate, sealChainSeq, recordedAt}`(자체 기록 하한)이다. 계획의 `existedAfter`라는 이름은 외부 증명처럼 읽혀 바꿨다(승인 Q13의 약한 문장). `tsaTrusted`도 함께 둔다.
    - 고정 문장은 `Statements` 상수이다.
  - **`verify package`**(`disclosure-audit`): 입력 바이트만 받는다. 자체 ZIP 리더와 계약 스키마로 직접 검증하며, 생산자(seal)·workflow·infra·DB·네트워크·파일 시스템·`javax.crypto`·스텁·HTTP TSA에 의존하지 않는다(ArchUnit).
    - 패키지 검사: 매니페스트 스키마, 엔트리 해시·길이·경로 순(빠진·목록에 없는 엔트리), canonical JCS 재계산, 봉인 PDF가 서명본의 접두인지, 서명 레코드(매니페스트·파일) 두 해시 결속, 감사 발췌 행별 `entry_hash` 재계산(연속은 보지 않는다)과 요약(행 수·from·to·마지막 해시).
    - 영수증 검사: 범위(테넌트·확인서·번호·체인 순번), 덮음, 직전 앵커 = 매니페스트 `anchor`이면서 문서보다 앞섬, 봉인 체인 구간(직전 머리 → 문서 행 = 매니페스트 해시 → 덮는 머리), 잎(레코드에서 다시) → 경로 → 루트, 토큰(신뢰 앵커가 없으면 `TSA_UNTRUSTED`).
    - 결론은 발견이 0일 때만 낸다. 영수증이 없으면 "내부 정합성만 확인. 존재 시각·체인 연속은 영수증 또는 verify tenant가 필요하다."를 출력한다. 영수증이 있으면 감사 연속은 verify tenant만 확인한다는 문장을 덧붙인다.
  - **영수증 내보내기**(`ReceiptExporter`, 스키마 `anchor-receipt-export.schema.json`): 증거 패키지를 감사되는 열람으로 읽어 매니페스트의 `chainSeq`·`audit.toSeq`·`anchor`를 얻는다. 내용은 다음과 같다.
    - `covering` = 문서 `chainSeq` 이상이면서 `auditSeq ≥ toSeq`인 첫 **고정된** 앵커와 그 영수증. 없으면 `NOT_YET_COVERED`.
    - `previous` = 매니페스트 `anchor`(문서보다 앞설 때만).
    - `sealChain` = previous 다음 … covering(해시만, 묘비 포함).
    - 감사 `ANCHOR_RECEIPT_EXPORTED`(내보낸 바이트 SHA-256)를 남긴다.
  - **`verify tenant`**(`TenantVerifier`, workflow 조정): REPEATABLE READ 한 스냅샷에서 감사·봉인 체인을 페이지로 흘려 읽고, 앵커 대조용으로는 checkpoint 머리만 다시 계산해 기억한다.
    - 순서: 감사 체인 → 봉인 체인(머리 도달) → 연도별 채번(1부터 빈틈·중복 없음) → 객체(산출물·서명 증거: 있음·복호화·평문 해시, 파기 건은 버전·마커 0) → 앵커(잎·두 머리) → 영수증(경로·토큰) → 미고정 기간(`verify.unstampedAnchorAlertDays`, KST 날짜).
    - 쓰기는 별도 트랜잭션 하나이다. `VERIFY_RUN`(보고서 해시·코드별 수)을 남기고, 무결성 불일치면 `CHAIN_BROKEN` 플래그를 올린다. 대상은 끊긴 지점의 확인서마다이다. 확인서를 정할 수 없으면 `disclosure_id NULL`로 그 지점을 대상으로 한다: 감사 체인은 `AUDIT_LOG`·seq, 앵커·영수증은 `ANCHOR`·앵커 순번, 그 밖은 `TENANT`(5 계획 §1.6).
    - `ANCHOR_UNSTAMPED`·`TSA_UNTRUSTED`는 운영·설정 신호라 종료 2지만 플래그를 올리지 않는다.
    - `DESTRUCTION_UNAUDITED`는 파기 감사가 생기는 Phase 5 8단계에서 더한다.

### 6.8 준법 점검

- **대상 계약 판정** `subjectRule`(데이터): 테넌트 `largeGa`, 상품군 대상 여부(자동차 등 제외), 체결일 ≥ 룰 시행일, 채널 조건. `subject_policy`는 엔진 `PolicyEventObserved`/청약 링크/CRM에서 채운다.
- **징구율** = 완료 확인서가 연결된 대상 계약 / 대상 계약 (기간·조직·설계사·상품군 축). 정의는 룰 데이터(`kpi.collectionRate`)이며 화면에 정의 버전을 표기한다.
- **큐**: MISSING(대상인데 확인서 없음), LATE(체결일 이후 완료), GRADE_UNAVAILABLE, TEMP_PRODUCT, VALIDATION_OVERRIDE, EXPIRED, CHAIN_BROKEN. 각 플래그는 담당·기한·해소 기록.
- **리포트**: 협회·당국 점검 대응용 내보내기(기간·조직별 징구율, 예외 목록, 표본 확인서 증거 패키지). 내보내기는 감사 기록 + 워터마크.
- **룰 승인 흐름**: DRAFT → 준법 승인(APPROVED) → 시행일 도래 시 ACTIVE. 시행일 전 미승인 룰이 있으면 운영 경보. 규제(GLOBAL) 룰은 번들 배포 시 APPROVED로 복제된다. 배포·승인·활성화 배치·번들 대사는 `disclosure-compliance`의 서비스이며 전부 `audit_log`에 같은 트랜잭션으로 남는다(Phase 1은 운영자 CLI, 인가·스케줄은 Phase 6).

### 6.9 청약 게이트

`gateMode`(BLOCK/WARN/OFF)는 테넌트 파라미터. 본 시스템은 답만 하고 막는 것은 호출자다(D-8). 응답에는 룰 버전을 포함해 "왜 필요/불필요로 판정됐는지"가 남는다.

## 8. 화면 설계 (모바일 우선, 텍스트 와이어)

**설계사 흐름 (5단계, 상단 스텝 표시)**

1. **고객·상품군**: 고객 선택/신규(이름·연락처 최소) · 상담일 · 유사상품군(생/손보 탭) · 정본 모드 배지(SELF/ASSOC)

## 9. 보안·개인정보·멀티테넌시

- **인증·인가**: 포털과 동일 OIDC. 고객은 1회용 토큰(서명 세션)만. 설계사 self 조회는 `agent_id` 소유 확인서만, 관리자는 `org_path` 접두, 준법은 테넌트 전체(전 건 `VIEW` 감사).
- **테넌트 격리 3중**: 컨텍스트·아키텍처 테스트·RLS. 오브젝트 스토리지 키도 `tenant_id/` 접두 + 버킷 정책.
- **개인정보 최소화**: 고객 이름·연락처·생년월일은 컬럼 암호화, 봉인 본문(canonical·PDF)에는 고객 **성명만**(§6.4 8항, 산출물은 테넌트 키로 암호화 저장). 개인정보는 CLI 인자·환경변수·셸 스크립트 인라인으로 전달하지 않는다 — 파일(허구 데이터) 또는 API로만(데모 고객은 `customers.json`을 `RegisterCustomer`로 등록). 주민번호·주소·계좌는 수신하지 않는다. 화면·로그는 마스킹. 서명 이미지는 개인정보로 취급(암호화 저장, 열람 감사).
- **고객 필드 암호화(Phase 2 확정)**:
  - 알고리즘 AES-256-GCM(JCA, 추가 라이브러리 없음), 랜덤 96비트 nonce, 128비트 태그. 저장 형식 `0x01(형식 버전) ‖ nonce(12) ‖ ciphertext‖tag`(DB CHECK가 머리·최소 길이를 검사).
  - AAD = JCS 정규 JSON `{column, customerRef, keyId, table, tenantId, v:1}`의 UTF-8. 암호문을 다른 테넌트·행·컬럼으로 옮기거나 `enc_key_id`를 바꾸면 태그 검증이 실패한다.
  - 평문 정규화: 이름 NFC·trim(제어문자 거부), 전화 숫자만(`01[016789]…`), 생년월일 `yyyy-MM-dd`. 파싱 오류 메시지에 입력값을 넣지 않는다.
  - 키 계층: 테넌트별 DEK(256비트)를 KEK로 감싸 `customer_data_key`에 저장(감싸기 AAD = `{kekId, keyId, tenantId, v:1}` — DEK를 다른 테넌트로 옮기면 풀리지 않는다). 포트 `KeyProviderPort`(`currentKekId`·`wrap`·`unwrap`): 운영은 KMS 어댑터(암호화 컨텍스트 = 위 AAD), 개발·테스트는 `LocalFileKeyProvider`(저장소 밖 KEK 파일, 권한 600이 아니면 거부, `ga.crypto.local-kek-file`, CLI `crypto init-kek`). 첫 등록 시 DEK를 만든다.
  - 순환(`customer rekey`): ① 새 DEK ACTIVE, 구 키 RETIRED(한 트랜잭션) ② 구 키 행을 배치로 복호화→재암호화 ③ 남은 행 0이면 구 키 DESTROYED(`wrapped_key` NULL). 중단되면 재실행이 이어받는다. 단계마다 감사(`CUSTOMER_KEY_ROTATE`·`CUSTOMER_REKEY`·`CUSTOMER_KEY_DESTROY`).
  - JCA 사용은 `infra.crypto` 패키지뿐(ArchUnit).
- **`Sensitive<T>`(Phase 2 확정)**: 도메인에서 고객 필드는 `Sensitive<CustomerName|PhoneNumber|BirthDate>`로만 다닌다. record가 아니고 `Serializable`이 아니며 게터가 없다. `toString`은 `Sensitive[FIELD:****]`(값 전부 가림), `equals`는 상수 시간 비교다. 원문은 `reveal(Function)`로만 꺼내며 호출할 수 있는 패키지는 FQN 허용 목록(`domain.pii`의 생년월일 대조, `infra.crypto`, `rules.pii`의 `MaskedView`)으로 제한한다(ArchUnit). 애플리케이션 JSON 매퍼는 `Sensitive`와 PII 값 타입의 직렬화를 거부한다. 생년월일 본인확인은 `BirthDate.matches`의 상수 시간 비교로 결과만 반환한다.
- **마스킹(Phase 2 확정)**: 화면용 부분 마스킹(예: 홍*동, 010****1234)은 룰 데이터 `masking`(필드별 `keepFirst`·`keepLast`·`maskChar`, 부록 D)이고 `tenantOverridable`로 사규가 덮어쓸 수 있다. 코드 포인트 단위로 적용하며, 가릴 글자가 없으면 전부 가린다. 실값은 §14 #12.
- **평문 누출 검사**: 모든 테스트 출력(결과 XML·표준 출력·로그)을 평문 센티널로 스캔하는 빌드 태스크(`scanPlaintextLeaks`)와, DB 전체 덤프·PostgreSQL 서버 로그를 스캔하는 통합 테스트(`PlaintextLeakScanIT`)가 있다. 한 건이라도 나오면 실패한다.
- **고객 조회 감사**: 등록 `CUSTOMER_REGISTER`, 열람 `CUSTOMER_VIEW`, 발송용 연락처 읽기 `CUSTOMER_PHONE_READ`(목적·호출자 참조 ID). 감사 detail에 PII를 넣지 않는다.
- **봉인 산출물 암호화(v1.8, 3A 수용심사 §3-5)**: 확인서마다 DEK(256비트)를 새로 만들어 테넌트 KEK로 감싼 뒤 `document_key`에 둔다(키 ID `DOC-{32 hex}`, 문서당 1개 — Phase 4 SIGNED_PDF·EVIDENCE_ZIP도 같은 키). 산출물은 클라이언트 측 AES-256-GCM, 형식은 고객 필드와 같고(`0x01 ‖ nonce ‖ 암호문 ‖ tag`, 길이 = 평문 + 29) AAD = JCS `{disclosureId, kind, tenantId, v:1}` — 다른 확인서·종류로 옮긴 바이트는 풀리지 않는다. `document_artifact.sha256`은 **평문** 해시(체인·열람 대조), `cipher_sha256`은 저장 바이트의 해시이고 객체 키 = `{tenant}/{disclosure}/{kind}/{cipher_sha256}`(버킷 목록에 평문 해시가 없다, 승인 Q4). 열람은 복호화 후 평문 해시가 기록과 같을 때만 내주고(`ARTIFACT_VIEW`), 키 파기·해시 불일치·풀리지 않는 객체는 거부하며 그것도 감사한다(`ARTIFACT_VIEW_DENIED`). 파기 = 감싼 키 NULL — 소유 롤의 `ga_shred_document_key`만(EXECUTE 부여 없음, Phase 5 파기 배치 롤이 받는다). SSE-KMS 테넌트 키 대안은 문서 단위 파기가 불가능해 기각. (v1.9, 3B 수용심사 §3-4·4 계획 승인 Q2) **서명 증거 객체**(스트로크·이미지·스캔)도 같은 문서 DEK로 암호화하고 AAD = JCS `{disclosureId, kind, signatureId, tenantId, v:1}` — 다른 서명·종류·확인서로 옮긴 바이트, 산출물 AAD로는 풀리지 않는다. 기록은 `signature_evidence`(1객체 1행), 객체 키 = `{tenant}/{disclosure}/SIG/{signature}/{kind}/{cipher_sha256}`. 열람(`viewEvidence`)은 산출물 열람과 같은 순서·같은 감사이고 상세에 서명 ID가 붙는다. 문서 키를 파기하면 증거도 읽을 수 없다(문서 단위 crypto-shredding이 서명 증거까지 덮는다). 완료 때의 SIGNED_PDF·EVIDENCE_ZIP은 봉인 때 만든 키를 다시 쓴다(`encrypt` — 새 키를 만들지 않는다).
- **잔여물 정리·재적용(v1.8)**: `artifacts gc`는 테넌트 접두 아래에서 참조 행이 없고 마지막 수정이 `시계 − 유예`(기본 24시간)보다 오래된 객체만 지운다(`ARTIFACT_GC`). 유예는 봉인 트랜잭션 제한(기본 60초)보다 커야 한다 — 진행 중인 봉인이 올린 객체는 언제나 그 제한보다 젊다(제한을 넘기면 다음 DB 문장이 실패해 롤백). 잠긴 객체는 저장소가 삭제를 거부한다. `artifacts reconcile`은 `retention_applied_at IS NULL`인 산출물에 봉인 때 정한 기한으로 잠금을 다시 건다(`ARTIFACT_RETAIN`). (v1.9 V8) 대상은 적용 기한(`retention_applied_until`)이 확인서 `retention_until`보다 짧은 산출물까지 넓어진다 — 보존기한이 연장되면 다시 건다(기한은 증가만). 서명 증거 객체도 **같은 코드 경로**다(승인 Q2): 재적용 대상 목록·적용 기록·잔여물 정리의 참조 판정이 `document_artifact`와 `signature_evidence`를 함께 본다(공통 타입 `LockedObject`).
- **보존·파기**: `retention_until` = 완료일(또는 계약일) + `rule.retentionYears`(법정 보존기간은 §14 #3 확인 후 데이터로 설정, 예시값 5년). (v1.11, 5 계획 승인 Q5·Q9·Q10) 보존기간 = `retentionYears`년 + `retentionDays`일 — 앵커마다 같은 산식 하나(`RetentionPeriod`), 합계 ≥ 1일(룰 스키마). 보존기한은 **KST 달력 날짜이고 그 날의 KST 종료까지**다: 객체 잠금은 다음 KST 자정, 파기 적격은 `asOf(KST 날짜) > retention_until`. 보존기한은 봉인 시 정해지고 앵커가 생길 때 연장만 하며, 파기 절차 파라미터(`retention.contractLinkWaitDays`·`customerRef`·`legalHoldReasons`)는 배치 실행 시점의 ACTIVE 룰로 읽고 파기 감사에 그 룰 버전을 적는다. 규제 변경으로 기존 문서의 보존기한을 늘리는 재계산은 별도 명시 작업이다(§14). 도래 시 파기 배치 → 스토리지 객체 삭제 + **해당 문서 데이터 키 파기**(crypto-shredding — 백업에 남은 암호문 사본도 무의미해진다, v1.7) + DB 본문 삭제 + **파기 기록은 감사 로그에 남김**(해시만 잔존). (v1.10, 4 수용심사 승인 ②) "DB 본문 삭제"는 행 삭제가 아니다: 파기 함수가 지정 개인정보 컬럼만 NULL로 바꾸고 번호·상태·해시·시각·체인은 묘비로 남는다(체인·채번·검증이 파기 뒤에도 성립). 파기 감사에는 지운 값의 해시를 남긴다. 지정 컬럼 전수는 Phase 5에서 기계 판독 표로 둔다. 봉인 산출물이 보존기간 동안 성명을 담는 것은 규제가 요구하는 보관 그 자체다. 미체결 상담 확인서의 보존은 §14 #3.
- **불변 저장**: Object Lock(Compliance 모드) 기간 = 보존기간. 운영자도 기간 내 삭제 불가. (v1.8) 버킷은 테넌트 공통 1개(키 접두 `{tenant}/`), Object Lock 활성·버전 관리 Enabled·**기본 보존 규칙 없음**을 저장소 첫 사용 직전에 한 번 확인한다(기본 규칙이 있으면 업로드 즉시 잠겨 커밋 전 잠금 금지가 깨진다). 확인이 실패하면 그 조작이 실패한다 — 저장소를 쓰지 않는 명령(룰 배포·카탈로그 수입 등)과 부팅을 저장소 가용성에 묶지 않으려고 기동 시점이 아니라 첫 사용 시점이다(`VerifiedArtifactStore`). 버킷 생성은 개발·데모 설정(`ga.storage.s3.create-bucket`)에서만 하고 운영 버킷은 인프라가 만든다. 개발·CI 구현은 SeaweedFS(digest 고정, S3 인증 켬, 볼륨 한도를 디스크 크기와 무관하게 고정 — 기본값은 여유 디스크에서 산정돼 CI 러너에서 버킷이 늘면 쓰기가 실패한다)이고 교체 수용 기준은 Object Lock 계약 테스트 5종(잠긴 버전 삭제 거부·우회 헤더 거부·단축 거부·연장 허용·잠기지 않은 객체 삭제 허용). (v1.11, 5 계획 §6·승인 B1) 계약에 다음 항목을 더한다.
  - 삭제는 키의 모든 버전과 삭제 마커를 **버전 ID로** 지운다. 버전 없는 삭제는 없는 키에도 마커를 만들기 때문에(SeaweedFS 4.48 실측) 어댑터가 보내지 않는다. 요청 캡처로 단언하며, 일괄 삭제와 거버넌스 우회 헤더도 보내지 않는다.
  - 없는 키를 삭제하면 아무것도 생기지 않는다.
  - 버전·마커 수(`versionCount`)를 조회할 수 있다. 파기 확인과 `verify tenant`의 `OBJECT_NOT_DELETED`가 쓴다.
  - legal hold는 키의 **모든 버전**에 걸고 푼다. 조회는 모든 버전이 ON일 때만 참이다. 보류 중 삭제는 거부되고, 보존기한이 지나도 보류가 켜져 있으면 거부된다(보류는 보존과 독립).
  - 능력은 `capabilities()`로 명시한다. 미지원이면 호출이 예외이고 조용한 no-op은 없다. 계약은 지원(SeaweedFS)과 미지원 대역 둘 다에 돈다.
  - **통제는 DB 보류(`legal_hold`, 파기 배치가 건너뛴다)이고 저장소 보류는 벨트다.** 이는 지원 여부와 무관하다.
- **서비스 간**: 엔진 호출 서비스 토큰(운영 mTLS — §14 미결정 그대로), 청약 게이트·이벤트 피드는 내부망 한정. 토큰은 256비트 난수이고 엔진은 SHA-256만 보관하며, 회전 겹침 기간에 현재·다음 두 해시를 인정한다(엔진 E3.1). 이 시스템의 보관은 3A에서 `EngineCredentialPort`(배포 설정) → Phase 8에서 Phase 2 볼트(테넌트 DEK, AAD = `tenant_id`·`engine_token`).
- **DB 롤**: `disclosure_migrator`(스키마 소유, Flyway 전용), `disclosure_app`(DML만, RLS 적용), `disclosure_operator`(V4, 운영자 CLI의 `--tenants all` 전용 — `tenant.tenant_id` 컬럼 SELECT와 이 롤 전용 `tenant_directory` 정책만 가진다. 테넌트 데이터 작업은 테넌트마다 `disclosure_app`으로 바인딩해 수행한다), `disclosure_destroyer`(v1.10, Phase 5 V9 — 파기 함수 3개(`ga_document_key_shred`·`ga_disclosure_destroy`·`ga_customer_ref_destroy`)의 EXECUTE **외에 어떤 권한도 없다**. 테이블·컬럼 GRANT 0. 3B가 문서 키 파기를 마이그레이터 경로로 예약한 것을 대체한다 — 마이그레이터는 DDL만), `disclosure_destroy_definer`(v1.11, V9 — 세 함수의 소유자(SECURITY DEFINER). 테이블 소유자가 아니어서 RLS를 그대로 따르고, 지정 컬럼의 UPDATE와 판정 읽기만 가진다). 다섯 롤 모두 NOBYPASSRLS이고 롤과 멤버십은 `init-roles.sql`이 만든다(마이그레이터는 NOCREATEROLE, V9는 존재·멤버십을 단언한다).
- **파기 트랜잭션(v1.11, 5 계획 승인 Q2)**: 파기는 앱 데이터소스의 **한 트랜잭션**이다. 테넌트 바인딩 → 지울 값을 읽어 해시(`pii-columns`의 표현) → 기존 경로로 감사(·아웃박스) 적재 → `SET LOCAL ROLE disclosure_destroyer` → 함수 → `RESET ROLE` → 커밋. 앱 롤은 파기자 롤로 SET ROLE만 할 수 있고(멤버십 `SET TRUE, INHERIT FALSE`) 권한을 물려받지 않으며, 파기자 롤이 가진 것은 함수 호출뿐이다. 함수는 바인딩된 테넌트를 다시 단언하고, 판정(봉인된 종료 상태·보존기한 당일 경과·활성 보류 없음·미파기·키 파기 선행)에 실패하면 GD114로 트랜잭션 전체(감사·아웃박스 포함)가 롤백된다. 불변 트리거는 **정의자 롤 + 함수가 세운 표식(`ga.destroy`)**일 때만 지정 컬럼을 NULL로 바꾸게 한다(앱 롤은 표식을 세워도 롤이 다르고, 파기자 롤은 테이블 권한이 없고, 정의자 롤도 표식 없이는 거부). 마이그레이터는 정의자 멤버십과 트리거 비활성화 권한을 가진 DDL 권한자로서 이 장치의 신뢰 경계 안에 있다. 두 커넥션 설계(파기자 롤 별도 연결)는 체인 연속 검사를 SQL로 한 번 더 구현해야 해서 채택하지 않았다.

  - **객체**는 컬럼이 아니라 ① 키 파기와 ② 객체 삭제로 지운다. 대상은 `document_artifact`의 CANONICAL_JSON·PDF·SIGNED_PDF·EVIDENCE_ZIP과 `signature_evidence`의 STROKES·IMAGE·SCAN이다. ②는 확인서의 산출물·증거 행 전부를 종류와 관계없이 지운다.
  - **남기는 것**: 직원 주체(`agent_id`, `signer_subject`, `actor_subject`, `placed_by` 등)는 고객 개인정보가 아니라 직원 업무 기록이다. 보존·파기는 Phase 6 인가·직원 수명주기와 함께 다룬다.
- **파기 배치(v1.11, 5 계획 §5·§8.5)**: `DestructionJob.run(테넌트, asOf, dryRun, 행위자, 상한)`.
  - **판정**은 순수 함수 `RetentionDecision`이 한다. 오늘은 asOf의 KST 날짜다.
    - 대상: 봉인된 종료 상태(COMPLETED·EXPIRED·VOID·SUPERSEDED) ∧ `retention_until < 오늘` ∧ 보류 없음 ∧ 객체 잠금 적용 기한이 전부 지남 ∧ 대기 중 앵커 없음 ∧ 미파기.
    - 앵커 대기: COMPLETED + `CONTRACT_DATE` 룰 + 계약일 없음이면, 완료일(KST) + `retention.contractLinkWaitDays` < 오늘이 될 때까지 `PENDING_ANCHOR`다. 지나면 파기하고 `anchorsWaived`에 센다. EXPIRED·VOID·SUPERSEDED는 계약일이 생길 수 없어 기다리지 않는다.
    - 건너뜀 사유는 대표 하나와 전체 목록을 낸다. 대표 우선순위는 `ALREADY_DESTROYED > NOT_TERMINAL > HOLD > LOCK_NOT_EXPIRED > PENDING_ANCHOR > RETENTION_NOT_REACHED`다. 보존기한 전인 확인서는 후보 쿼리에서 빠진다.
  - **확인서마다의 순서**(단계별 멱등, 중단 뒤 재실행이 이어받는다):
    - ⓪ 잠금 적용 기한이 남은 객체가 하나라도 있으면 아무것도 바꾸지 않는다(`LOCK_NOT_EXPIRED`).
    - ① 키 파기: 감사 `DOCUMENT_KEY_SHREDDED`, 감싼 키 바이트의 해시를 남긴다.
    - ② 키마다 모든 버전·마커를 ID로 삭제한다. 저장소 잠금 거부면 `LOCK_NOT_EXPIRED`로 보고하고 ③에 들어가지 않는다. 그 밖의 저장소 오류는 실패 `DELETE_OBJECTS`다.
    - ③ 모든 키의 버전·마커가 0인지 확인한 뒤 확인서 파기: 감사 `DISCLOSURE_DESTROYED`, 아웃박스 `DisclosureDestroyed`(식별자·번호·시각만, V10).
    - ①·③·고객 파기는 각각 한 트랜잭션이다. 함수 거부(GD114)는 감사·아웃박스까지 롤백한다.
    - ① 뒤에 보류가 걸리면 ②·③이 멈추고 `holdAfterShred`로 센다(키 파기는 되돌릴 수 없다).
  - **이미 끝난 단계**: V9 함수는 이미 파기된 키·확인서에 GD114로 거부한다(계획 §5.2는 NULL·`ALREADY_DESTROYED` 반환을 예정했다). 그래서 배치가 단계 전에 상태(키 생존·`destroyed_at`)를 읽고 끝난 단계를 건너뛴다. **재실행 멱등의 근거는 함수가 아니라 배치가 단계 전에 읽는 이 상태다**(함수는 기파기를 거부할 뿐 건너뛰지 않는다, 5 수용심사 D9). 함수는 계획보다 엄격하다.
  - **고객 파기**는 확인서 처리 뒤 같은 실행에서 한다. 조건은 live 확인서(봉인 전 초안 포함) 0 ∧ 고객 보류 없음 ∧ 기준일 + 유예 ≤ 오늘이다. 기준일·유예는 마지막 확인서 파기일 + `customerRef.graceDaysAfterLastDestruction`, 확인서가 없었으면 등록일 + `customerRef.abandonedDays`다. 감사는 `CUSTOMER_REF_DESTROYED`이고 이벤트는 없다. 파기된 고객 행은 더 바뀌지 않고(GD113), DELETE는 여전히 GD064다.
  - **dry-run**은 판정만 하고 쓰기가 0이다(감사도 0, 보고서만).
  - **실행 기록**: 테넌트마다 요약 감사 1행 `DESTRUCTION_BATCH_RUN`을 남긴다. 보고서 스키마는 `contracts/verify/v1/destruction-report.schema.json`(닫힌 객체, 개인정보 없음, 형식은 pattern으로 강제)이다.
  - **`verify tenant`**: 파기된 확인서의 객체가 다시 나타나면 `OBJECT_NOT_DELETED`다. `destroyed_at`과 `DISCLOSURE_DESTROYED` 감사가 어긋나면(감사 없는 파기 또는 파기 없는 감사) `DESTRUCTION_UNAUDITED`다. 파기 건의 객체 부재는 정상이다.
- **보존 종료 뒤의 잠금 재적용(v1.11, 승인 Q6(b))**: 적용할 잠금 기한이 이미 지났으면 저장소를 부르지 않는다. 대신 적용 기한을 기록하고 감사 `ARTIFACT_RETAIN.detail.reason = RETENTION_ALREADY_ELAPSED`를 남긴다(S3는 과거 기한을 거부한다).
  - 이 경로는 짧은 보존 데모·테스트(과거 시계)에서만 생겨야 한다.
  - 통합 테스트 실행 끝의 스캔(승인 B3)이 공유 DB 전체에서 이 감사를 찾는다. 짧은 보존 테넌트 열거 밖에서 나오면 실패한다.
  - 대조군으로, 보존 종료 뒤 재적용을 부른 테넌트는 전부 보여야 한다. 스캔 파일이 없어도 Gradle `verifyElapsedRetentionScan`이 실패한다.
- **법적 보류(v1.11, 5 계획 §8.6)**: `LegalHoldService.place|release`. 대상은 확인서 하나 또는 고객 하나이고, 대상당 활성 보류는 1건이다(앱 거부 `ALREADY_HELD` + 유일 인덱스).
  - 사유 코드·텍스트 상한은 설정 시점 룰(`legalHoldReasons`·`legalHoldReasonTextMaxLength`)이다. 감사에는 텍스트 길이만 남긴다. 해제 사유 코드는 §14 #15 전까지 형식만 검사한다.
  - **통제는 DB 보류**다. 파기 배치·파기 함수가 건너뛴다. 저장소 legal hold는 벨트로, 대상 객체의 모든 버전에 켜고 해제 때 끈다. 다른 활성 보류(고객 ↔ 확인서)가 덮는 객체는 끄지 않는다.
  - 저장소 미지원·실패는 결과에 세고 DB 보류는 유지한다. `retention_until`은 바꾸지 않는다.
  - 해제된 보류의 사유 텍스트는 대상의 파기 때 NULL이 된다(V11, `pii-columns`).
- **직접 DB 접근 허용 목록**: 규약은 "**직접 접근 허용 목록은 닫힌 FQN 열거이고, 각 항목은 테넌트 데이터를 읽지 않으며 전용 롤을 쓴다**"이다(Phase 1 심사 확정, CLAUDE.md 규칙 5). 목록은 아키텍처 테스트의 FQN 열거가 정본이며, 폐기된 항목이 남아 있으면 테스트가 실패한다.

- **Phase 9(후속)** — ASSOC 어댑터 실연동, 전자서명 사업자, 자동차보험 템플릿, CRM 연계, 오프라인 초안.
