## 1. 인정하는 것

- **"HTTP 표면이 0이다"를 먼저 적은 것.** `platform-spring`의 보안 설정이 `compileOnly`라 어떤 앱에서도 로드되지 않았다는 사실은 코드를 읽지 않으면 모른다. Phase 0의 "컨트롤러 없음" 단언을 약화가 아니라 **만료**로 분류한 것도 맞다.
- **평문 스캔의 사각**(CLI IT가 `System.out`을 버퍼로 돌려 결과 XML에 가지 않음)을 계획 단계에서 찾아 보완에 넣은 것. 스캔이 "0건"이라고 말할 때 무엇을 보지 않았는지를 아는 것이 스캔의 가치다.
- **Q4.** "해시만 저장"과 "저장 응답 재생"이 양립하지 않음을 짚고, 응답을 닫힌 영수증 스키마로 한정해 둘 다 참이 되게 한 것. 지시문의 두 문장이 충돌했고, 충돌을 푼 방법이 더 강한 제약(개인정보가 들어갈 자리가 스키마상 없음)이다.
- **5.1의 "그 밖의 모든 예외도 거부로"**와 **5.2의 상수 바이트 본문.** 동일 응답을 "같은 코드"가 아니라 "같은 바이트"로 정의했다.
- 멱등에서 **404를 저장하지 않는** 이유(키 재사용으로 과거 존재 여부를 알 수 없게)를 스스로 찾은 것.

## 3. 보강

- **B1. 잠금 상실 감지.** §6.2의 고아 정리는 "잠금 커넥션이 끊기면 DB가 푼다"에 기댄다. 그런데 커넥션만 끊기고 실행기 스레드가 살아 있으면 새 작업이 옛 작업과 **겹쳐 돈다**. `JobRunner`는 보고서 저장·종단 전이 직전에 잠금 커넥션이 살아 있고 잠금을 여전히 쥐고 있는지(`pg_advisory_lock` 보유 확인 — 같은 커넥션에서 `SELECT 1` 뒤 `pg_locks` 조회 또는 커넥션 유효성) 확인하고, 잃었으면 `FAILED(LOCK_LOST)`로 끝내며 보고서를 저장하지 않는다. `JobRunnerIT`에 "실행 중 잠금 커넥션 강제 종료 → 옛 작업 `LOCK_LOST`, 새 작업 정상"을 추가. 주입: 확인 제거 → 두 작업이 모두 SUCCEEDED가 되는 것을 실패로.
- **B2. 공개 경로 한도의 키.** 알려진 테넌트만 키로 둔다는 것은 맞지만, 한도 판정 자체가 "테넌트 존재"를 **시간 차로** 드러내서는 안 된다. 없는 테넌트 접두는 카운터를 거치지 않고 거부되는데, 거부 지점이 달라도 패딩이 전체 응답을 덮으므로 괜찮다 — 이것을 `PublicSignUniformResponseIT`가 "한도 경로 거부와 없는 테넌트 거부의 패딩 요청값이 같은 식(하한 − 경과)"으로 단언하면 충분하다. 별도 장치 불요, 단언만 추가.
- **B3. 설계서 v1.13**: Q5(§4.5 피드 규약 유지, 서명 커서는 목록만), Q6(§9 패딩 하한 = 배포 설정), Q7(§6.7 앵커는 플랫폼 배치), Q15(§7 접두 셋·`/sign/{token}` 삭제), Q1(§5), 지시문 오기 2건 기록.
