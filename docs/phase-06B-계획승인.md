# Phase 6B 계획 승인 (2026-10-09)

## 판정: 승인(§9 고객 등록은 조건부). 넓히는 항목 2건 중 1건 부분 수용·1건 수용. 질문은 요약으로 받은 4건을 결정하고, 나머지는 권장안

단서: 받은 것은 표지 요약이다. 요약에 없는 질문 12건은 **권장안 채택**으로 두되, 불변식·인가 표·동일 응답을 넓히는 것이면 보고서에 따로 표시한다(이미 둘을 표시했으므로 나머지는 넓히지 않는 것으로 읽는다). 6A 첫 커밋 `602d865`의 두 반영(플래그 목록에 번호 외 ID 포함 — 봉인 전 플래그 때문이라는 이유가 맞다; 400 뒤 키 해제가 V13을 요구해 본 DDL이 V14로 밀린 것)은 수용.

## 1. 인정하는 것

- **멱등 `request_hash`가 키 없는 SHA-256이라 사전 대입으로 본문이 복원된다**는 지적. 고객 등록 본문(이름·전화·생년월일)은 정의역이 작아 해시가 곧 값이다 — Phase 5 Q3와 같은 논리를 6A의 산출물에 스스로 적용했다. 6A 심사가 이것을 놓쳤다는 것도 기록한다.
- 징구율 산식을 **규제 문서에서 찾지 못했다고 적은 것.** 보험신보 체크리스트가 "주기 점검" 의무만 적는다는 것까지 확인하고 후보를 근거와 함께 낸 것이 지시문이 요구한 그대로다.
- 계약 연결에서 **기존 컬럼을 이력의 현재값으로 두어 Phase 4·5 로직을 건드리지 않는** 선택. 변경 범위를 줄이는 쪽이 늘 맞다.

## 2. 넓히는 항목 2건

| # | 판정 |
|---|---|
| D2 인가 표 — MANAGER에 `VALIDATE`·`SUPERSEDE` | **`VALIDATE`는 수용, `SUPERSEDE`는 거부.** 검증은 플래그 계산이라 관리자가 돌려도 문서가 바뀌지 않는다. 정정은 **새 버전을 작성하는 행위**이고 그 버전의 `agent_id`는 그 문서에 서명할 설계사여야 한다 — 관리자가 정정하면 `agent_id`가 관리자이거나 재배정 의미가 필요한데 둘 다 설계되지 않았다. 설계사가 퇴사한 문서는 관리자가 **`VOID`**(이미 ORG 권한)하고 다른 설계사가 새로 작성한다. 재배정이 정말 필요하면 §14에 올린다. |
| 멱등 `request_hash` → 서버 키 HMAC | **수용.** 커서 키와 같은 규약(저장소 밖, 600, 운영 필수). 키가 바뀌면 기존 진행 중 청구는 재생 불가 → 새 요청으로 처리(부작용은 상태 가드가 막는다). 6A에 소급하는 수정이므로 설계서 §7에 "6A 결함, 6B 수정"으로 적는다. |

## 4. §9 고객 등록 API — 조건부 승인

본문을 보지 못했으므로 **수용 기준을 조건으로 승인**한다. 하나라도 어긋나면 그 단계 전에 멈추고 묻는다.
1. 요청 본문이 로그·감사·멱등 저장소·예외·응답 어디에도 없고, 멱등 해시는 §2의 HMAC이다.
2. 응답은 가명과 등록 영수증뿐이다.
3. 한도는 룰 데이터이고 초과는 429가 아니라 **같은 422 거부**(열거 방지 — 존재하는 고객 중복 판정도 같은 응답).
4. 이름·전화·생년월일 검색 엔드포인트가 라우트 집합에 없다(테스트).
5. 누출 스캔은 실행 중 생성한 **동적 센티널**(그 요청의 실제 값)로 돈다.
6. Phase 2 `register` 규약(암호화·가명·중복)을 그대로 쓰고 HTTP 계층에 판단이 없다.

## 5. E4
