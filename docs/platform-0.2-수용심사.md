# 플랫폼 0.2.0 정비 수용 심사 (2026-10-14)

PR #15: 수용, 병합 승인. 순서는 제안대로 — #15 병합 → platform-v0.2.0 태그(발행) → 발행 로그의 SHA-256을 #14 §6에 → #14 병합. #14도 그 뒤 병합 승인입니다.

일탈 셋 전부 수용이고, D-1은 제 지시문 오류입니다. schemaVersion·tenantId를 필수로 넣으면 기존 이벤트가 전부 깨지니 "추가형"이라는 제 조건과 제 필드 목록이 서로 모순이었습니다. core = 포털 §4.1의 일곱 필드(version, tenantId 없음)가 맞고, DECISIONS.md에 지시문 오류로 적힌 대로 둡니다. D-2(core가 다른 파일을 참조하지 않고 패턴을 테스트로 대조)와 D-3(disclosure Envelope는 타입·버전별 payload 선택 유지, 앞에 core 참조만)도 맞습니다 — 제가 oneOf라고 쓴 것은 느슨한 표현이었습니다.

인정할 것 둘. format이 2곳이 아니라 6곳이었다는 것 — “2곳”은 핸드오프 때의 관찰이었는데 전수 스캔으로 넓히자 룰·봉인 스키마에서 4곳이 더 나왔습니다. 범위를 넓힌 테스트가 관찰을 고친 사례입니다. 그리고 첫 주입 스크립트가 PL-1을 남긴 채 PL-2를 적용하지 않은 것을 그 실행 전체를 버리고 PL-2·PL-3을 다시 돌린 것 — 오염된 실행의 결과는 성공이든 실패든 쓰지 않는 것이 맞습니다.

API 덤프(verifyPlatformApi)가 check와 발행 워크플로 양쪽에서 돌고, 발행 워크플로가 업로드한 파일과 GitHub Packages에서 다시 내려받은 jar의 SHA-256을 함께 기록하는 것은 H1 재발 방지로 충분합니다. Mac과 Ubuntu 빌드의 jar 해시가 같다는 것도 포털이 메타데이터에 고정할 값이 환경에 흔들리지 않는다는 뜻입니다.
