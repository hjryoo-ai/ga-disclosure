# Phase 4 수용 심사 결과 (2026-10-03)

## 판정: 수용. 단, 절차 위반 1건 기록

**PR #7은 심사 전에 병합됐다.** 지금까지의 규약은 "병합은 수용 심사 뒤"였고(Phase 1~3B 전부 그렇게 했다), 이번 보고는 병합 완료 상태로 왔다. 결과적으로 수용이라 되돌릴 것은 없지만, 심사가 거부했다면 revert PR이 필요했을 것이다. 수용 심사는 병합 게이트다. CLAUDE.md 작업 방식에 한 줄 추가한다: **"PR 병합은 수용 심사 회신 뒤에만. 태그는 먼저 달아도 된다."** 사실 정정이 아니라 규약 추가이므로 이 심사가 그 승인이다.

## 1. 인정하는 것

- **D2 서명 시각의 엄격 증가.** 같은 시각 두 서명의 순서가 흔들려 SEQUENTIAL 검사가 거짓으로 실패한 것(S7)을 "flaky 테스트"로 넘기지 않고, 저장 순서가 서명 순서를 증명하지 못한다는 증거 문제로 읽어 `max(시계, 직전+1µs)`로 고쳤다. 증거 시스템에서 시각은 순서의 증명이라는 점을 정확히 짚었다.
- **D1 잠금 순서 교착 발견.** 계획(세션 → 확인서)을 구현 중 뒤집어 모든 경로가 확인서를 먼저 잠그게 했다. 계획을 고친 사유가 교착이라는 구체적 사실이다.
- **D11 — 3A·3B의 규칙 5 위반을 소급 수정.** 확인서 `agent_id`에 행위자 subject를 그대로 저장하던 것을 `identity_link` 해석으로 바꿨다. 이전 Phase의 결함을 다음 Phase가 잡아 고친 첫 사례다. 3A·3B 심사가 이것을 놓쳤다는 것도 함께 기록한다.
- **D10 ZIP DOS 시각 00:00:02.** 00:00:00이 JDK에서 확장 타임스탬프를 붙여 결정론을 깨는 것을 G8이 잡았다. 이런 종류의 발견은 테스트가 있어야만 나온다.
- **S9 첫 주입의 실패 0을 "중복 방어"로 진단**하고, 테스트를 손대지 않은 채 빠진 경계 사례(UTC 자정을 넘는 하나의 KST 날)를 추가한 뒤 다른 주입으로 대체한 것.
- 매니페스트 예시를 **저장소 코드 없이 Python으로 독립 검증**한 것. 자기 코드로 자기 산출물을 검증하는 순환을 피했다.

## 2. D1~D11 판정

전부 수용. 불변식을 넓힌 것은 없다. D3(존재 누설 — 테넌트 행이 있을 때만 감사)는 Phase 6 공개 엔드포인트의 응답 지연 동일화와 짝을 이뤄야 완성된다(Phase 6 완료 기준으로 이월됨). D7(문서 사건은 언제나 REVOKED)은 지시문 문언보다 정확하다 — 설계서 §6.5에 그대로.

## 3. Phase 5 질문 8건과 승인 2건

**승인 ① BouncyCastle `bcpkix-jdk18on` 추가: 승인.** Boot BOM 비관리이므로 최신 안정판 확인 후 고정, 라이선스(MIT 계열) 기록. 용도는 **RFC 3161 토큰 생성(테스트 스텁 TSA)·검증**에 한정하고, 아키텍처 규칙으로 `org.bouncycastle..` 참조를 `disclosure-audit`의 `..tsa..` 패키지와 테스트 픽스처로 제한한다.

**승인 ② 파기와 규칙 2: 승인, 규칙 문구 한 줄 추가.** 권장 해석("파기는 본문을 바꾸는 것이 아니라 보존 의무가 끝난 개인정보를 지우는 것")을 채택한다. CLAUDE.md 규칙 2에 덧붙인다: *"봉인 본문은 **보존기간 중** 불변이다. 보존기간 종료 후 파기는 전용 롤의 파기 함수만이 지정 컬럼을 NULL로 바꿀 수 있고, 번호·상태·해시·시각·체인은 묘비로 남는다. 파기 감사에는 지운 값의 해시를 남긴다."* 파기 함수는 세 번째 직접 접근 허용 목록 항목(`disclosure_destroyer` 롤)이다.

| # | 결정 |
|---|---|
| 1 | **일일(KST) 테넌트별 앵커 레코드 → 머클 루트 1개 외부 고정** 채택. 보강: 잎을 **고정 깊이**(예: 16)로 패딩해 경로 길이가 테넌트 수를 드러내지 않게 한다. 패딩 잎은 결정론적 상수 해시. |
| 2 | **패키지는 다시 만들지 않는다.** `anchor` = 완료 시점에 이미 있던 최신 앵커 참조(없으면 null). 이후 증명은 불변 객체 `anchor_receipt`(테넌트별 행: 앵커·배치 ID·루트·머클 경로·TSA 토큰). `verify`가 `chainSeq`·`audit.toSeq`를 덮는 첫 영수증을 찾아 잇는다. **배치(루트·토큰)를 담는 테넌트 없는 테이블은 만들지 않는다** — 영수증 행마다 루트·토큰을 중복 저장한다(작다). 배치 계산은 `TenantDirectoryReader`로 테넌트를 순회하되 쓰기는 테넌트 트랜잭션별로. |
| 3 | **TSA는 일일 루트에만.** 포트 + 로컬 스텁(BouncyCastle 자체 서명 TSA, 테스트 픽스처·데모 프로파일). 토큰 검증은 **설정된 신뢰 앵커**에 대해서만. 실제 TSA 기관·인증서 체인 보관은 §14 #4 그대로 운영 결정. |
| 4 | **`verify package`(오프라인) · `verify tenant`(온라인) 두 명령** 채택. 출력은 JSON 보고서 + 종료 코드(0 일치 / 2 불일치 / 3 입력 오류). `verify tenant` 불일치는 `CHAIN_BROKEN` 플래그. 패키지 단독으로 체인 연속을 증명하지 못한다는 한계는 `verify package` 보고서에 **명시적 문장**으로 출력한다. 보강: 영수증 내보내기에 **봉인 체인 구간(해시만)** 을 함께 담아, 패키지 + 영수증만으로 "이 문서가 TSA 시각 이전에 이 내용으로 존재했다"를 오프라인에서 증명할 수 있게 한다. 감사 체인 연속은 `verify tenant`만(감사 행 내보내기는 하지 않는다). |
| 5 | **파기 순서 채택**: ① 문서 키 파기 → ② Object Lock 만료 확인 후 객체 삭제 → ③ DB 묘비(번호·상태·해시·시각·체인 유지, 지정 컬럼 NULL). 대상 컬럼은 **최소** `recommendation.reason_text`, 무효·정정 `reason_text`, `signature.device`·`ip`·`view_evidence`(기기·IP는 개인정보다), `signature_evidence`(객체), `document_key.wrapped_dek` — 전수 목록은 지시문대로 기계 판독 표로 만들고 테스트가 파기 함수와 대조한다. `customer_ref`의 이름·전화·생년월일은 **그 고객의 살아 있는 확인서가 0건**이고 마지막 활동 + 보존연수가 지났을 때 같은 함수가 NULL로(GD064 DELETE 금지 유지, 묘비). 파기 감사 1행에 지운 값의 해시. |
| 6 | **계약일 앵커 대기 채택**: `retentionAnchors`에 날짜 없는 앵커가 있으면 파기 보류, `contractLinkWaitDays` 경과 시 "계약 없음" 확정. 룰 키 추가. |
| 7 | **`legal_hold` 채택**(준법 역할, 설정·해제 감사, 보존기한 불변). 배치는 보류 건을 건너뛴다. S3 legal hold API는 `ArtifactStoreContract`에 항목을 추가해 SeaweedFS 지원을 확인하고, 미지원이면 **DB 보류 + Object Lock 보존이 통제**임을 설계서에 적는다(배치 건너뜀이 실제 통제, S3 보류는 벨트). |
