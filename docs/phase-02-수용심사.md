# Phase 2 수용 심사 결과 (2026-09-30)

## 판정: 수용. PR #3 병합 승인 (merge commit)

E3(엔진 PR #1)는 **아직 심사하지 않았다.** 백그라운드 에이전트의 결과는 다른 Phase와 같은 형식의 보고서(`docs/phase-E3-보고서.md`: 커밋·테스트 건수·E1~E12 증거·설계서 변경·계약 변경 요청)로 올려야 심사한다. 그 전에는 엔진 PR을 병합하지 않는다. "에이전트 보고 기준으로 CI 통과"는 증거가 아니다.

## 1. 인정하는 것

- **평문 유출 검사의 범위.** 테스트 결과 XML 49개·DB 덤프·PostgreSQL 서버 로그·예외 메시지까지 검사 대상에 넣은 것. 서버 로그를 포함한 것이 중요하다 — 애플리케이션이 안 남겨도 DB가 바인드 값을 로그에 남기는 경로가 있다.
- **데모 고객 등록을 구현하지 않은 판단.** CLI 인자가 셸 이력에 남는다는 이유로 멈춘 것은 규칙 6을 결과물이 아니라 작업 방식에까지 적용한 것이다. 처리 방식은 §3.
- **플랫폼 0.1.0을 mavenLocal 없이 GitHub Packages만으로 소비 빌드**한 것. "발행됐다"가 아니라 "소비된다"를 증명했다.
- **계약 PR #2를 먼저 병합하고 브랜치에 반영**한 순서. 두 저장소가 공유하는 접점을 다루는 규칙이 지켜졌다.

## 3. §9 질문에 대한 결정

**1. 상품 키 길이: 엔진의 40자에 맞춘다.** 상품 키는 엔진이 수수료 데이터를 갖는 상품의 식별자이므로 엔진의 도메인이 기준이다. 계약 `productKey`: `maxLength: 40`, `pattern: ^[A-Z0-9]{1,8}:[A-Za-z0-9._-]{1,31}$`(보험사 코드 ≤ 8 + `:` + 코드 ≤ 31). `disclosure-domain`의 `ProductKey`도 같은 규칙, 카탈로그 수입은 규칙에 맞지 않는 키를 **자르지 않고 거부**하며 행 번호와 함께 보고한다. 계약 PR로 처리(§3-3과 묶어서).

**2. 엔진 `contracts/UPSTREAM`: 병합 커밋(440a009)으로 바꾼다.** 규칙으로 명문화: UPSTREAM은 항상 `ga-disclosure` `main`에서 도달 가능한 커밋을 가리킨다. 계약 변경 순서는 (ⅰ) `ga-disclosure` 계약 PR 병합 → (ⅱ) 엔진이 UPSTREAM을 그 병합 커밋으로 갱신 + CHECKSUMS 재검사. 엔진 쪽 CI에 "UPSTREAM 커밋이 `ga-disclosure` main의 조상인지" 검사를 두는 것은 선택(원격 조회가 필요하므로 강제하지 않는다).

**3. E3의 계약 후속 작업: Phase 3 전에 계약 PR로 처리한다.** 단, 내용을 아직 보지 못했다. E3 보고서에 변경 요청 목록을 실어 올리고, 그중 **추가만 하는 변경**(새 `reason` 값, 새 오류 코드, 선택 필드 추가)은 심사 없이 계약 PR에 포함해도 된다. `OK`/`UNAVAILABLE`의 형태, `ratioToAvg`·`tieBreak`·`rankInSet` 의미에 닿는 변경은 심사 뒤에 한다.

**4. 봉인 본문에 고객 성명: 넣는다. 권장안(customer_ref만)은 기각.** 이유는 세 가지다.
- 확인서는 **고객에게 교부되는 문서**이고, 서명자가 누구인지 문서 자체가 말해야 증거다. 성명 없는 서명 문서는 사후 점검·민원에서 "그 고객에게 설명했다"를 증명하지 못한다.
- 봉인의 결정론(canonical JSON + 템플릿 → 같은 PDF)은 렌더 시점에 외부 값을 주입하는 순간 깨진다. 성명을 PDF에는 넣고 canonical에는 안 넣는 방식은 §6.4 7항과 양립하지 않는다.
- "불변 보관물에 PII가 영구히 남는다"는 전제가 틀렸다. 보관물은 **법정 보존기간 동안** 남고, 그 기간이 지나면 §9 파기 배치가 지운다. Object Lock 보존기간 = `retention_until`이므로 그 뒤의 삭제는 가능하다. PII를 보존기간 동안 보관하는 것이 규제의 요구 그 자체다.

따라서: 본문에는 **성명만** 들어간다(전화·생년월일·`customer_ref` 이외 식별정보는 절대 넣지 않는다). 봉인 산출물(canonical JSON·PDF·증거 패키지)은 오브젝트 스토리지에 **테넌트 키로 암호화**(SSE-KMS 또는 클라이언트 측 봉투 암호화, 어댑터가 결정)해 저장하고, Phase 5 파기는 객체 삭제 + 해당 문서 데이터 키 파기(crypto-shredding — 백업에 남은 사본도 무의미화)로 한다. 봉인 산출물 열람은 전 건 감사. 설계서 §6.4·§9에 이 결정을 적는다.

**5. 임시등록 판정: 이 시스템의 `temp_product`만으로 한다. 임시등록 상품은 엔진에 보내지 않는다.** 엔진 도메인에 없는 상품이라 키를 지어 보내면 충돌 위험만 있다. 워크플로가 로컬에서 `UNAVAILABLE(reason=TEMP_PRODUCT, source=LOCAL)`로 표기하고 순위 세트에서 제외한다(엔진이 `OK`만으로 순위를 매기는 규칙과 일치). §6.3 (i) "응답 집합 = 요청 집합" 검사는 **임시등록을 제외한 항목**에 적용한다. 엔진의 `unavailableReasons` 데이터에서 `TEMP_PRODUCT`를 뺀다(데이터 변경, E3 후속). `disclosure_item`에 `grade_source TEXT`(ENGINE|LOCAL)를 V6에 추가.
